## 1. 项目背景与目标

### 1.1 背景

随着大语言模型能力提升，AI Agent 已从代码补全工具演进为可执行多步骤研发任务的工程化系统。本项目旨在建设一个**面向软件研发团队的 AI Agent 平台**，覆盖需求理解、代码分析、任务规划、代码修改、测试验证到 Pull Request 创建的完整研发闭环。

### 1.2 核心价值主张

> 用户提交一个 Issue 或研发任务，Agent 理解项目上下文，生成实施计划，在隔离环境中完成代码修改并运行验证，最终产出可供人工审查的 Pull Request。

第一阶段目标不是"无人值守的自动软件工程师"，而是一个**可控、可审查、可恢复、可审计**的研发 Agent 平台。

### 1.3 产品边界（MVP）

**包含**：
- 单组织、单仓库，GitHub 优先接入
- Bug 修复和小型功能开发
- Issue 到 PR 的完整闭环
- 统一 Model Gateway 接入单一主流大模型
- Web 任务控制台
- 任务创建、规划、审批、执行、暂停、恢复、取消
- 代码读取、搜索、编辑、Git、测试、有限 Shell 工具
- Linux 云端生产沙箱，网络按已批准连接器策略开放
- 基础 RBAC、Policy Gateway、审计
- Diff、测试证据、PR 创建

**不包含**：
- 自动合并生产代码
- 生产数据库/生产环境直接访问
- 完全无人审批的高风险操作
- 无边界浏览器自动化
- 复杂多 Agent 自由协作
- 多仓库、复杂 Monorepo、长期组织记忆
- 自研基础模型、复杂计费系统

### 1.4 版本规划路线图

| 版本 | 主要范围 | 自主级别 |
|-----|---------|---------|
| **MVP** | Issue 到 PR 的基本闭环 | 建议与执行并存，合并必须人工确认 |
| **V1** | 权限、审批、策略、审计、质量门禁、评估平台 | 按风险级别控制自主执行 |
| **V2** | 多仓库、知识库、Webhook、异步任务、IDE/CLI | 低风险任务可无人值守 |
| **企业版** | SSO/SCIM、SIEM、私有化、多模型、多 Agent | 组织级策略和自动化治理 |

## 4. 总体架构需求

### 4.1 分层架构（6 层）

```text
用户体验层        Web 控制台 / 对话 / 任务 / Diff / PR / CLI
接入与集成层      GitHub / GitLab / Issue / Webhook / SSO / IDE / MCP / 模型接口
Agent 控制平面    任务编排 / 计划 / 上下文 / 工具 / 策略 / 模型路由 / 审批 / 状态机 / 预算 / 重试
Agent 执行平面    Workspace / Docker 沙箱 / 文件 / Shell / Git / 测试 / 构建 / 网络白名单
质量与安全平面    Lint / Test / SAST / SCA / Secret Scan / 覆盖率 / 许可证 / PR 门禁 / 回滚
数据与观测平面    PostgreSQL / 向量库 / 事件 / 审计 / 指标 / Trace / 成本 / 评估 / 告警
```

**核心隔离原则**：
- 控制平面负责任务状态、模型调用、工具授权、审批、策略和审计
- 执行平面负责文件操作、Shell、Git、测试、构建和依赖安装，必须运行在隔离容器/微虚拟机中
- 控制平面不能直接将宿主机权限暴露给 Agent
- 每个任务使用独立工作区，完成后清理或归档

### 4.2 六层 Harness 架构

每个 Worker 遵循统一职责边界：

| 层 | 职责 |
|---|---|
| Identity Harness | 用户、组织、项目、仓库和任务身份 |
| Context Harness | 按权限和预算加载上下文 |
| Tool Harness | 按 Worker 能力暴露工具 |
| Execution Harness | 工作区、沙箱、网络和资源限制 |
| Policy Harness | 风险、审批、预算和输出校验 |
| Evidence Harness | 事件、Trace、Artifact、Evidence 和指标记录 |

### 4.3 Agent 执行分层与边界规则

```text
Durable State Machine（持久化/暂停/恢复/重试/超时/审批等待）
  → Workflow DAG / Coordinator（Worker依赖/并行/汇聚/有限重规划）
    → Worker ReAct Loop（局部推理和工具选择）
      → Action（动作提议）
        → Policy Gateway（策略网关，唯一执行决策入口）
          → Tool / Sandbox（工具执行/沙箱）
            → Observation / Evidence（观察结果/证据）
```

**强制边界规则**：
- 模型不能直接执行 Action
- Worker 不能绕过 Policy Gateway
- Worker 之间通过结构化 Artifact 和 Evidence 协作，不共享完整对话历史
- 不允许无限递归创建 Worker

### 4.4 Coordinator + 专家 Worker 编排

| Worker 类型 | 职责 | 权限 |
|---|---|---|
| Explorer | 代码库探索、依赖和影响范围分析 | 只读 |
| Planner | 生成实施计划、风险和验收条件 | 只读 |
| Coder | 按已批准计划修改代码 | 可写，限任务分支 |
| Tester | 设计和执行测试、分析失败 | 默认只读 |
| Reviewer | 检查 Diff、质量、安全和规范 | 只读 |
| Resolver | 处理测试或评审失败 | 可写，限任务分支 |
| Release | 生成 PR、发布说明和交付摘要 | 只读 |

**任务图基线**：

```text
Explorer → Planner → [人工审批] → Coder ─┐
                 │                        ├→ Reviewer → Release
                 └────→ Tester ───────────┘
```

## 6. 非功能性需求

### 6.1 性能需求

| 指标 | 目标值 | 来源模块 |
|---|---|---|
| 检索端到端延迟 | p50 < 200ms，p95 < 500ms | CTX-004 |
| 检索召回率/精确率 | Recall@20 > 85%，Precision@5 > 75% | CTX-004 |
| 索引构建时间 | SMALL<5s，MEDIUM<30s，LARGE<120s | CTX-002/003 |
| 沙箱分配延迟 | p95 ≤ 200ms | SEC-004 |
| 任务恢复成功率 | > 95% | 验收标准 |
| 工具调用成功率 | > 98% | 验收标准 |
| p95 任务耗时 | < 30 分钟 | 验收标准 |

### 6.2 安全需求

- 零信任、默认拒绝、最小权限贯穿所有模块
- Agent 不持有长期凭据，凭据短期、范围受限、任务绑定并可审计
- 所有 Action 经过 Policy Gateway 双重策略校验（前/后）
- 支持从单个 Action 到全局的 Kill Switch（M0-M5 六模式）
- 安全扫描违规拦截率 = 100%，Secret 泄露拦截率 = 100%
- 高风险操作必须人工审批；审批默认 24 小时有效

### 6.3 合规与数据治理需求

- 数据分级 L1 公开 / L2 内部 / L3 敏感 / L4 机密
- 事件分层留存：30 天热存储 + 180 天冷存储 + 合规保留；审计归档可达 3-7 年
- 合规规划顺序：ISO 27001 → SOC 2 → GDPR（按需）
- 分级审批 + HITL（Human-in-the-loop）合规删除流程
- 多租户强制隔离（计算 Pool + 存储/密钥 per-team 隔离）

### 6.4 可靠性与可观测性需求

- 事件事实源 + 状态投影 + 检查点恢复三位一体
- 全链路 Trace 关联（Task→Workflow→Worker→Action→Tool/Model/Sandbox）
- 审计日志与普通运行日志物理分离
- 故障注入覆盖 8 大类别，恢复成功率 ≥ 90%

### 6.5 成本需求

| 指标 | 目标值 |
|---|---|
| 单任务 Token 消耗 | < 100K |
| 单任务模型成本 | < $0.50 |
| 每项目月度成本 | < $500 |
| 缓存命中率 | > 60% |

## 7. 需求优先级与依赖关系

### 7.1 优先级分布

- **P0（4 个主题规范，占阻塞地位）**：01-运行时基础契约、02-安全威胁模型、03-失败恢复与重试、05-评估体系（含 HAR、OBS 并入 P0 管理）
- **P1（1 个主题规范）**：04-上下文管理与代码索引（含 MEM 记忆管理）

### 7.2 模块依赖关系图（文字版，图形版见配套 XMind 文件）

```text
01-运行时基础契约（RT）── 所有模块的共享坐标系（Task/Workflow/Action/Trace/Version）
    │
    ├──→ 02-安全威胁模型（SEC）── 依赖 RT 的身份与状态契约
    │
    ├──→ 03-失败恢复与重试（REL）── 依赖 RT 的事件/检查点契约，依赖 SEC 的审批/Kill Switch
    │
    ├──→ 04-上下文管理与代码索引（CTX）── 依赖 RT 版本坐标，依赖 SEC 的权限/租户隔离
    │       └──→ 05-记忆管理（MEM）── 依赖 CTX 的 Context Selector，依赖 SEC 的租户隔离
    │
    └──→ 05-评估体系（EVA）── 依赖 RT/REL 的 Task/Failure 模型，依赖全部模块产出证据

Harness 工程（HAR）── 横向贯穿，依赖 RT/SEC/CTX/REL，为 Worker 提供六层运行时边界
可观测性（OBS）── 横向贯穿，依赖 RT-006（Trace），为 SEC/REL/EVA 提供证据与告警联动
```

### 7.3 冻结顺序（官方既定顺序）

```text
Runtime Contract v1
  → Security Threat Model v1
    → Failure Recovery Baseline v1
      → Context and Code Index Baseline v1
        → Evaluation and Release Gate v1
```

## 8. 风险与开放问题

### 8.1 技术风险

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 事件存储性能不足 | 高 | 中 | 提前压力测试，准备分片方案 |
| 检查点恢复时间过长 | 中 | 中 | 优化检查点大小，使用增量检查点 |
| 沙箱冷启动慢 | 中 | 高 | 使用预热池（WarmPool） |
| 检索质量不达标 | 高 | 中 | 多方案对比，及时调整 |
| 模型成本超预算 | 高 | 中 | 严格预算限制，优化 Prompt |

### 8.2 组织风险

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 人力不足 | 高 | 中 | 优先完成 P0 功能 |
| 跨团队协作困难 | 中 | 高 | 定期同步会，明确责任边界 |
| 需求变更频繁 | 中 | 高 | 先冻结核心契约，减少返工 |

### 8.3 当前唯一未完成需求

- **`REQ-EVA-007`（生产反馈、数据集更新和版本回滚）**：待详细设计。核心职责已收窄为补齐"评估模块主动发起、面向生产态漂移的回滚触发路径"，不新增 OBS 采集基础设施，不重新设计 Kill Switch。存在与 `EVA-006` 触发器 Schema 协同的中等风险，非阻塞性。

### 8.4 跨模块冻结风险

- 全部 60 项已完成详细设计的需求均**未经跨模块评审与冻结**，可能在评审中发现接口不一致（例如 EVA-007 与 EVA-006 的触发器字段）。
- 当前没有任何模块标记为"已实现并验证"，所有设计结论在编码前仍可调整。

## 9. 结论与建议

1. **设计完成度高，但未进入实现**：60 项正式基线需求（100%）均已完成详细设计，整体设计体系完整覆盖运行时、安全、可靠性、上下文、记忆、Harness、可观测性和评估八大领域，但全部待跨模块评审与冻结，不可直接作为开发依据。
2. **下一步行动建议**：
   - 优先完成 `REQ-EVA-007` 详细设计，使 60 项基线需求 100% 完成设计；
   - 启动 Runtime Contract v1 的跨模块交叉评审，作为后续安全、可靠性、上下文、评估模块冻结的前置条件；
   - 按既定冻结顺序（RT→SEC→REL→CTX→EVA）推进评审，避免并行冻结导致坐标系不一致。
3. **风险提示**：所有版本号为 `v0.x-designed` 的内容仅为设计输入，不得在未冻结前进入编码实现；`REQ-EVA-007` 的触发器 Schema 变更风险需在详细设计阶段与 `EVA-006` 作者协同确认。
