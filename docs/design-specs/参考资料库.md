### 2.1 Anthropic - Demystifying evals for AI agents

**资料信息**：
- **标题**：Demystifying evals for AI agents
- **来源**：https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- **发布日期**：2026-01-09
- **访问日期**：2026-10-05, 2026-10-06
- **证据等级**：A（官方工程博客，一次来源）
- **引用需求**：REQ-EVA-007（生产反馈、数据集更新和版本回滚）

**关键引用段落**：

> **原文位置**："How evals fit with other methods for a holistic understanding of agents"章节，方法对比表后段
>
> **引用内容**："These methods map to different stages of agent development. Automated evals are especially useful pre-launch and in CI/CD, running on each agent change and model upgrade as the first line of defense against quality problems. **Production monitoring kicks in post-launch to detect distribution drift and unanticipated real-world failures.** A/B testing validates significant changes once you have sufficient traffic. **User feedback and transcript review are ongoing practices to fill the gaps**: triage feedback constantly, sample transcripts to read weekly, and dig deeper as needed."

**借鉴点**：
1. 评估方法需要分阶段部署：pre-launch（自动化 evals）vs post-launch（生产监控）
2. 生产监控的核心目标是"检测分布漂移"（distribution drift）和"预料外的真实世界故障"
3. 用户反馈和转录审查是"持续实践"（ongoing practices），而非一次性工作

---

> **原文位置**："Capability vs. regression evals"章节
>
> **引用内容**："Capability or 'quality' evals ask, 'What can this agent do well?' They should start at a low pass rate, targeting tasks the agent struggles with and giving teams a hill to climb. Regression evals ask, 'Does the agent still handle all the tasks it used to?' and should have a nearly 100% pass rate. They protect against backsliding, as a decline in score signals that something is broken and needs to be improved. As teams hill-climb on capability evals, it's important to also run regression evals to make sure changes don't cause issues elsewhere. **After an agent is launched and optimized, capability evals with high pass rates can 'graduate' to become a regression suite that is run continuously to catch any drift.**"

**借鉴点**：
1. Capability evals 与 regression evals 的明确区分（低通过率 vs 接近 100% 通过率）
2. Capability evals 饱和后应"毕业"为 regression suite，持续运行以捕获漂移
3. 这一转换机制暗示了评估集需要动态更新（从"爬坡目标"变为"回归检测基准"）

---

**应用于 REQ-EVA-007 的设计启示**：
- 生产反馈采集不是可选的"Phase 2 功能"，而是评估体系从 pre-launch 到 post-launch 的必经阶段转换
- 分布漂移检测需要独立于"代码/配置变更检测"的信号源（即使快照不变，模型供应商侧更新仍可能引发漂移）
- Golden Dataset 更新应支持"capability eval → regression suite"的转换流程

### 5.2 OWASP Top 10 for Agentic Applications 2026

**资料信息**：
- **标题**：OWASP Top 10 for Agentic Applications 2026
- **来源**：https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/
- **发布日期**：2025-12-09
- **访问日期**：2026-10-06
- **证据等级**：A（安全领域权威标准，全球 100+ 专家协作评审）
- **引用需求**：REQ-SEC-010（红队验证矩阵 D1-D6 域映射），`AGENTS.md` §7（威胁模型对照）

**完整 ASI01-ASI10 清单与本项目映射**：

| ASI 编号 | 威胁名称 | 定义 | 本项目对应控制与域 |
|---------|---------|------|-------------------|
| ASI01 | Agent Goal Hijack | 不可信内容（Issue/PR/仓库文件/网页）重定向 Agent 目标或插入隐藏子目标 | REQ-SEC-006 Prompt 注入防护；REQ-SEC-010 D2 域 |
| ASI02 | Tool Misuse and Exploitation | 合法工具被诱导以非预期参数/顺序/频率调用或串联出未预期操作 | REQ-SEC-003 Policy Gateway；REQ-SEC-010 D3 域 |
| ASI03 | Identity & Privilege Abuse | 凭据/权限越界使用、跨租户访问 | REQ-SEC-002 RBAC、REQ-SEC-005 凭据代理；REQ-SEC-010 D1/D5 域 |
| ASI04 | Agentic Supply Chain Vulnerabilities | 依赖、容器镜像、MCP 连接器、第三方插件被投毒或篡改 | REQ-SEC-007 MCP 连接器治理；REQ-SEC-010 D4 域 |
| ASI05 | Unexpected Code Execution | 自然语言驱动的意外代码执行、沙箱逃逸 | REQ-SEC-004 沙箱隔离；REQ-SEC-010 D4 域 |
| ASI06 | Memory & Context Poisoning | 记忆/上下文被污染后长期影响后续决策 | REQ-MEM-*；REQ-SEC-010 D2 域 |
| ASI07 | Insecure Inter-Agent Communication | Worker 间消息被伪造或篡改 | REQ-HAR-* Harness 间通信；REQ-SEC-010 D3 域（若连接器承载跨 Agent 消息） |
| ASI08 | Cascading Failures | 一个 Worker 的错误信号级联放大到整条任务链 | REQ-REL-* 重试与补偿；REQ-SEC-010 D6 域 |
| ASI09 | Human-Agent Trust Exploitation | 自信但错误的解释误导人工批准高风险操作；审批疲劳 | 审批 UI 必须展示可核验的结构化 Diff/Action 清单；REQ-SEC-010 D6 域专项验证 |
| ASI10 | Rogue Agents | Worker 偏离既定目标、隐瞒行为或自主扩权 | REQ-SEC-009 Kill Switch 必须不依赖目标 Worker 自身配合；REQ-SEC-010 D6 域专项验证 |

**核心设计启示**：
- ASI01-ASI10 是专门针对**自主 Agent 系统**（能规划、选择工具、执行、保持记忆、委托、产生副作用）的威胁分类，比通用 LLM Top 10 v1.1 更贴合本项目特征。
- ASI09（Human-Agent Trust Exploitation）和 ASI10（Rogue Agents）是之前 LLM Top 10 未覆盖的新类别，直接对应本项目"强审批门禁"模式下的审批疲劳与过度信任风险、以及 Worker 自主行为失控风险。
- 本项目 `REQ-SEC-010` 的 D1-D6 六个攻击面域与 ASI01-10 为**多对多映射**（同一 ASI 可分布在多个域，同一域可覆盖多个 ASI），不能因"已在某域覆盖该 ASI"就跳过其在其他域的变体。
- `AGENTS.md` §7「威胁模型对照」段落在 2026-10-06 已补全 ASI01-10 的日常自查条款，与 `REQ-SEC-010` D1-D6 矩阵保持同源；两者冲突时必须修复文档漂移。

**与 §5.1 OWASP LLM Top 10 v1.1 的关系**：
- LLM Top 10 v1.1（LLM01-LLM10）针对模型本身的安全风险（训练数据投毒、模型拒绝服务等），部分与 ASI 重叠（LLM01 Prompt Injection ≈ ASI01 Goal Hijack）但视角不同。
- Agentic Top 10 2026（ASI01-ASI10）针对具有自主性的 Agent 系统在工具调用、身份、记忆、多 Agent 协作、人机协作等场景的独有威胁。
- 本项目应**同时**对标两者：模型层安全参照 LLM Top 10 v1.1（已体现在 REQ-SEC-001/006），Agent 系统层安全参照 Agentic Top 10 2026（已体现在 REQ-SEC-010 和 AGENTS.md §7）。

## 10. 资料维护流程

### 10.1 新增资料

1. 确认资料符合证据等级定义（A/B/C）
2. 填写完整元数据（标题、来源、发布日期、访问日期、证据等级、引用需求）
3. 摘录关键段落或章节（不超过 500 字）
4. 标注"借鉴点"（对应本项目哪个设计决策）
5. 提交 PR，由架构组 review 后合并

### 10.2 资料失效检查

每季度复核一次所有资料：
- 检查 URL 是否失效（返回 404 或重定向）
- 检查是否有新版本发布（如 OWASP Top 10 v1.2）
- 更新访问日期和证据等级（如社区项目停止维护，降级为 C 级）

### 10.3 冲突资料处理

如果两份资料对同一问题给出不同建议：
- 优先采用证据等级更高的资料（A > B > C）
- 优先采用发布日期更新的资料
- 如果等级和日期相同，在需求文档中说明"存在两种业界实践"，并给出选择理由
