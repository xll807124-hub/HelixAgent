# 阶段 0 设计冻结 - 跨模块接口对齐检查清单

>
> 1. 冲突 2 写的"凭据最长有效期 2 小时"无出处。`REQ-SEC-005` 实际为按服务类型配置上限（GitHub ≤ 1h，AWS ≤ 15min，OAuth ≤ 30min），租约不可续期；暂停任务的凭据在 TTL 内继续有效，TTL 已过则重新申请（SEC-005 第 287 行）。
> 2. 冲突 3 与设计点 1 把 Kill Switch `M2` 当作"停用工具"。`REQ-SEC-009` 中 `M2` 是 APPROVALS_REQUIRED（写操作与高风险操作需双人审批，15 分钟自动解除），并非停用工具。"M2 可在 30 秒内触发"也无出处，30s 是 MTTC-p99 传播目标。
> 3. 设计点 1 写的"Policy 缓存 5 分钟"无出处。`REQ-SEC-003` 对高风险或写操作的缓存是 30 秒至 1 分钟，或不缓存。

## 🔴 需要紧急确认的冲突点（P0）

### 冲突 1：Task 创建时 Prompt 注入防护时机

**问题**：
- RT-001 说 Task 的 title/description 是用户输入
- SEC-006 说需要检测 Prompt 注入
- **何时执行？**

**当前设计**：Task 创建时通过 Prompt 检测引擎扫描 → 低风险继续 → 中高风险要求确认

**需确认**：
- [ ] Task 创建是否阻塞在检测上？
- [ ] 检测失败时返回什么错误？
- [ ] 误报率多少时 User 可以申请绕过？

**建议决策**：Task 创建不阻塞，但风险评分会升高，导致后续更严格的审批。

---

### 冲突 2：Checkpoint 中的凭据有效期管理

**问题**：
- RT-005 需要保存恢复所需的工作区引用
- SEC-005 说凭据最长有效期 2 小时
- **如果 Checkpoint 创建时凭据有效，但 2 小时后恢复时凭据已过期怎么办？**

**当前设计**：Checkpoint 不保存凭据本身，仅保存凭据 ID 和签发时间戳

**需确认**：
- [ ] 恢复时自动获取新凭据是否算"重新授权"？
- [ ] 新凭据权限与原凭据相同吗？
- [ ] 如果权限变化（用户被移出仓库），恢复应拒绝吗？

**建议决策**：恢复时重新签发凭据，需重新评估权限。权限变化时恢复拒绝，进入人工审查。

---

### 冲突 3：Kill Switch 期间的 Checkpoint 创建

**问题**：
- RT-005 说异常时可以创建 Checkpoint 用于后续恢复
- SEC-009 说 M2+ 会禁用工具或停止任务
- **M2 停用某工具时，应该创建还是丢弃 Checkpoint？**

**当前设计**：M2 停用工具时，允许创建 Checkpoint（为了未来恢复知道停在哪里），但不允许新 Action 使用该工具。

**需确认**：
- [ ] 恢复时该工具仍被禁用，恢复会再次失败，这是预期的吗？
- [ ] 应该自动跳过失败 Action 还是交给人工决定？

**建议决策**：恢复时应让操作者知道"该工具已被禁用"，交给人工决定重新启用或替换工具。

---

### 冲突 4：审计日志保留期与事件历史分段

**问题**：
- RT-008 说审计日志 30 天热存储 + 180 天冷存储
- RT-005 说长事件历史需要分段（Continue-As-New）
- **分段后的旧 Workflow 事件如何在审计日志中查询？**

**当前设计**：旧 Workflow 事件保留完整链接，查询时通过 `parent_workflow_id` 穿透查询。

**需确认**：
- [ ] 冷存储中的事件查询延迟可以接受吗（预期 < 5 分钟）？
- [ ] 跨 Workflow 审计追踪是否需要特殊权限？

**建议决策**：冷存储查询允许异步，返回 202 Accepted + 后台计算；跨 Workflow 审计需要 AUDITOR+ 权限。

## 🟡 需要进一步评审的设计点（P1）

### 设计点 1：Policy 缓存与 Kill Switch 级联

**问题描述**：
- SEC-003 的 Policy 决策缓存 5 分钟
- SEC-009 的 Kill Switch M2 可在 30 秒内触发
- **缓存中的 ALLOW 决策在 M2 启动后应如何处理？**

**当前设计**：M2 启动时无效所有受影响工具的 Policy 缓存，后续 Action 重新评估。

**需确认**：
- [ ] 是否需要立即拒绝所有进行中的该工具 Action？
- [ ] 还是仅阻止新 Action？

**建议决策**：进行中的 Action 允许完成（以防丢失中间状态），但新 Action 拒绝。

---

### 设计点 2：Worker 执行权限与 Runtime Asset 版本变化

**问题描述**：
- RT-001 说 Worker 有 `allowed_tools` 和 `toolset_version`
- SEC-004 说沙箱隔离
- **如果 Toolset 版本更新（新工具加入），Worker 能否使用？**

**当前设计**：Worker 的 `toolset_version` 在创建时冻结，不能使用新版本的工具。

**需确认**：
- [ ] 是否允许 Hot-upgrade 的工具（如 LTS 安全补丁）？
- [ ] 如何区分安全补丁与功能更新？

**建议决策**：允许安全补丁（Patch 版本号升级），拒绝功能新增（Minor/Major 升级）。

---

### 设计点 3：Task 预算与 Kill Switch 资源限制

**问题描述**：
- RT-001 定义了 Task 级别的 `budget` (tokens, cost, duration)
- SEC-004 定义了 Sandbox 级别的资源限制（CPU/内存/磁盘）
- **二者应该如何协调？**

**当前设计**：Task 预算是业务级限制，Sandbox 限制是技术级保护，二者独立。

**需确认**：
- [ ] Task 预算耗尽时应该优雅关闭还是强制杀死？
- [ ] 强制杀死时是否应该触发 Kill Switch？

**建议决策**：Task 预算耗尽 → 拒绝新 Action 但允许正在执行的 Action 完成；Sandbox OOM → 立即杀死进程。

## ✅ 已确认的对齐项

- ✅ **租户隔离**：同层多次确认，RT/SEC 都要求 organization_id 强制过滤
- ✅ **身份信息**：RT-001 的 ActorRef 与 SEC-002 的 Actor 定义一致
- ✅ **权限继承**：都明确说明权限不向下继承（Worker 不能自动获得 Workflow 权限）
- ✅ **审计日志**：RT-008 与 SEC-009/010 的审计记录格式对齐
- ✅ **凭据管理**：RT-001 的 policy_decision_id 与 SEC-005 的凭据签发关联一致
