## 2. 目标、范围与边界

### 2.1 目标

建立可维护、可审计、可验证的 AI Agent 平台威胁模型，为安全架构、后续 SEC 专项、发布门禁和轻量红队测试提供统一依据。模型应覆盖资产、信任边界、攻击者、威胁场景、风险、控制、残余风险和证据之间的关联。

### 2.2 范围

- 控制平面、执行平面、证据与治理平面，以及它们之间的边界。
- Agent 的提示与上下文、模型、记忆、工具、MCP/连接器、代码仓库、沙箱、凭据、网络、CI/CD 和第三方依赖。
- 机会主义攻击者及内部威胁；MVP 暂不以国家级攻击者为设计目标。
- 云服务、开源组件、容器镜像和 CI/CD 工具链等第三方依赖风险。
- MVP 轻量红队测试用例模板与上线门禁。

### 2.3 非目标

- 本需求不替代 SEC-002 的授权模型、SEC-003 的策略决策、SEC-004 的完整沙箱规范、SEC-005 的凭据代理设计或 SEC-010 的完整控制验证计划。
- 不承诺某项认证或合规框架已经满足；仅建立控制映射和差距跟踪。
- 不把模型拒绝能力、提示词或单一检测器作为安全边界。
- 不在本阶段设计国家级对手能力或大规模红队行动。

## 3. 问题分析

当前安全规范已经列出 A-G 威胁类别、若干控制清单和候选沙箱方案，但仍缺少统一的风险评估口径、攻击路径、数据分级规则、第三方供应链基线、控制所有者与证据、风险接受审批，以及可执行的 MVP 上线验证。若继续直接进入实现，可能发生清单完整但控制无验收、同类风险评分不一致、风险例外未授权、提示注入与网络外传链路遗漏、依赖供应链无版本溯源等问题。

这些缺口影响：用户代码和凭据的机密性、任务与代码变更的完整性、平台可用性、模型与沙箱运行成本、上线审计可证明性，以及后续 SEC 需求之间的设计一致性。

## 4. 标杆依据与公开事实/推断

研究访问日期：2026-09-23。公开产品做法仅作为设计参考，不代表其控制对本项目无条件适用，也不表示对其实现做独立验证。

### 4.1 GitHub Copilot Cloud Agent

**公开事实**：GitHub 公开描述其托管 Agent 安全思路包括最小化自主性、提高可解释性、过滤部分隐藏字符、限制网络访问、控制凭据和要求人工审查；官方风险文档说明依赖与代码安全检查及 PR 工作流中的人工控制。网络防火墙文档同时说明适用边界和绕过/例外情形。

**设计推断**：威胁模型应同时记录控制有效范围和例外边界；“已启用防火墙”不能等同于所有进程、连接器和启动阶段都受保护。

来源：

- https://github.com/github/docs/blob/main/content/copilot/concepts/agents/coding-agent/risks-and-mitigations.md

### 4.2 Microsoft AI Agent 威胁建模与 Azure SRE Agent

**公开事实**：Microsoft 指引将 Agent 风险建模视为持续工程活动，要求识别资产、端到端架构、数据流、信任边界、滥用场景、工具权限、人类审批和观测能力。Azure SRE Agent 文档描述独立沙箱、凭据与执行环境隔离、逐次工具调用作用域、出站代理和客户/区域隔离等防御层。

**设计推断**：本项目威胁模型应覆盖模型之外的编排、身份、工具、记忆、外部数据和执行链路，并将架构边界映射到控制及证据，而非只按传统应用组件列漏洞。

## 5. 威胁建模方法与资产分类

### 5.1 建模流程

1. 确认本版本架构、产品范围、数据流和运行模式。
2. 识别资产、数据分类、责任主体和信任边界。
3. 描述攻击者目标、能力、机会与前提条件。
4. 以资产为根目标分解攻击路径，标注替代路径和必须同时满足的条件。
5. 将威胁映射到机密性、完整性、可用性、身份/授权、隐私与合规影响。
6. 按统一评分规则评估固有风险，映射预防、检测、响应/恢复控制。
7. 验证控制设计和运行证据，重新评估残余风险。
8. 由指定责任人审查、批准例外并归档；在重大变更或事件后更新。

可采用 STRIDE 作为传统组件威胁的检查清单，并补充 Agent 特有滥用场景：直接/间接提示注入、工具过度授权、混淆代理、记忆投毒、工具输出污染、多 Agent 委派链、模型/索引/技能资产投毒及计划审批前副作用。框架仅辅助发现，不取代资产和攻击路径分析。

### 5.2 数据分级

| 级别 | 名称 | 定义 | 例子（待结合项目数据盘点确认） |
|---|---|---|---|
| L1 | 公开级 | 泄露无危害 | 经授权公开发布的信息 |
| L2 | 内部级 | 泄露造成一般危害 | 非公开但影响有限的内部资料 |
| L3 | 敏感级 | 泄露造成严重危害 | 私有源代码、未公开漏洞信息等 |
| L4 | 机密级 | 泄露造成特别严重危害 | 凭据、密钥、敏感个人信息等 |

定级规则：
- 混合数据集按其中最高数据级别定级。
- 聚合、摘要、嵌入、缓存、日志、备份和模型上下文的级别不得低于其来源数据的最高级别；只有经批准且可验证的去标识/降级流程才能改变级别。
- 敏感个人信息不低于 L4。
- 级别可动态上调；下调必须有数据责任人和安全团队审批、理由及证据。
- 所有检索、模型路由、日志、存储、导出和删除控制应消费同一分类结果。具体法规定义及跨境处理条件须由法务/隐私责任人确认。

### 5.3 资产与信任边界

资产至少覆盖用户身份与会话、组织/仓库授权、源代码和 Issue 内容、提示与上下文、模型和模型配置、记忆和索引、工具/MCP、工作区与沙箱、短期凭据、网络连接、事件/Trace/审计证据、Artifact/PR、构建与发布资产，以及第三方依赖和 SBOM。

信任边界至少覆盖：用户/外部 Issue 到控制平面；控制平面到模型供应商；模型输出到策略与工具执行；控制平面到沙箱；沙箱到宿主与网络；检索/仓库/工具结果到模型上下文；组织/租户之间；平台到代码托管、云服务、包注册表及 CI/CD；运行数据到日志、指标、Trace、备份和分析系统。

### 5.4 攻击者假设

MVP 聚焦机会主义攻击者，暂不将国家级攻击者作为目标画像：

- 自动化扫描工具：持续扫描暴露服务、错误配置和已知漏洞。
- 脚本小子：利用公开漏洞、弱认证和默认配置。
- 网络犯罪团伙：以勒索、数据窃取或滥用算力牟利。
- 内部威胁：拥有合法访问的人员滥用权限或误操作。

共同假设：攻击者可能控制用户提交内容、仓库文件、Issue/PR 评论、依赖包或外部服务响应；可能尝试提示注入、凭据窃取、权限滥用、网络外传、资源耗尽和供应链攻击。内部威胁覆盖恶意行为与非故意错误。模型本身、工具和第三方服务均不作为可信授权者。

## 6. 风险评估与接受

### 6.1 评分口径

对每项威胁分别给出固有风险与残余风险。影响（I）和可能性（L）分别按 1-5 级评分，风险值 R = I × L。风险等级暂定：1-4 Low、5-9 Medium、10-16 High、17-25 Critical。分值用于排序和决策支持，不能替代专业判断；若影响评分存在多个维度，采用机密性、完整性、可用性、隐私/合规和业务连续性中的最高可信影响，避免平均值掩盖严重后果。

| 分值 | 影响或可能性含义 |
|---|---|
| 1 | 极低：影响可忽略，或需要极不现实的条件 |
| 2 | 低：影响有限，攻击条件不常见 |
| 3 | 中：造成可恢复的业务/数据影响，存在现实攻击路径 |
| 4 | 高：严重数据或服务影响，攻击路径较现实 |
| 5 | 极高：重大机密、完整性、可用性或合规影响，或攻击易规模化 |

可能性评估须记录攻击者能力、可达性、利用复杂度、所需前置条件、暴露时长和已有独立控制。不得仅以“有控制”直接减分；只有控制有测试/运行证据后才用于残余风险重评。评分结果需说明依据、假设、证据来源、评审人和日期。

### 6.2 风险接受阈值与审批

- **Low**：可接受；部门负责人审批，可不追加控制，但仍记录风险、范围、责任人和复审日期。
- **Medium**：可接受的前提是安全团队与业务负责人联合审批，并形成有负责人、期限和验证条件的缓解计划。
- **High/Critical**：不可接受，必须采取控制降低风险。确实无法降低时，必须完成书面受益-风险分析，由风险管理决策层（如 CTO/CISO）与管理层双重审批后才可例外接受；Critical 还需明确停止/限制相关功能的临时措施。
- 所有残余风险接受均须书面记录并归档为审计证据，包含风险场景、固有/残余评分、业务理由、控制与缺口、影响范围、审批人、有效期、复审触发条件及到期处理。
- 任何审批不得豁免法律义务、用户承诺或强制安全门禁；适用性由法务/合规确认。

## 7. 威胁场景目录与攻击路径

下表是本项目最低威胁目录，后续专项可细化，不限制新增场景。状态表示需求建模要求，不代表实现状态。

| ID | 攻击目标/威胁场景 | 主要前提与路径 | 主要影响 | MVP重点控制/后续归属 |
|---|---|---|---|---|
| T01 | 身份伪造、会话或 Token 滥用 | 弱口令、窃取或伪造凭据 | 未授权任务/代码操作 | 身份验证、短期凭据、撤销、审计；SEC-002/005 |
| T02 | 水平/垂直越权、混淆代理 | 用户或 Agent 借更高权限工具访问资源 | 跨仓库/组织泄露或变更 | 每 Action 授权、资源范围绑定、默认拒绝；SEC-002/003 |
| T03 | 直接或间接提示注入 | Issue、代码、文档、工具结果中的恶意指令进入上下文 | 越权工具调用、数据外传、恶意代码 | 不可信来源标记、确定性策略、执行门禁；SEC-003/006 |
| T04 | 敏感数据外发 | 恶意指令或工具将代码/密钥送往外部 | L3/L4 泄露、合规事件 | 网络默认拒绝、出口白名单、模型数据策略、脱敏；SEC-004/005/008 |
| T05 | 凭据泄露 | 环境变量、文件、日志、工具输出暴露密钥 | 仓库/云服务被接管 | 无长期凭据、敏感路径与输出扫描、日志脱敏；SEC-005/008 |
| T06 | 沙箱逃逸与宿主访问 | 危险系统调用、容器配置错误或内核漏洞 | 横向移动、宿主/租户失陷 | Docker 非特权、默认 Seccomp、最小能力、资源隔离；SEC-004 |
| T07 | 危险命令/恶意代码写入 | Agent 被诱导执行破坏操作或写入漏洞 | 代码完整性、构建链或用户资产受损 | 工具策略、分支隔离、代码扫描、人工 PR 审核 |
| T08 | 第三方依赖/镜像/CI 工具链供应链攻击 | 漏洞、投毒、标签漂移、签名/哈希缺失 | 运行环境或产物被控制 | SBOM、锁版本、禁止 latest、漏洞监控、关键依赖校验 |
| T09 | MCP/工具连接器越权或被替换 | 连接器身份、Schema、权限或来源不可信 | 外部系统读写与数据外泄 | 白名单、最小权限、版本/签名治理、审计；SEC-007/HAR-005 |
| T10 | 跨租户数据混淆 | 查询、缓存、索引、日志或工作区隔离失效 | 多组织数据泄露 | 租户标识强制传播、隔离测试、缓存分区；SEC-008 |
| T11 | 资源耗尽、拒绝服务或费用滥用 | 循环调用、并发、超大输入或外部限流 | 可用性下降、成本失控 | 任务/模型/沙箱预算、速率限制、熔断与停止 |
| T12 | 事件、日志或审计证据被遗漏/篡改 | 覆盖不足、敏感信息误记、权限过宽 | 事件无法调查、合规证据不足 | 不可变事件、审计隔离、脱敏与完整性验证；RT/OBS |
| T13 | 记忆、索引或缓存投毒 | 恶意内容持久化并跨任务复用 | 持续错误决策或指令执行 | 来源、版本、权限与生命周期；MEM/CTX |
| T14 | 计划审批前产生副作用 | Agent 在计划确认前联网、执行或泄露 | 人类审批失去保护作用 | 审批前限制副作用，预先声明外部访问与动作 |
| T15 | 隐私/数据驻留/留存不当 | L3/L4 数据传输或保存超范围 | 法律、合同和信任损害 | 分类驱动路由、存储、留存和删除；SEC-008 |

攻击树应以目标为根并描述 AND/OR 条件。例如“外传私有代码”可由“获得可读代码上下文”与“建立外部传输路径”共同达成；传输路径可能是宽松网络、受控工具连接器缺陷或受污染的依赖/启动流程等替代路径。每条路径都要标出先决条件、受影响资产、可检测信号和对应控制，不能只提供没有边界/来源的图形。

## 8. 控制基线与 MVP 范围

### 8.1 MVP 必须具备

1. **身份与授权**：强认证传输、任务和仓库范围授权、默认拒绝、每个敏感 Action 重新检查授权；认证/拒绝事件可审计。
2. **数据分级**：L1-L4 分类贯穿上下文、模型路由、存储、日志、备份、导出与删除；敏感个人信息不低于 L4。
3. **Agent 防护**：所有仓库、Issue、网页、工具和模型返回均按不可信数据处理；模型输出不能直接授权；高风险操作需要策略校验和人工确认。
4. **执行隔离**：MVP 使用 Docker + Seccomp 默认策略；不使用特权容器，禁用 `CAP_SYS_ADMIN` 等非必要能力；资源受限；网络默认拒绝并按审批白名单开放。
5. **凭据**：Agent/Worker 不持有长期凭据；短期、任务/资源作用域凭据由受控服务提供并可撤销；禁止通过未筛选环境变量继承凭据。
6. **第三方依赖**：建立可追溯 SBOM；锁定依赖版本；禁止容器镜像 `latest` 标签；持续监控开源组件漏洞；关键依赖执行哈希校验与签名验证，校验失败阻断构建/运行。
7. **代码交付**：变更经过测试和安全扫描，PR 必须人工审查；Agent 不自动合并。
8. **审计与响应**：关键身份、策略决策、工具/网络调用、凭据使用、沙箱生命周期及发布操作有可关联审计证据；提供任务/工具级暂停与凭据撤销路径。
9. **红队上线门禁**：至少执行第 10 节测试用例；高风险失败阻塞上线，中风险须有已批准修复计划、责任人和期限。

### 8.2 Seccomp 指南与容器基线清单

- 使用 Docker 当前受支持版本的默认 Seccomp profile 作为起点，确认运行时未通过配置禁用；不为方便任意放宽系统调用。
- 对 `ptrace`、`mount`、`keyctl` 等高风险系统调用维持默认拒绝/限制；如确需例外，记录业务理由、镜像和工作负载范围、风险评估、批准人及回归测试，并采用最窄例外。
- 以非 root 用户运行；禁止 `--privileged`；删除所有非必需 Linux capabilities，尤其不得授予 `CAP_SYS_ADMIN`。
- 根文件系统只读；仅为任务工作区挂载最小目录；不得挂载 Docker socket、宿主敏感路径或不必要设备。
- 启用资源限制（CPU、内存、进程数、磁盘、运行时长）；设置健康检查和超限终止行为。
- 网络默认关闭；确需依赖下载时使用受控代理和精确目的地允许列表，阻断云元数据地址、回环/私网绕行及 DNS 隧道风险。
- 镜像固定不可变 digest 或受控版本，来源可信并验证签名/摘要；定期重建修补基础镜像。
- 容器配置检查需记录镜像身份、运行用户、Seccomp 状态、capabilities、特权标志、挂载、网络策略、资源限制、密钥暴露面和清理结果。
- 上述清单是基线要求，不是 Docker 容器可抵御所有宿主内核/运行时漏洞的保证；隔离充分性须通过测试与威胁评审确认。

## 9. 第三方依赖治理

纳入范围的依赖类型包括 npm/PyPI/Maven 等开源包、容器镜像、数据库/消息队列/CDN 等云服务，以及 GitHub Actions、Jenkins 插件等 CI/CD 工具链。模型供应商、MCP 服务、解析器、索引和扫描服务亦需纳入适用的第三方清单。

最低治理要求：
- 为发布构建生成并归档 SBOM，关联应用/镜像版本、构建来源和时间。
- 依赖版本锁定并可复现；容器镜像禁止使用可漂移的 `latest` 标签。
- 持续监控已知漏洞、安全公告和依赖终止支持状态；严重漏洞要有影响分析、缓解/升级责任人与时限。
- 对关键依赖验证哈希和签名；验证失败时阻止发布或运行，不允许静默回退到未验证来源。
- CI/CD 插件和工作流按最小权限运行，限制可写 Token，变更需审查；第三方云服务评估数据分类、区域、留存、可用性和供应商责任边界。
- 引入/升级关键依赖前评估来源、维护状态、权限、漏洞历史和替代方案；例外进入风险接受流程。

关键依赖定义、漏洞严重等级与修复时限应在供应链专项或发布策略中冻结，本需求不凭空设定具体 SLA。

## 10. MVP 轻量红队测试

### 10.1 测试定位与模板字段

MVP 发布前进行一次范围受控的上线门禁验证，不作为大规模对抗演练。每个测试用例至少记录：用例编号、目标资产/边界、风险等级、OWASP Top 10 或项目威胁映射、前置条件、测试输入/步骤描述、预期安全行为、观察证据、严重性、实际结果、缺陷链接、修复责任人和复测结论。不得在共享/生产环境执行破坏性测试。

### 10.2 最低场景集

| 场景 | 风险 | 期望行为 | 失败严重性/门禁 |
|---|---|---|---|
| 弱密码或认证策略绕过 | 高 | 拒绝弱认证或触发既定保护；认证事件留痕 | 可绕过为高风险，阻塞上线 |
| Token 伪造、篡改、过期或撤销后重放 | 高 | 签名/受众/有效期/作用域校验失败；不得执行 Action | 成功冒用为高风险，阻塞上线 |
| SQL 注入、XSS、命令注入 | 高 | 输入按上下文安全处理；不得获得任意查询、脚本执行或宿主能力 | 可利用为高风险，阻塞上线 |
| 水平/垂直越权及跨仓库访问 | 高 | 访问在上下文加载和 Action 执行前拒绝，留下审计 | 任意越权为高风险，阻塞上线 |
| 日志密钥、未脱敏响应或 L3/L4 外泄 | 高 | 秘密不出现在日志/响应；外传渠道受策略阻断 | 可泄露为高风险，阻塞上线 |
| 第三方依赖已知漏洞利用/被替换 | 高 | SBOM 可追溯；策略识别漏洞或签名/摘要不符并阻断 | 关键依赖可利用且无缓解为高风险，阻塞上线 |
| 间接提示注入诱导调用工具或网络外传 | 高 | 不可信内容不能改变权限；未授权 Action/网络访问被拒绝 | 越权副作用为高风险，阻塞上线 |
| Docker 特权、能力、挂载或 Seccomp 回归 | 高 | 基线检查发现特权/危险能力/违规挂载或策略关闭 | 安全基线缺失为高风险，阻塞上线 |
| 超大输入、循环工具调用或资源耗尽 | 中至高 | 达到预算/速率/资源限制后停止并记录 | 中风险有修复计划；可跨任务/租户影响升级高风险 |

测试用例应覆盖 OWASP Top 10 的适用风险和项目特定场景。框架版本、测试范围与覆盖映射须在执行时注明，不能把“有测试用例”误报为“完整覆盖全部 OWASP 风险”。

### 10.3 上线门禁

- 任一高风险测试失败、核心控制无证据或风险评分未完成：阻塞上线。
- 中风险失败：只有经安全团队与业务负责人批准，且有责任人、修复期限、缓解措施和复测安排，才可继续评估发布。
- 低风险失败：记录并按风险接受流程处理。
- 门禁结论、执行版本、环境、测试证据、例外审批和复测结果归档。

## 11. 人类在环、运营与可观测性

安全负责人维护威胁模型与风险登记；资产/业务负责人确认数据分类、业务影响和风险接受；工程负责人提供控制实现与运行证据；安全团队复核高风险评分和测试；法务/隐私负责人确认法规、合同和跨境适用性；发布责任人执行门禁。具体组织名称可由项目治理确定，但职责不能空缺。

每项威胁至少能追溯到资产、数据级别、控制、责任人、风险接受记录（如有）、测试证据和版本。监控重点包括授权拒绝、异常凭据使用、出站阻断、敏感数据检测、沙箱策略偏离、依赖漏洞、异常资源消耗、审计完整性和 Kill Switch 操作。观测数据自身按来源数据最高级别保护并执行脱敏/访问控制。

## 12. 性能、成本与延迟

用户提供的预算是安全投入规划假设，不是已测量的项目事实：基础型 MVP（非敏感数据、无支付）安全预算约 8%–10%；中等复杂度 MVP（含用户数据、后端集成）约 12%–15%。立项时应明确预算分母（总开发投入、工程人力或总项目成本）和纳入项，防止不同团队采用不同口径。

安全控制带来的性能损耗目标控制在 5%–10% 以内；超过 10% 应开展替代方案和风险评估，不得以性能为由静默关闭强制控制。基准测试需对比启用/关闭可安全隔离的控制时的端到端任务延迟、沙箱启动、依赖扫描与构建耗时、吞吐和成本；TLS、加解密等具体影响按真实环境测量。高风险校验与授权不得因性能退化被跳过。

## 13. 验收标准

| 编号 | 验收标准 | 验证证据 |
|---|---|---|
| AC-01 | 威胁模型明确架构范围、资产、数据流和信任边界，并经安全与架构责任人评审 | 签署评审记录、版本化架构/边界清单 |
| AC-02 | 覆盖本文件最低威胁目录，包含 Agent 特有威胁、第三方依赖和内部威胁；新增/不适用项有理由 | 威胁登记表及映射审查 |
| AC-03 | 每项 High/Critical 威胁有攻击路径、前提、控制、责任人和可验证测试/证据要求 | 完整性审查、控制追踪矩阵 |
| AC-04 | 风险评分遵循 1-5 影响/可能性及风险等级口径，评分依据可复核，固有与残余风险分开 | 抽样重评一致性审查 |
| AC-05 | 风险接受遵循 Low/Medium/High/Critical 审批规则，所有残余接受有书面归档字段 | 风险接受记录审查 |
| AC-06 | L1-L4、聚合取最高级、动态上调及敏感个人信息不低于 L4 已纳入数据流控制要求 | 数据分类与数据流评审 |
| AC-07 | MVP Docker/Seccomp 容器基线及检查清单明确包含非特权、能力最小化、禁止 privileged、网络与资源限制 | 配置基线审查及运行检查证据 |
| AC-08 | 第三方依赖范围含开源包、镜像、云服务、CI/CD；规定 SBOM、锁版本、禁用 latest、漏洞监控及关键依赖哈希/签名验证 | 构建与供应链流程审查 |
| AC-09 | 红队模板覆盖身份、注入、越权、敏感数据、依赖漏洞及项目特定 Agent 威胁；高风险失败阻塞上线，中风险有审批缓解计划 | 门禁记录、测试用例与复测证据 |
| AC-10 | 合规优先级记录为 ISO 27001 → SOC 2 → GDPR（按需），适用性及认证状态不被误述为已满足 | 合规映射和法务/合规确认记录 |
| AC-11 | 性能损耗目标、预算假设及测量口径被记录；超过 10% 的替代方案评估有审批证据 | 性能基准与预算决策记录 |
| AC-12 | 需求与 SEC-002 至 SEC-010、HAR-001/004、OBS-007 等边界和依赖完成一致性检查 | 跨模块评审记录 |

“威胁覆盖率 95%”等比例不作为本需求的独立通过指标，因为在无完备威胁全集时分母不可客观确定。应以最低威胁目录、架构边界审查、差异登记和责任人签署作为可审计验收依据。

## 14. 依赖与跨模块接口

- **REQ-RT-001**：复用 Task、Workflow、Worker、Action、Artifact、Evidence、Trace 等共享身份与版本坐标；不另造运行时实体体系。
- **REQ-SEC-002/003**：消费威胁场景、资源边界、风险等级与高风险审批要求。
- **REQ-SEC-004/005**：消费沙箱逃逸、网络外传、凭据滥用威胁；`REQ-SEC-004 v0.2-designed` 定义多后端隔离路由、连接器审批出口和不可降级的隔离要求，`REQ-SEC-005` 定义凭据代理。
- **REQ-SEC-006/007**：消费提示注入、恶意仓库、MCP/工具供应链威胁。
- **REQ-SEC-008/009/010**：消费数据分级、残余风险、响应优先级和红队场景。
- **REQ-HAR-001/004/005**：消费 Worker/Hook/连接器的风险分级、最小权限和审计要求。
- **REQ-OBS-004/007**：消费日志数据分级、脱敏和审计证据完整性要求。
- **REQ-EVA-006**：消费高风险阻断、中风险例外审批和安全结果不可被效率指标抵消的门禁原则。

## 15. 版本与演进

本文件 `v0.1-designed` 表示详细设计草案完成，待跨模块评审；不表示代码实现、渗透验证、认证通过或冻结。设计冻结前需完成安全、架构、业务、隐私/合规评审，并把组织职责、数据盘点、评分边界及外部法规适用性作为确认项。

发生以下情形时触发复评：架构/信任边界/模型或工具重大变更；新增数据类别、租户或外部连接器；高危漏洞或安全事件；控制测试失败；法规、合同或供应商条件变更；至少按季度复核一次。每次变更保留版本、理由、风险差异、批准记录和受影响的下游专项。

## 16. 待确认问题

以下问题不阻止当前形成设计基线，但须在评审/实施前确认：

1. 8%–10%/12%–15%安全预算的统计分母与预算负责人。
2. L1-L4 的具体数据目录、数据责任人，以及脱敏/去标识后降级的批准规则。
3. 具体 ISO 27001 版本/范围、SOC 2 类型与时间窗口；GDPR 是否适用及适用实体/地区。
4. High/Critical 风险管理决策层和管理层的正式岗位、审批授权与例外有效期上限。
5. Docker Engine/平台版本、Seccomp 默认策略更新流程、允许的网络目的地与依赖代理方案。
6. SBOM 格式、漏洞严重等级来源、修复 SLA、关键依赖定义及哈希/签名验证机制的归属专项。
7. 红队测试环境、测试责任人、OWASP Top 10 版本、复测时限及中风险修复计划最长周期。
8. 5%–10%性能损耗的基线、测量窗口、置信要求及可归因控制范围。
