## 一、设计目标

建立统一的事件查询、留存、脱敏和权限边界体系，确保：

1. **可查询性**：提供结构化事件查询接口，支持多维过滤、分页、时间范围
2. **分层留存**：平衡合规要求、存储成本和查询性能
3. **敏感保护**：内置敏感字段脱敏机制，支持可扩展的脱敏规则
4. **权限隔离**：强制租户隔离和最小权限查询控制
5. **合规可审计**：满足监管要求的事件留存和防篡改

## 五、查询 API 设计

### 5.1 查询接口定义

**端点**: `GET /api/v1/events`

**请求参数**:

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `organization_id` | UUID | 是 | 强制租户过滤（自动注入） |
| `task_id` | UUID | 否 | 按任务 ID 过滤 |
| `workflow_id` | UUID | 否 | 按工作流 ID 过滤 |
| `actor_id` | UUID | 否 | 按执行者 ID 过滤 |
| `actor_type` | enum | 否 | user / worker / system |
| `event_type` | string[] | 否 | 按事件类型过滤 |
| `risk_level` | enum[] | 否 | LOW / MEDIUM / HIGH / CRITICAL |
| `status` | enum[] | 否 | 按状态过滤 |
| `trace_id` | UUID | 否 | 按 Trace ID 过滤（轻量关联） |
| `start_time` | ISO8601 | 否 | 开始时间（默认 30 天前） |
| `end_time` | ISO8601 | 否 | 结束时间（默认当前） |
| `page` | int | 否 | 页码（默认 1） |
| `page_size` | int | 否 | 每页条数（默认 50，最大 500） |
| `sort_by` | enum | 否 | created_at / event_type（默认 created_at） |
| `sort_order` | enum | 否 | asc / desc（默认 desc） |

**响应结构**:

```json

      "event_id": "uuid",

      "actor": {
        "type": "worker",
        "id": "planner-001"
      },
      "timestamp": "2026-09-23T10:30:00Z",
      "payload": {
        // 脱敏后的 Payload
      },
      "redacted_fields": ["payload.file_content"],
      "metadata": {
        "idempotency_key": "...",
        "causation_id": "...",
        "correlation_id": "..."
      }
    }
  ],
  "pagination": {
    "page": 1,
    "page_size": 50,
```

### 5.2 流式传输接口

**端点**: `GET /api/v1/events/stream`

**协议支持**:

## 六、留存策略设计

### 6.1 分层存储架构

```
┌─────────────────────────────────────────────────────────────┐
│                    事件生产者                                │
│  Worker / Policy Gateway / Tool Executor                    │
└──────────────────────┬────────────────────────────────────┘
                       │ 写入事件
                       ▼
┌─────────────────────────────────────────────────────────────┐
│              PostgreSQL（热存储）                            │
│  保留期: 30 天                                               │
│  用途: 高效查询、最近事件                                    │
└──────────────────────┬────────────────────────────────────┘
                       │ 自动归档（每日）
                       ▼
┌─────────────────────────────────────────────────────────────┐
│              S3/Blob Storage（冷存储）                        │
│  保留期: 180 天                                              │
│  用途: 合规留存、成本优化                                    │
└─────────────────────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────────────┐
│              归档存储（按组织配置）                           │
│  保留期: 组织可覆盖（最长 2 年）                             │
│  用途: 特殊合规要求                                         │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 留存配置

| 配置项 | 平台默认值 | 组织可覆盖 | 说明 |
|--------|-----------|-----------|------|
| 热存储天数 | 30 天 | 是（15-90 天） | 超过后自动归档 |
| 冷存储天数 | 180 天 | 是（30-730 天） | 超过后评估删除 |
| 合规保留 | 无 | 是 | 法律/监管要求的强制保留 |
| 归档格式 | Parquet | 否 | 高效压缩和查询 |

### 6.3 归档规则

**高风险事件（CRITICAL / HIGH）**：
- 完整 Payload 归档
- 保留 2 年
- 不自动删除，需人工审批

**中风险事件（MEDIUM）**：
- 完整 Payload 归档
- 保留 180 天
- 可自动删除（无合规保留）

**低风险事件（LOW）**：
- 仅元数据归档（不含大字段）
- 保留 90 天
- 可自动删除

## 七、脱敏设计

### 7.1 脱敏规则类型

| 类型 | 说明 | 示例 |
|------|------|------|
| `full_redact` | 完全脱敏 | `"secret_key" → "[REDACTED]"` |
| `partial_redact` | 部分脱敏 | `"sk-abc123***" → "sk-***"` |
| `hash_redact` | 哈希脱敏 | `"user@example.com" → "sha256:..."` |
| `preserve` | 保留原文 | 不处理（默认） |

### 7.2 平台级默认脱敏规则

| 字段模式 | 风险级别 | 脱敏类型 | 说明 |
|----------|----------|----------|------|
| `payload.file_content` | MEDIUM+ | partial_redact | 保留前 100 字符 |
| `payload.command_output` | MEDIUM+ | partial_redact | 保留前 200 字符 |
| `payload.*token*` | CRITICAL | full_redact | 完全隐藏 |
| `payload.*secret*` | CRITICAL | full_redact | 完全隐藏 |
| `payload.*password*` | CRITICAL | full_redact | 完全隐藏 |
| `payload.*key*` | HIGH+ | full_redact | 完全隐藏 |
| `payload.env.*` | HIGH+ | full_redact | 环境变量完全隐藏 |
| `payload.api_key` | CRITICAL | full_redact | API 密钥完全隐藏 |
| `actor.email` | HIGH | hash_redact | 保留可关联性 |
| `actor.ip_address` | MEDIUM | partial_redact | 仅保留国家代码 |

### 7.3 脱敏执行时机

- **读取时脱敏**：不修改原始存储
- **降级策略**：脱敏失败时完全脱敏，记录错误日志
- **管理员视图**：`include_redacted=true` 仅平台管理员可用（V1 扩展）

## 八、权限模型设计

### 8.1 角色与权限

| 角色 | 查询范围 | 脱敏查看 | 导出 | 删除 | HITL 审批 |
|------|---------|---------|------|------|----------|
| 普通用户 | 仅自己创建的 Task | 否 | 否 | 否 | 否 |
| 组织管理员 | 组织内所有 Task | 否 | 是 | 否 | 部分 |
| 安全工程师 | 组织内所有 Task | 是 | 是 | 否 | 部分 |
| 平台管理员 | 所有组织 | 是 | 是 | 合规场景 | 是 |
| 合规团队 | 所有组织 | 是 | 是 | 是（需审批） | 是 |

### 8.2 查询权限校验

```
1. 验证认证令牌（Bearer Token / API Key）
2. 提取 organization_id、user_id、roles
3. 强制注入 organization_id 过滤（防止跨租户查询）
4. 根据角色判断查询范围
5. 校验特殊权限（如 include_redacted）
6. 记录查询审计日志
```

### 8.3 跨租户防护

- 所有查询强制 `organization_id` 过滤
- 禁止跨组织 JOIN 查询
- 跨租户查询尝试触发安全告警

## 九、合规删除设计

### 9.1 分级审批流程

```
┌─────────────────────────────────────────────────────────────┐
│                    删除请求提交                              │
│  用户提交数据删除请求（GDPR 右被遗忘权）                      │
└──────────────────────┬────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                    数据敏感度评估                            │
│  自动分析待删除数据的敏感级别                                 │
│  - HIGH/CRITICAL: 强制人工审批                              │
│  - MEDIUM: 自动 + 审计记录                                 │
│  - LOW: 自动处理                                           │
└──────────────────────┬────────────────────────────────────┘
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
    ┌──────────┐              ┌──────────┐
    │ 自动处理 │              │ 人工审批  │
    │ (LOW)    │              │ (HIGH+)  │
    └────┬─────┘              └────┬─────┘
         │                         │
         │ 审计记录                │ HITL 介入
         ▼                         ▼
┌─────────────────────────────────────────────────────────────┐
│                    执行脱敏/删除                             │
│  - PII 脱敏: 替换为哈希值                                  │
│  - 完全删除: 保留元数据索引，删除 Payload                    │
│  - 归档删除: 从冷存储移除                                    │
└──────────────────────┬────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                    删除审计记录                              │
│  记录删除操作的操作人、时间、范围、审批链                     │
└─────────────────────────────────────────────────────────────┘
```

### 9.2 删除类型

| 类型 | 说明 | 适用场景 |
|------|------|----------|
| `pii_redact` | PII 字段脱敏 | 保留可关联性 |
| `full_delete` | 完全删除 Payload | 右被遗忘权 |
| `archive_delete` | 冷存储删除 | 合规过期 |

## 十四、与 RT-006 的边界

RT-008 坚持**事件层定位**：

- 通过事件模型中的 `trace_id` 字段关联 Trace
- 仅提供基于 `trace_id` 的事件过滤与轻量摘要查询
- **全链路聚合**仍由 RT-006 负责
- 实现**职责分离**与**查询性能的最优平衡**
