## 1. 需求定义

### 1.1 目标

建立面向 AI Agent 持久执行的恢复决策与失败处理协议，使系统能够在 Worker 崩溃、节点故障、暂停、审批等待、检查点损坏、凭据失效和外部副作用不确定等场景下，选择可证明安全的恢复路径。

本需求解决四个问题：

1. 恢复点应由外部世界的污染范围决定，而不是简单按检查点层数回退。
2. 失败回退必须知道哪些副作用已经发生、哪些动作可补偿，以及补偿的边界。
3. 恢复过程本身可能形成流量峰值，必须受到更严格的保护。
4. 自动恢复无法安全推进时，必须进入可审计、可接管、不可静默丢弃的人工处理路径。

### 1.2 非目标

本需求不重新定义：

- Checkpoint 的基础 Schema、保存协议和事件事实源，归属 `REQ-RT-005`；
- Failure Taxonomy 和初始失败枚举，归属 `REQ-REL-001`；
- 通用重试退避、基础重试预算和基础熔断器，归属 `REQ-REL-002`；
- 幂等键生成和幂等账本，归属 `REQ-RT-007`、`REQ-REL-006`；
- 补偿动作目录的完整实现，归属 `REQ-REL-007`；
- 具体数据库、消息队列、API 和 UI 实现。

## 2. 行业标杆研究与设计判断

### 2.1 可确认的公开事实

- Temporal 的 Saga 资料要求补偿动作具备幂等性，并建议在正向动作前注册补偿，以覆盖“动作已产生外部影响但响应丢失”的情况。来源：[Temporal Saga Pattern](https://docs.temporal.io/design-patterns/saga-pattern)，访问日期：2026-09-24。
- LangGraph 官方资料说明检查点可支持故障恢复，但节点重新执行可能重复外部副作用，因此应用必须自行提供幂等键、条件写入或读前检查。来源：[LangGraph Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)、[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)，访问日期：2026-09-24。
- Devin 官方资料公开了运行记录、结果重放和失败节点的 retry、skip、substitute、fatal 分流；恢复依赖稳定的 Run ID 和可重放的调用记录。来源：[Devin Dynamic Workflows](https://docs.devin.ai/work-with-devin/dynamic-workflows)，访问日期：2026-09-24。
- DeepSeek Harness 公开了在失败步骤关闭后由错误处理监听器决定 retry 或保留原错误的事件驱动模式，并在等待前记录重试事件。来源：[DeepSeek Harness Agent Lifecycle](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/agent-lifecycle.md)，访问日期：2026-09-24。
- OpenAI Codex 公开了持久 Thread、resume、fork、archive 和服务端事件历史，说明客户端断开不应成为长任务事实源。来源：[Unlocking the Codex Harness](https://openai.com/index/unlocking-the-codex-harness/)，访问日期：2026-09-24。
- Qoder 官方 SDK 资料区分 Agent Result 与 SDK 异常，要求只对已知瞬态错误进行有限重试；文件回滚不等于外部副作用回滚。来源：[Qoder Errors](https://docs.qoder.com/cli/sdk/errors)，访问日期：2026-09-24。

### 2.2 对本项目的设计判断

你的五项修正符合行业持久执行系统的共同工程原则，而且比单纯“最近检查点加固定回退层数”更适合 Agent 场景。尤其是外部世界污染、不可补偿动作、结果未知和补偿失败，不能由普通对话状态或模型判断替代。

需要补充的边界是：

- `contamination_radius` 不是模型自由生成的风险描述，而是由 Effect Log、Action 状态、外部确认和执行器证据共同计算的保守上界。
- Pivot 不意味着系统立即失败；Pivot 后禁止假装回滚，允许进入“前向收敛”或人工接管。
- “根因去重”必须以稳定根因指纹为依据，不能以重复出现次数代替根因分析。
- 恢复态保护不是另一个独立重试器，而是对现有 `REQ-REL-003` 计数器、预算和熔断器施加更严格的恢复期策略。

## 3. 核心设计决策

### 3.1 污染半径优先

每个 Workflow Checkpoint 必须具有恢复决策使用的 `contamination_radius` 属性。该属性描述从该检查点之后，外部世界可能已经被本任务影响的最大范围，而不是描述模型上下文长度或事件数量。

污染半径由以下信息计算：

- 检查点之后已提交或可能已提交的 Effect Log；
- Action 的 `side_effect_state` 和结果未知状态；
- 外部系统确认、查询和审计证据；
- 动作的可补偿性、影响范围和不可逆性；
- 是否已经跨过 Pivot；
- 是否存在凭据签发、通知发送、分支推送、PR 创建等外部事实。

恢复点定义为：

> 在版本、合规和状态一致性均通过的前提下，选择污染半径未越过当前恢复安全边界的最后一个检查点。

回退深度只作为检索和运维上限，不作为安全判定标准。即使候选检查点相隔八层，只读且无外部影响，也可能比相隔三层但已经写入外部系统的检查点更安全。

### 3.2 三个恢复点闸门

恢复点必须依次通过：

1. **版本兼容性闸门**：检查 Runtime Contract、Workflow、Agent Profile、Toolset、Policy、Sandbox、Context 和 Checkpoint Schema 版本；不兼容时只能迁移到明确兼容版本或人工处理。
2. **根因去重跳层闸门**：识别检查点之后重复出现且根因指纹相同的失败段，跳过已证明无效的恢复候选，不把同一缺陷当成多个独立故障消耗恢复预算。
3. **检查点合规属性闸门**：确认检查点的租户、数据分类、保留期限、法律留存、删除状态、访问授权、审计引用和污染证据均有效。合规属性不完整时不能使用该检查点恢复。

### 3.3 Effect Log 与三段式契约

Effect Log 是外部副作用的专用事实账本，与事件流和 Checkpoint 分工如下：

- 事件流记录运行时事实和状态变化；
- Checkpoint 记录恢复优化快照；
- Effect Log 记录外部世界副作用的意图、执行阶段、确认状态和补偿关联。

每个可能产生外部影响的 Action 必须采用三段式契约：

1. **准备段**：登记正向动作、规范化请求摘要、幂等键、资源范围、风险等级、可补偿性、候选补偿和是否为 Pivot。
2. **执行确认段**：记录发送、接受、结果未知、外部确认或明确未执行；未确认不得被推断为未发生。
3. **收敛段**：记录最终确认、补偿完成、补偿失败、前向收敛或人工接管结果。

Effect Log 必须先于不可撤回的外部通知落账。涉及 Pivot 的动作，必须先完成 Effect Log 和结果确认，再发送对外通知、交付声明或完成承诺。外部世界不可回滚，因此系统不得在事实确认之前对外承诺已完成或已撤销。

### 3.4 Pivot Transaction

Pivot 是进入不可回退或只能通过业务补偿收敛的边界。Pivot 必须在计划和 Effect Log 中显式标记，并至少包含：影响范围、不可逆原因、确认条件、允许的后续动作、人工责任方和升级 SLA。

Pivot 前：

- 可以回到未污染检查点；
- 可以执行已登记且幂等的补偿；
- 不得发送依赖最终成功的外部通知。

Pivot 后：

- 不得宣称技术回滚已经恢复原状；
- 不得删除或覆盖已发生的 Effect Log；
- 默认采用前向收敛、业务补偿或人工接管；
- 任何对外完成、撤销或失败声明必须引用确认后的 Effect Log 和 Evidence。

不可补偿动作不能自动跨过 Pivot，除非策略明确将其定义为人工审批的 Pivot 操作。

### 3.5 补偿独立安全域

补偿不是清理脚本，也不是正向动作的隐式反向调用。每个补偿必须：

- 通过与正向动作相同的 Policy Gateway；
- 通过独立的幂等闸门和独立补偿幂等键；
- 拥有独立重试预算、独立熔断器和独立 Trace；
- 记录补偿前置条件、目标资源、授权范围和结果；
- 支持正向动作从未发生时的幂等空操作；
- 失败后继续评估其它可独立补偿项，但补偿任务整体必须进入人工升级路径。

补偿失败不得静默丢弃，不得被普通恢复重试吞掉，也不得因为任务终止而停止审计和告警。补偿失败属于最高级可靠性事故之一，必须保全 Effect Log、现场快照、凭据撤销状态和责任人信息。

### 3.6 根因去重升级

升级判定不使用“连续三次失败”作为充分条件。系统为失败证据生成稳定根因指纹，至少结合失败类别、阶段、受影响资源、版本、依赖、策略和关键错误证据进行规范化。

以下任一条件满足时升级：

- 同一根因指纹跨越恢复候选仍未改变；
- 失败类别为不可补救、权限拒绝、状态损坏、合规冲突或未知副作用；
- 没有可查询的权威真相源；
- 已跨越 Pivot 且没有安全的前向收敛路径；
- 补偿动作失败；
- 恢复期保护已触发；
- 版本、合规或权限闸门不通过。

不同根因可以分别拥有有限自动恢复预算；同一根因不得通过换 Worker、换检查点或重复重试伪装成新的恢复机会。

### 3.7 恢复期保护

恢复态下，系统默认处于比正常运行更严格的保护等级。恢复控制器必须：

- 限制同一任务、Workflow、Action 和 Effect Log 的并发恢复者为一个；
- 降低自动恢复并发和恢复期重试预算；
- 对写操作、通知、凭据签发和跨系统调用采用更高风险门槛；
- 先运行只读核查，再允许最小范围写操作；
- 恢复期失败计数独立标记，并同时更新现有连续失败和窗口失败率计数器；
- 恢复期进入黄色区间时提前排队，进入红色区间时只允许核查和人工操作；
- 禁止通过恢复动作绕过正常熔断器、Policy Gateway、Kill Switch 或审批。

恢复期保护与 `REQ-REL-003` 的双计数器和三值对账联动，但不创建第三套替代计数器。

## 4. 九态恢复状态机

恢复状态机在 Workflow/Task 层表达恢复控制语义，不替代 `REQ-RT-002` 的 Task、Workflow、Worker、Action 状态机。

九个状态为：

1. **RECOVERY_REQUESTED**：已收到崩溃、暂停、恢复请求或失败事件，尚未读取候选检查点。
2. **ASSESSING**：正在验证事实序列、状态投影、Checkpoint、版本、合规属性、污染半径和根因指纹。
3. **RECONCILING**：正在对未完成 Action 和 Effect Log 做只读核查，使用 `REQ-REL-003` 的三值对账语义。
4. **COMPENSATING**：已确定存在可补偿影响，按安全顺序执行补偿；每个补偿均需独立授权和幂等保护。
5. **RESUMING**：恢复点和副作用边界已确认，正在重新授权、刷新凭据、分配预算并启动新 Worker attempt。
6. **CONVERGING**：已跨越 Pivot 或无法完全回退，系统执行前向收敛、剩余交付或业务补偿，不再假装回滚。
7. **ESCALATED**：自动路径无法安全推进，已创建人工处理责任和升级 SLA，自动业务动作冻结。
8. **RECOVERY_PAUSED**：因人工等待、审批、Kill Switch、资源不可用或保护策略暂停；只允许定义的控制和审计动作。
9. **RECOVERY_TERMINATED**：恢复流程终止，原因、Effect Log、证据、补偿结果和后续责任均已固化。

### 4.1 合法主路径

- `RECOVERY_REQUESTED` → `ASSESSING`
- `ASSESSING` → `RECONCILING`、`RESUMING`、`ESCALATED`、`RECOVERY_PAUSED`、`RECOVERY_TERMINATED`
- `RECONCILING` → `COMPENSATING`、`RESUMING`、`CONVERGING`、`ESCALATED`、`RECOVERY_PAUSED`
- `COMPENSATING` → `RESUMING`、`CONVERGING`、`ESCALATED`、`RECOVERY_PAUSED`
- `RESUMING` → `ASSESSING`、`CONVERGING`、`ESCALATED`、`RECOVERY_PAUSED`、`RECOVERY_TERMINATED`
- `CONVERGING` → `RESUMING`、`ESCALATED`、`RECOVERY_PAUSED`、`RECOVERY_TERMINATED`
- `ESCALATED` → `RECOVERY_PAUSED`、`RESUMING`、`CONVERGING`、`RECOVERY_TERMINATED`
- `RECOVERY_PAUSED` → `ASSESSING`、`RECONCILING`、`RESUMING`、`ESCALATED`、`RECOVERY_TERMINATED`
- `RECOVERY_TERMINATED` 为不可逆终态。

禁止从 `RECOVERY_TERMINATED` 回到任何活动状态；禁止从 `ESCALATED` 直接跳过人工决策进入外部写操作；禁止从 `ASSESSING` 直接宣称恢复成功。

### 4.2 终态不变量

进入 `RECOVERY_TERMINATED` 前必须满足：

- 恢复决策已持久化并关联原始 Task、Workflow、Trace 和失败根因；
- Effect Log 中所有已知或未知副作用都有最终确认、人工责任或明确的未决状态；
- 补偿成功、补偿失败或不适用的原因均已记录；
- 所有短期凭据已撤销、过期或有明确的未撤销风险；
- 不存在仍可运行的恢复 Worker 或未受控的恢复 Action；
- 对外通知只引用已确认事实，不把推断写成完成或回滚；
- 审计、合规留存和告警记录已经提交；
- 终态不可通过普通重试或状态覆盖重新激活。

## 5. 恢复决策流程

1. 接收恢复触发事件，并创建唯一 Recovery Attempt。
2. 读取事件事实、投影进度和候选 Checkpoint，禁止只依赖过期投影。
3. 通过版本兼容性闸门和检查点合规属性闸门。
4. 根据 Effect Log、Action 状态、外部确认和 Pivot 标记计算污染半径。
5. 使用根因指纹进行去重，跳过已证明无效的重复恢复路径。
6. 从最新候选开始选择最后一个未越界且可验证的检查点；回退层数仅用于保护查询范围和运营成本。
7. 对未完成 Action 执行只读副作用核查；没有权威真相源时进入升级，不作“未执行”假设。
8. 判断是否需要补偿、是否已经跨过 Pivot，以及是否存在安全的前向收敛路径。
9. 检查恢复期保护、任务预算、全局预算、熔断器、Kill Switch、Policy Gateway 和权限状态。
10. 可安全恢复时重新验证权限、Policy、Workspace、Toolset 和短期凭据，创建新的 Worker attempt。
11. 需要补偿时，先落补偿意图，再逐项执行；补偿失败立即升级，同时继续处理其它独立补偿项。
12. 恢复或收敛后的首个安全边界必须形成新的 Recovery Checkpoint，并将结果写入 Effect Log、事件事实和审计链。
13. 只有满足 `REQ-RT-002` 的父子状态和交付证据要求，才能推进原业务 Workflow；恢复成功不等于任务完成。

## 6. 人工在环与失败处理

### 6.1 自动升级条件

自动升级由以下维度共同决定：

- 根因是否重复且未改变；
- 失败类别是否可补救；
- 污染半径是否越界；
- 是否存在 Pivot 或不可补偿动作；
- 是否存在权威真相源；
- 补偿是否失败；
- 恢复期保护是否触发；
- 版本、权限和合规闸门是否通过。

次数只能作为预算耗尽的辅助信号，不能作为升级的唯一判据。

### 6.2 人工责任

升级事件必须指定责任主体、响应期限和可执行操作。交互选项只是人工决策载体，不能替代容错协议。人工可选择的动作包括：

- 选择已验证的检查点继续；
- 批准一个更窄权限的前向收敛路径；
- 批准或拒绝某个补偿动作；
- 终止任务并保全现场；
- 接管外部系统修复，并回填确认后的 Effect Log。

人工选择不能直接改变事实状态、伪造外部确认或跳过 Policy Gateway。

## 7. 安全、权限、成本与可观测性

### 7.1 安全与合规

- 恢复前重新执行主体、租户、仓库、路径和任务权限校验。
- 恢复后的每个业务 Action 和补偿 Action 都必须经过 Policy Gateway。
- 凭据只通过 `REQ-SEC-005` 重新签发短期引用，不能从 Checkpoint 或 Effect Log 恢复明文凭据。
- Checkpoint、Effect Log 和审计记录遵循数据分类、租户隔离、保留、删除和 Legal Hold 规则。
- Kill Switch 在恢复期间具有更高优先级；被锁定的任务不能通过恢复路径绕过。

### 7.2 成本与延迟

恢复成本由检查点读取、Effect Log 核查、独立探测、补偿、凭据签发和人工等待共同组成。恢复期保护优先于最低延迟，不能为追求恢复速度而放宽安全边界。

候选目标：

- 可恢复且无外部未知副作用的恢复路径 p95 小于 30 秒；
- 进入对账或人工升级的路径不设置虚假自动恢复 SLA，而是记录分风险等级响应时间；
- 恢复造成的重复外部副作用为零；
- 补偿失败事件的发现和升级必须可观测，不得静默丢失。

上述目标必须通过故障注入和基准评测校准，不代表已验证结果。

### 7.3 指标

至少记录：

- 恢复请求、评估、对账、补偿、收敛、升级和终止数量；
- 按根因指纹去重后的恢复路径数量；
- 污染半径分布和越界比例；
- 选择的恢复点与最近检查点的距离；
- Effect Log 未知状态数量和持续时间；
- 补偿成功率、补偿失败率、补偿熔断次数和人工升级数；
- 恢复态并发、恢复期限流、恢复期熔断和预算消耗；
- 恢复延迟、人工响应时间和前向收敛完成时间；
- 恢复后重复副作用数、未授权动作数和对外错误承诺数。

---

## 8. 验收标准

1. 检查点选择由污染半径是否越界决定，而非固定回退层数；相同故障分别注入只读链和外部写入链，选择结果符合污染边界。
2. 版本不兼容的检查点不能恢复；存在明确迁移器时才允许迁移。
3. 根因指纹相同的重复失败不会重复消耗同等自动恢复预算。
4. 检查点缺少租户、数据分类、保留、审计或 Legal Hold 属性时不能恢复。
5. 每个可能产生外部影响的 Action 都能在 Effect Log 中找到准备、执行确认和收敛记录。
6. 未确认的外部副作用进入三值对账；无权威真相源时直接升级，不能推断未执行。
7. Pivot 前允许安全补偿；Pivot 后禁止伪造技术回滚，并能进入前向收敛或人工接管。
8. 补偿动作经过 Policy Gateway 和幂等闸门；补偿独立预算和熔断器生效。
9. 任一补偿失败均产生高等级告警和人工升级，不被静默丢弃；其它独立补偿仍按策略继续。
10. 恢复态会降低并发和写操作放行能力，并与已有双计数器、预算和熔断器联动。
11. 九态状态机只允许定义的迁移；`RECOVERY_TERMINATED` 不可逆，终态不变量全部满足。
12. 恢复后创建新 Worker attempt，不覆盖原 Worker、Action、Artifact、Evidence 或 Effect Log 历史。
13. 恢复过程中权限、策略、凭据、Workspace、Toolset 或 Kill Switch 任一不通过时，系统拒绝或升级。
14. 恢复路径不会产生未记录的 Git Push、PR、通知、凭据签发或其它外部副作用。
15. 所有恢复决策、补偿、人工操作和对外承诺均可通过 Task、Workflow、Trace、Event、Evidence 和 Effect Log 关联回放。

## 9. 对其它需求的影响

- `REQ-RT-005`：增加恢复决策所需的污染半径和合规属性引用，但不改变 Checkpoint 基础 Schema 的事实源定位；需在跨模块冻结时确认扩展字段的兼容方式。
- `REQ-REL-003`：复用三值对账、IN_DOUBT 锁键、双计数器和 Policy Gateway 预裁决；新增恢复态保护作为调用上下文，不创建替代重试引擎。
- `REQ-REL-006`：必须支持正向 Action 与补偿 Action 的独立幂等键、结果未知核查和恢复后复用。
- `REQ-REL-007`：必须以 Effect Log 为补偿输入，支持 Pivot 前后不同路径，并将补偿失败升级而不是静默结束。
- `REQ-SEC-005`：恢复必须重新校验或重新签发短期凭据，不能从检查点读取凭据值。
- `REQ-SEC-009`：Kill Switch 优先于恢复和补偿调度；恢复态不得绕过锁定状态。
- `REQ-OBS-*`：需要增加污染半径、根因指纹、Effect Log 状态、恢复态、补偿态和对外承诺关联指标。
- `REQ-EVA-*`：需要增加崩溃、部分写入、Pivot、补偿失败、恢复流量峰值和错误承诺测试集。

## 10. 版本与冻结条件

### 10.1 MVP

MVP 必须包含：污染半径恢复点判定、版本与合规闸门、根因去重、Effect Log 三段式契约、Pivot 标记、补偿独立治理、恢复期保护和九态状态机。

MVP 不要求支持自动学习恢复策略、跨组织补偿、多仓库全局事务或复杂前向收敛优化。

### 10.2 冻结条件

升级到 `v1.0-frozen` 前必须完成：

1. 与 `REQ-RT-005`、`REQ-RT-007`、`REQ-REL-003`、`REQ-REL-006`、`REQ-REL-007` 的契约交叉评审；
2. Effect Log 和 contamination_radius 的字段、来源和计算责任评审；
3. Pivot 前补偿、Pivot 后收敛和补偿失败升级的故障注入设计；
4. 恢复期保护下的并发、限流、预算和熔断基准测试；
5. 九态状态机迁移和终态不变量契约测试；
6. 权限、凭据、Kill Switch、租户隔离和合规留存安全评审；
7. 通过 Golden Dataset、故障注入和安全门禁后再冻结阈值。
