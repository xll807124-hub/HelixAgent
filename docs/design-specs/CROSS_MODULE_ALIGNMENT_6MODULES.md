## 📋 模块接口总览

### 1. REL（可靠性） - 核心失败处理与恢复

**模块定位**: 失败分类、重试策略、Checkpoint 恢复、故障注入验证

**核心 API**:
- `REQ-REL-001`: Failure Taxonomy（3 正交维度：症状 / 生命周期 / 根因）
- `REQ-REL-002/003`: RetryPolicy 与 RetryDecisionEngine
- `REQ-REL-004`: Checkpoint 保留期与恢复决策
- `REQ-REL-006`: 写操作幂等性（与 RT-007 共享）
- `REQ-REL-009`: 故障注入验证场景库

**与 RT 的交接**:
| RT 需求 | REL 需求 | 交接点 | 对齐状态 |
|---------|---------|------|---------|
| RT-005 Checkpoint | REL-004 保留期 | Checkpoint 何时创建、多久过期、如何恢复 | ✅ 已对齐 |
| RT-007 幂等性 | REL-006 幂等性 | 幂等键生成与去重逻辑共享 | ✅ 已对齐 |
| RT-002 状态机 | REL-005 恢复决策 | Task 失败→Checkpoint→恢复 转移路径 | ⚠️ 需确认 |
| RT-008 事件查询 | REL-001 失败分类 | 事件中的 failure_symptoms、failure_stage、root_cause 字段 | ⚠️ 需确认 |

**与 SEC 的交接**:
| SEC 需求 | REL 需求 | 交接点 | 对齐状态 |
|---------|---------|------|---------|
| SEC-009 Kill Switch | REL-005 恢复决策 | 在 Kill Switch M2+ 期间，Checkpoint 恢复是否仍允许？ | ⚠️ 需确认 |
| SEC-003 Policy | REL-002/003 重试 | 权限拒绝的重试策略（应该禁止盲重试） | ✅ 已对齐 |

**已知风险**:
- Checkpoint 在 Kill Switch M2+ 期间的行为未明确（RT-SEC 清单已标为 P0 冲突 3）
- 故障注入验证场景库与实现设计的同步需要确认

### 2. CTX（上下文管理） - 代码索引与检索

**模块定位**: 代码索引、符号提取、混合检索、权限过滤、上下文压缩

**核心 API**:
- `REQ-CTX-001`: 索引 Schema（File / Symbol / Dependency / Relation）
- `REQ-CTX-003`: AST / LSP 依赖解析
- `REQ-CTX-004`: 混合检索与排序
- `REQ-CTX-005`: 权限过滤（只读/可写范围）
- `REQ-CTX-006`: Context Selector 与预算管理

**与 RT 的交接**:
| RT 需求 | CTX 需求 | 交接点 | 对齐状态 |
|---------|---------|------|---------|
| RT-001 Task/Action | CTX-001 索引 Schema | Action 的 code_range / target_file 字段与 Index Entity 的绑定 | ⚠️ 需确认 |
| RT-006 Trace Context | CTX 所有需求 | 检索操作应该记入 Trace 吗？采样率如何处理？ | ⚠️ 需确认 |

**与 SEC 的交接**:
| SEC 需求 | CTX 需求 | 交接点 | 对齐状态 |
|---------|---------|------|---------|
| SEC-002 RBAC | CTX-005 权限过滤 | 符号和文件的读写权限应该如何校验？ | ⚠️ 需确认 |
| SEC-008 多租户 | CTX 所有需求 | 索引数据是否严格按租户隔离？ | ✅ 已对齐 |

**已知风险**:
- 与权限检查的集成点不清楚（REL + CTX 的权限过滤怎么协作）
- 检索性能基线（p95 < 500ms）与上下文预算的权衡需要实现验证

## 🔴 需要紧急确认的跨模块冲突点

### 冲突 1: Checkpoint 在 Kill Switch 中的语义

**问题**:
- REL-004 定义 Checkpoint 保留期与恢复决策
- SEC-009 Kill Switch M2+ 期间禁用工具或升级审批
- **如果 Checkpoint 涉及被禁用的工具，恢复应该怎样处理？**

**现状**: REL 和 SEC 尚未评审这个场景

**建议决策**:
- 恢复时应该告知用户"该工具已被禁用"，交给人工决定
- 禁止静默跳过失败 Action

---

### 冲突 2: 记忆（MEM）的权限隔离

**问题**:
- MEM-001 定义四层记忆 Schema（工作 / 任务 / 项目 / 组织）
- SEC-002 定义 RBAC 与权限交集
- **记忆的读写权限应该与创建任务的权限相同吗？还是更严格？**

**现状**: MEM 和 SEC 未讨论此权限边界

**建议决策**:
- 记忆继承创建 Task 时的权限上下文，但不能扩大权限
- 跨租户记忆检索必须强制组织隔离

---

### 冲突 3: Harness 是否应该是 Worker 的一种

**问题**:
- RT-001 定义 Worker 为任务执行者（有 allowed_tools、budget）
- HAR-001 定义 Harness 为独立测试框架（有独立状态机）
- **Harness 创建故障注入时，是应该作为特殊 Worker 提交还是独立路径？**

**现状**: RT 和 HAR 尚未明确此分工

**建议决策**:
- Harness 不是 Worker，是独立实体
- Harness 运行结果（Verdict + Evidence）应该产生专用事件类型（不走 Action 路径）

---

### 冲突 4: OBS 中 Trace 和 Event 的关系

**问题**:
- RT-003 定义 EventEnvelope（事件存储）
- OBS-002 定义 Trace Event（可观测性追踪）
- **是否每个 RT Event 都应该对应一个 OBS Trace Span？还是有选择地产生？**

**现状**: RT 和 OBS 未明确映射关系

**建议决策**:
- 并非所有 RT Event 都产生 Span（例如 idempotency_result 可能只有选择性记录）
- Span 生成遵循 OBS-001 的采样规则和权限过滤

## 🟡 需要进一步评审的设计点（P1）

### 设计点 1: CTX 权限过滤与 SEC-002 RBAC 的集成

**问题描述**:
- CTX-005 定义符号和文件的"只读"与"可写"权限
- SEC-002 定义 Agent 权限是用户/组织/策略/代码托管平台四维交集
- **如何在检索时高效执行这个交集？是否需要缓存投影？**

**当前设计**: CTX-005 未定义与 Policy Gateway 的实时交互

**需确认**:
- 是否需要在投影层预计算权限视图？
- 检索延迟基线（p95 < 500ms）如何与权限校验耗时对齐？

---

### 设计点 2: MEM 与 CTX 的内容交集

**问题描述**:
- MEM-003 处理记忆检索与冲突
- CTX-004 处理代码符号检索与排序
- **如果同时查询代码符号和过往记忆，两个结果应该如何合并排序？**

**当前设计**: MEM 和 CTX 未定义联合检索规范

**需确认**:
- 是否需要统一的 Context Selector 来分配两者的预算？
- 排序权重应该如何定义（最近性 vs 相关性 vs 置信度）？

---

### 设计点 3: EVA 中 Golden Dataset 污染控制与实现

**问题描述**:
- EVA-001 要求"污染控制等同安全事件"
- EVA-005 定义回归管道
- **如何检测数据污染？是否需要与 Git 版本绑定？与 RED TEAM 隔离如何实现？**

**当前设计**: EVA-001 定义了原则，但检测机制未详细设计

**需确认**:
- 污染检测是自动化还是人工审查？
- 回滚机制的 SLA 是多久？
