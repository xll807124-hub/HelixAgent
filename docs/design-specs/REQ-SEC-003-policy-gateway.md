## 2. 目标、范围与问题分析

### 2.1 目标

建立一个统一、确定、可审计的策略决策能力，在 Agent 生命周期内的规定干预点评估动作，并返回允许、拒绝或要求审批的结果。所有工具和外部副作用必须在执行前经过策略执行点（PEP）校验。策略决策点（PDP）只评估并返回有界决策，不执行工具、不签发凭据；执行器、Harness、工具适配器负责强制执行结果。

### 2.2 原需求缺口

原待办未定义 Policy Gateway 与 RBAC、风险分类、状态机、执行器和审批服务的边界；未定义审批矩阵、策略优先级、超时、策略版本和决策失效语义；也未规定模型或策略服务故障、计划变化、多 Agent 委派和审计数据处理方式。这些缺口可能导致消费者对同一动作作出不同决定、审批被绕过、过期决定被重放或审计泄露敏感数据。

### 2.3 范围

包含策略干预点、PDP/PEP 职责、OPA/Cedar 策略引擎集成、确定性决策语义、审批矩阵、独立 Auto-review 服务、审批状态与超时升级、计划变化重审、决策缓存、安全审计、故障处理、评估与验收。

不包含 RBAC 主体和资源授权模型（`REQ-SEC-002`）、凭据签发与撤销（`REQ-SEC-005`）、沙箱强制隔离（`REQ-SEC-004`）、提示注入检测算法（`REQ-SEC-006`）、MCP 注册治理（`REQ-SEC-007`）、Kill Switch 全面事故流程（`REQ-SEC-009`）、具体 UI/API 协议、数据库结构及生产 SLA。

### 2.4 设计不变量

1. 未明确允许即拒绝；显式拒绝、组织不可覆盖的安全约束及紧急停止优先于审批和允许规则。
2. 决策由确定性策略引擎基于经过验证的结构化事实作出；模型输出、用户说明、仓库文本和 Agent 自述理由不能授予权限。
3. 所有 Action 在工具执行前由 PEP 检查，执行器在副作用发生前再次校验决定仍有效。
4. 审批只覆盖明确主体、动作、资源、参数摘要、计划版本和有效期；任一关键范围扩大、策略版本变化或身份授权变化都须重新评估。
5. Auto-review 是独立服务，只处理策略判定为可升级审批的请求；其批准不扩大原授权范围，不得覆盖拒绝规则、硬约束或强制人工审批类别。
6. Policy Gateway 不持有、查看或传递凭据材料；凭据代理只接受可验证且仍有效的批准依据，并独立执行 SEC-005 规则。
7. 权限/策略/身份关键依赖不确定或不可用时 fail-closed；不能把系统故障伪装成用户拒绝。
8. 每个决定及审批生命周期必须与 Runtime 的 Task、Workflow、Worker、Action、Trace 坐标关联并产生不可变审计事实。

## 3. 公开依据与设计参考

研究访问日期：2026-09-23。公开事实仅描述资料明确公开的产品行为，不推断未公开内部实现。

**公开事实**：企业托管权限覆盖部分 Shell、文件、网络及 MCP 操作，并支持拒绝、要求新的人类批准、允许等规则；官方设置资料说明 deny/ask/allow 的优先关系及管理策略不可被用户偏好、自动批准或既有批准削弱。  
**设计推断**：组织强制约束应不可由下级策略放宽；重复性许可需受策略版本和动作范围约束。  
来源：[Enterprise managed permissions](https://github.blog/changelog/2026-09-09-enterprise-managed-permissions-for-github-copilot-agent-operations/)、[Enterprise managed settings](https://docs.github.com/en/enterprise-cloud@latest/copilot/reference/enterprise-managed-settings-reference)、[配置指南](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/manage-agents/configure-enterprise-managed-settings)。

**设计推断**：审批钩子应与硬拒绝规则组合，而不是成为替代授权的旁路。

### 3.3 OpenAI Codex

**设计推断**：独立审查者只能替换审批处理者，不能授予超出原策略边界的能力。  
来源：[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)、[Auto-review](https://developers.openai.com/codex/concepts/sandboxing/auto-review)、[Permissions](https://developers.openai.com/codex/permissions)。

## 4. 功能需求与决策模型

### 4.1 功能目标与使用方

| 使用方 | 目标 |
|---|---|
| Harness/Coordinator | 在任务启动、计划审批及关键阶段迁移前取得策略判定 |
| Tool Adapter/Executor | 每次工具调用和副作用前验证决策、授权版本和运行状态 |
| 审批服务 | 建立人工审批请求、提醒、升级、超时及结果事件 |
| 独立 Auto-review 服务 | 对限定范围内的审批请求给出建议性审批结论或升级人工 |
| SEC-005 凭据代理 | 验证有效批准引用后按自身策略签发最小权限短期凭据 |
| 审计与安全运营 | 追溯决策事实、策略版本、审批来源、拒绝类别及行动结果 |

### 4.2 MVP 干预点

MVP 强制支持：

1. **任务授权**：任务进入可规划阶段前校验用户、组织、仓库、任务范围及组织策略。
2. **计划审批**：计划进入执行前，根据计划范围、风险和组织规则决定放行、人工审批或拒绝。
3. **工具/Action 执行前**：每个工具调用均在执行前评估工具类别、参数约束、资源目标、运行状态、RBAC 结果、风险分类、预算和 Kill Switch 信号。
4. **审批恢复前**：审批通过后，在状态迁移和实际执行前重新验证审批有效性、主体授权、动作摘要、计划版本、策略版本及运行状态。
5. **工具结果返回前（限定）**：对含敏感数据或高风险外部来源的结果，允许调用方接入输出检查；具体检测由 SEC-006、CTX 与工具适配需求负责。MVP 不宣称实现完整内容安全过滤。

网络访问和最终输出审核为后续扩展干预点；MVP 网络规则由沙箱/执行环境与工具策略共同约束，不能将未来扩展点描述为已交付能力。

### 4.3 决策结果与规则优先级

决策结果为：

- **ALLOW**：当前动作在全部硬约束和策略范围内，可进入执行器的二次校验。
- **REQUIRE_APPROVAL**：当前动作未触发硬拒绝，但需在执行前完成指定人工审批或符合条件的独立 Auto-review。
- **DENY**：动作违反硬约束、明确拒绝规则或不可满足的安全要求；不执行，不因普通重试改变结果。

规则合成采用如下约束，而非简单的“第一个匹配规则即结束”：身份/租户/资源授权拒绝、策略显式拒绝、状态禁止、Kill Switch、强制人工审批类别属于不可放宽的限制；所有适用限制取交集，任何 DENY 胜过审批或允许；审批要求胜过普通 ALLOW；只有全部适用规则允许且无待审批条件时才 ALLOW。未知动作、无匹配策略或冲突无法确定时 DENY。范围变换只允许缩小目标资源/操作范围，且必须把变换后的目标返回给 PEP 并供执行器验证。

OPA/Cedar 负责对可信、类型化、经验证的事实作确定性评估。规则优先级、默认决策和版本在策略包中显式管理；未经测试的策略变更先进入只评估不执行的影子阶段。OPA/Cedar 具体选型及适配不锁定某个 DSL 文法或网络协议。

### 4.4 决策输入和输出（概念层面）

**输入事实至少包括**：请求唯一关联、干预点、主体链（发起用户及当前 Agent/Worker）、组织和资源引用、操作/工具类别、经规范化的目标资源与必要参数属性、Task/Workflow/Worker/Action 状态、计划 Artifact 版本、SEC-002 授权结果及授权版本、数据敏感级别、SEC-001 风险类别/级别、预算/时间边界、审批引用、策略版本、Kill Switch 状态和 Trace 关联。

只传递策略判断所必需的最少事实；不传入模型隐藏思维链、长期凭据或无关源代码。Agent 提供的理由文本可供审批人和审计员理解上下文，但不得单独作为授权事实。

**输出至少包括**：决策结果、不可变决策标识、请求/运行实体关联、策略及授权版本、适用规则/原因类别、是否需要审批及审批等级、经批准的范围上限、有效期/再验证要求、决策来源（规则/人工/独立 Auto-review）、审计关联及必要的完整性证明。具体序列化格式和签名算法留给实现设计。

拒绝原因至少可区分：身份无效、租户/资源不匹配、SEC-002 拒绝、未知动作/工具、状态不允许、风险策略拒绝、需人工审批、审批缺失/拒绝/过期、策略版本未知、Kill Switch、生效策略冲突、依赖不可用、预算或范围越界。面向最终用户的错误应避免泄露其他组织资源是否存在；受控审计保留更精细的原因。

## 5. 核心处理流程

### 5.1 执行前决策

1. PEP 在工具执行前形成单个 Action 决策请求，并绑定 Task、Workflow、Worker、Action、Trace 和请求版本。
2. PEP 校验调用主体、工具 Schema 版本、目标资源和参数摘要；不完整、不可规范化或未知字段按拒绝处理。
3. PDP 验证身份链、组织边界、运行状态、策略版本与 Kill Switch 状态。
4. PDP 获取 SEC-002 对同一主体、资源和操作的授权决定及授权版本；RBAC 是上限，不被策略引擎的 allow 覆盖。
5. PDP 取得可信风险分类和数据敏感度；风险服务缺失或关键事实未知时，对受保护动作拒绝或暂停，不推断放宽。
6. OPA/Cedar 评估组织基线与适用策略；合成硬限制、审批要求和范围窄化结果。
7. PDP 将 ALLOW、REQUIRE_APPROVAL 或 DENY 返回 PEP，并写入决策审计事实。未收到有效决定不得执行。
8. 对 ALLOW，执行器在产生副作用前复核决定的时效、策略/授权版本、Action 摘要、任务状态和 Kill Switch；任何变化都重新评估。
9. 对 REQUIRE_APPROVAL，暂停依赖该决定的 Action，并创建正式审批待办；不得通过模型重规划、并行 Worker 或重试绕过等待。
10. 对 DENY，PEP 阻止执行并记录拒绝事件；是否继续不相关工作由 Workflow 规则决定，拒绝本身不得自动转成允许。

### 5.2 计划审批与变更检测

计划批准绑定 Plan Artifact 版本、计划摘要、仓库/路径范围、工具类别和预期副作用。计划或授权事实变化后必须重新评估。

计划差异检测采用三层策略：

1. **结构化/文本差异快速筛选**：对计划字段和 Artifact 差异做确定性比较，纯格式或无语义说明变更可按组织规则免重复审批；不能仅因“注释/格式化”标签自动放行实际权限范围变化。
2. **语义差异分析**：当文件、符号、函数签名、逻辑行为、重命名/移动或调用关系发生实质变化时，使用版本化索引及语义比较结果辅助识别影响。语义分析属于风险信号，不是授权依据，也不以 LLM 判断取代硬规则。
3. **高风险强制复核**：权限扩大、敏感路径、外部网络、凭据/身份边界、破坏性操作或影响范围不确定时，必须人工 Review；Auto-review 不得批准被标记为强制人工的类别。

差异不确定、索引不可用或无法建立新旧计划对应关系时，保守地要求重新审批。差异报告记录旧/新版本、分类和证据引用，避免把完整敏感文件内容写入普通审计日志。

### 5.3 审批、超时和升级

审批请求必须绑定请求者、被审批动作、资源范围、风险级别、计划版本、策略版本、审批职责、理由摘要、创建时间和到期策略。请求者不能审批自己的提权或高风险动作；审批者必须具备对应职责并与请求范围匹配。

审批生命周期包括待处理、提醒中、已升级、已批准、已拒绝、已撤销、已过期等概念状态。其状态事实由运行时/审批工作流持久化，Policy Gateway 消费审批事实并重新决策，不直接覆写 Task/Action 状态。

超时处理分层进行：

1. 到期前按组织配置通过已启用渠道提醒当前审批人，并保留提醒尝试结果；通知渠道不可用不构成批准。
2. 达到升级时点时转交上一级主管或指定备份审批人；升级不改变请求内容或原定审批门槛。
3. 最终超时采用组织配置的兜底行为。默认安全基线为低风险、可逆、只读且明确列入允许清单的动作可自动批准；写入、高风险、敏感数据、不可逆或强制人工类别自动拒绝/过期。不得将“低风险”标签本身视为充分条件，须同时满足组织策略、授权、范围和动作白名单。
4. 组织可以收紧兜底行为；放宽默认拒绝边界须通过受控策略变更审查，且不得覆盖平台不可放宽的安全基线。
5. 超时到达和升级事件必须审计。审批服务故障、通知失败或升级对象不可解析时，不自动批准，转入拒绝/过期或等待人工处置的安全兜底。

审批完成后，PDP/PEP 在继续前重新检查主体、当前授权版本、策略版本、任务状态、计划版本、Action 摘要和授权范围。拒绝及过期不得被重试绕过；修改后的动作必须形成新的请求和决策关联。

## 6. Auto-review 独立服务

Auto-review 作为独立服务部署，与 Policy Gateway 的确定性策略评估面分离。Policy Gateway 只把明确标记为可 Auto-review 的 REQUIRE_APPROVAL 请求路由给该服务；其输入是最小化、脱敏后的结构化动作事实、计划差异摘要、风险信号和组织安全基线，不包含凭据和不必要源码。

Auto-review 输出为建议性批准、拒绝或升级人工，并附可审计理由类别与模型/策略版本。最终接受该结果的主体及如何形成正式审批事件由审批服务/Policy Gateway 的受控集成决定。高风险强制人工类别、硬拒绝、身份/授权失败、范围扩大和关键事实不确定不得进入自动批准路径。服务不可用、超时、输出格式无效或置信不足时升级人工或拒绝，不回退为 ALLOW。

**安全基线默认值**：Auto-review 默认关闭自动批准能力，先以影子/建议模式积累评估证据；启用后仅对低风险、可逆、只读或经明确枚举的窄范围动作开放。组织管理员可在平台下限内收紧或覆盖可配置阈值，但不能调整强制人工类别或平台硬拒绝条件。阈值以离线验证、误放行率、误拒率和分层评测结果校准；本设计不虚构置信度数值。

## 7. 多 Agent 与 OBO 身份链

每次策略决策的授权主体始终是发起用户；当前 Agent/Worker 作为执行者和委派链信息单独记录。每一层 Agent 的每次工具调用都独立经 Policy Gateway 判定，权限上限是用户当前有效授权、组织策略、当前任务批准范围和已批准委派范围的交集。Agent、Agent 之间的转交或子 Agent 声明不能扩大该交集。

Agent 间采用短寿命、单跳的 OBO（On-Behalf-Of）身份传递概念：至少能验证用户主体、来源 Agent、目标 Audience、委派动作/范围、签发时间、分钟级有效期及唯一防重放关联。接收 Agent 只能在指定 Audience 和授权范围内使用；跨 Agent 再委派须产生新的受控单跳凭证并重新决策，不可透传旧凭证无限链式使用。令牌具体格式、密码算法、撤销机制和凭据签发职责由 SEC-005/实现设计确定；Policy Gateway 不持有令牌秘密。

## 8. 决策缓存、一致性与故障处理

决策缓存不是授权事实源。缓存键至少区分主体链、组织、资源、操作类别、目标摘要、Action/计划版本、策略版本、授权版本、运行状态和 Kill Switch epoch。敏感操作、写操作、破坏性操作、审批恢复及权限版本不确定时直查或在副作用前强制重新验证。

缓存 TTL 按风险与操作性质差异化，推荐初始范围如下，最终值须经负载和撤销时效基准测试确认：

- 低风险只读：5 至 15 分钟；
- 高风险或写操作：30 秒至 1 分钟，或不缓存而直查；
- `REQUIRE_APPROVAL` 不缓存为执行许可；审批事实单独持久化并在恢复时复核；
- DENY 可有限缓存，但身份、授权、策略和 Kill Switch 变化须立即失效。

所有 TTL 采用约 ±10% 随机抖动以分散集中失效；抖动不得使有效期超过对应风险上限。策略版本、RBAC 授权版本、身份撤销、计划版本或 Kill Switch 变化应触发相关缓存失效。不能确认失效传播或当前版本时，对受保护操作拒绝/暂停。

故障规则：

| 故障 | 行为 |
|---|---|
| OPA/Cedar 引擎、策略包或策略版本不可用/无效 | 拒绝受保护动作；保留系统故障类别，不误报为普通用户拒绝 |
| SEC-002、身份、租户或资源归属校验不可用 | 拒绝，不使用陈旧允许结果 |
| 风险分类关键字段未知 | 采取更严格类别并要求人工或拒绝；不得自动降级 |
| 审批/通知服务不可用 | 保持未获批准状态，最终按安全超时兜底，不自动批准 |
| Auto-review 不可用或输出无效 | 升级人工或拒绝 |
| 审计事实无法可靠记录 | 对安全敏感动作暂停/拒绝；不可静默放行 |
| Kill Switch 激活 | 阻止新动作，并由 SEC-009 定义在途副作用处理；立即失效相关缓存 |
| 重复或并发决策请求 | 以稳定请求关联去重；同一关联的内容摘要不同则拒绝冲突并审计 |

## 9. 状态管理、数据流与人类在环

Policy Gateway 返回决策事实，不直接修改 Task、Workflow、Worker 或 Action 状态。PEP/状态机依据 `REQ-RT-002` 执行合法迁移：ALLOW 可使 Action 进入授权/执行路径；REQUIRE_APPROVAL 进入 `WAITING_APPROVAL`；DENY 进入 `REJECTED` 或上层定义的受控失败/取消分支。审批通过后必须先复核，再由状态机迁移；审批拒绝/过期不得转成执行态。

人工审批界面至少应向有权限的审批人展示动作类别、目标资源的脱敏标识、参数影响摘要、计划差异、风险等级、批准范围、有效期、拒绝影响及发起者；提供批准、拒绝、要求修改/补充信息等动作。批准不可编辑原动作范围；要求修改产生新计划/Action 版本。审批人身份、职责、决定及时间写入审计事实。

## 10. 权限、安全、审计与合规

- PDP/PEP 分离；策略服务无工具执行、凭据读取和状态覆写能力。
- 所有策略输入来自经验证的结构化事实；外部内容和 Agent 自述均按不可信输入处理。
- 策略变更必须版本化、经过授权审查、可回滚且保留历史；不能由运行中的 Agent 修改。
- 决策凭证须可绑定请求、主体链、Action 摘要、资源、策略/授权版本及有效期，并具备防篡改/重放语义；具体签名机制待实现安全设计确定。
- 审计依据 `REQ-RT-003/006/008` 的事件、Trace、查询、留存和访问控制约束；安全决策审计不得依赖普通 Trace 采样。
- 审计字段采用三级脱敏：**一级必须完全移除或不可逆脱敏**，如密钥、Token、密码、身份证号、银行卡号及敏感精确金额；**二级应模糊化或受限访问**，如具体路径、内部 IP、未公开 API 端点、合同条款；**三级可保留**，如操作类别、决策结果、风险等级、时间戳及脱敏资源标识。法规、合同或组织规则更严格时从严执行。
- 用户界面仅展示理解决策所需原因，避免暴露其他租户资源存在性、策略内部细节或敏感数据。
- 安全决策服务应限制调用身份与组织范围；管理策略的能力与读取业务数据的能力分离。

## 11. 性能、成本与可观测性

性能以不牺牲撤销及时性、每次 Action 校验和审计完整性为约束。可通过请求内去重、并行读取可信事实和有限低风险缓存优化；不得在未知状态下使用预评估作为最终许可。自动审查模型成本单独归集，不把人工审批等待时间混入同步决策延迟。

实施阶段建立代表性并发和故障基准后确定延迟/容量 SLO；当前不设未测量的 QPS 或硬延迟验收值。

最低可观测指标包括决策总量及结果、按干预点/工具类别/风险级别的延迟和拒绝类别、策略版本/授权版本不一致、审批等待与升级时延、超时兜底结果、Auto-review 使用率/升级率/人工一致性、影子策略差异、缓存命中与失效传播、依赖故障和审计写入失败。指标标签不含用户 ID、完整路径、原始参数或源码；细节仅存于受控审计。

Auto-review 评估应包括按风险和动作类别分层的误批准、误拒绝、人工升级、一致性与漂移；不能用总体准确率掩盖高风险类别错误。任何强制人工边界的违反均为阻断性缺陷。

## 12. 异常场景

| 场景 | 预期行为 |
|---|---|
| 未知工具、操作或策略版本 | DENY，记录原因类别；不执行 |
| 请求上下文缺字段、目标资源歧义或参数校验失败 | DENY；要求调用方重新构造有效请求 |
| RBAC 与策略结果冲突 | 采用更严格结果；RBAC 拒绝不能被策略 ALLOW 覆盖 |
| 两条策略冲突或匹配规则不确定 | DENY 并产生配置告警 |
| 审批后计划、Action 参数、工具版本或资源范围改变 | 原审批失效，创建新请求并重新审批 |
| 审批者无对应职责或请求者自批 | 拒绝审批结果并审计 |
| 审批超时且升级失败 | 安全兜底：高风险/写/敏感动作拒绝；仅明确列入低风险白名单者可按组织配置处理 |
| Auto-review 建议批准但存在强制人工/硬拒绝条件 | 忽略自动批准，拒绝或转人工；不得执行 |
| 多 Agent OBO Audience、单跳或期限验证失败 | DENY，并记录身份链验证失败 |
| 缓存失效事件延迟或版本不可确认 | 高风险动作直查；无法验证则拒绝/暂停 |
| 审计服务写入失败 | 安全敏感决策不得静默放行；受控暂停/拒绝并触发运营告警 |

## 13. 验收标准

| 编号 | 可验证标准 | 验证方式 |
|---|---|---|
| SEC-003-AC1 | 每个工具调用在实际执行前经 PEP 获得与 Action 摘要、资源及策略版本绑定的有效决定；缺少决定不得执行 | 端到端绕过测试 |
| SEC-003-AC2 | ALLOW、REQUIRE_APPROVAL、DENY 分别按定义执行；拒绝或待审批动作不发生副作用 | 决策契约与状态机集成测试 |
| SEC-003-AC3 | RBAC 拒绝、硬策略拒绝、状态禁止、Kill Switch 或强制人工类别不能被普通 ALLOW/Auto-review 覆盖 | 策略组合负向测试 |
| SEC-003-AC4 | 授权、策略、身份或运行状态版本变化后，旧决策不能用于新的副作用 | 并发撤销与版本失效测试 |
| SEC-003-AC5 | 计划文本变化按差异规则分类；语义/范围变化重审，高风险变化强制人工；分析不确定时不自动批准 | 固定差异样本集回归测试 |
| SEC-003-AC6 | 审批请求绑定主体、动作、范围、Plan/Policy 版本和期限；修改范围后旧批准不可复用 | 审批重放与范围扩大测试 |
| SEC-003-AC7 | 提醒、升级和最终超时兜底按配置执行；通知/升级服务故障不会导致自动放行 | 时间控制与故障注入测试 |
| SEC-003-AC8 | Auto-review 为独立服务；硬拒绝和强制人工请求不可自动批准；超时/无效输出不放行 | 服务隔离、攻击和故障注入测试 |
| SEC-003-AC9 | 多 Agent 每层工具动作单独决策，授权始终受发起用户权限上限约束；错误 Audience、过期或跨跳凭证被拒绝 | 委派链属性与重放测试 |
| SEC-003-AC10 | 低风险只读与高风险写操作使用不同 TTL 范围和约 ±10% 抖动；高风险版本变化可立即失效/直查 | 可控时钟缓存测试 |
| SEC-003-AC11 | OPA/Cedar 或策略适配层不可用、策略包无效、关键依赖不可用时受保护动作 fail-closed | 故障注入测试 |
| SEC-003-AC12 | 每项决策和审批/升级/过期事实可追溯至 Action、Task、Workflow、Worker 和 Trace，且审计不包含密钥、隐藏思维链或不必要源码 | 审计完整性与敏感数据扫描 |
| SEC-003-AC13 | 审计字段遵守一级移除、二级模糊化/受控、三级按需保留的脱敏级别 | 字段级脱敏测试 |
| SEC-003-AC14 | 策略影子模式只记录预测决定、不影响执行； enforce 模式严格执行规范化 verdict | 双模式一致性测试 |
| SEC-003-AC15 | 策略配置变更、发布、回滚和版本引用可审计；运行中 Agent 不能更改策略 | 权限和变更审计测试 |

## 14. 依赖与接口边界

### 14.1 上游

- `REQ-RT-001/002/003/006/007/008`：共享实体、Action 状态、事件事实、Trace、幂等关联和审计治理。
- `REQ-SEC-001`：风险类别、数据敏感级别与威胁语境；本需求不重新定义风险分值算法。
- `REQ-SEC-002`：主体、资源、授权决定、拒绝原因、授权版本和策略上限。
- OPA 或 Cedar：确定性策略评估引擎；部署形态、策略语言和版本仍需工程评审。
- 审批服务：审批队列、身份/职责验证、通知、升级与审批结果事实。
- 独立 Auto-review 服务：受限的升级请求判断。

### 14.2 下游

- `REQ-HAR-001/003`：Harness 与工具适配器在规定干预点调用 PDP，并作为 PEP 强制执行结果。
- `REQ-SEC-005`：仅消费可验证、未过期、范围匹配的批准依据；不接受凭自然语言理由签发凭据。
- `REQ-SEC-006/007`：注入检测结果、MCP 工具身份/Schema/操作进入策略上下文。
- `REQ-SEC-009`：Kill Switch 触发阻断及缓存失效，具体在途处置归 SEC-009。
- `REQ-CTX-005`：检索动作和候选内容访问前执行权限/策略约束。
- `REQ-RT-002`：消费策略结果后由状态机服务执行合法迁移；Policy Gateway 不覆写状态。

概念接口只交换最小化的主体链、资源、操作、版本、风险、审批状态、决定及原因类别。不冻结具体 RPC 协议、策略文法、数据库 Schema 或令牌格式。

## 15. MVP 与版本演进

### MVP

- 支持任务授权、计划审批、Action 执行前决策和审批恢复复核。
- 使用 OPA 或 Cedar 之一作为外部/集成策略引擎；在实施评审前确定单一选型，不要求两者并行运行。
- 采用 ALLOW / REQUIRE_APPROVAL / DENY 三态和默认拒绝、硬约束优先规则。
- 审批矩阵按工具类别与资源敏感级别粗粒度配置；平台安全基线高于组织覆盖值。
- 独立部署 Auto-review 服务，默认影子/建议模式；组织管理员可在平台安全基线内覆盖适用阈值。
- 审批提醒、升级和按风险类别区分的组织兜底；高风险和写操作超时默认拒绝。
- 差异检测采用文本筛选、语义影响辅助及高风险强制人工复核。
- 多 Agent 逐 Action 决策和受发起用户权限约束的短寿命单跳 OBO 语义；令牌细节由 SEC-005 负责。
- 风险差异化缓存 TTL 与随机抖动；策略/授权变化失效，敏感动作执行前复核。
- 三级审计脱敏、影子评估、策略版本化与 fail-closed。

### 后续版本候选

审批矩阵下钻到具体工具/路径；完整网络与输出干预点；策略影响分析和管理员模拟；更细粒度职责分离/MFA；更丰富的 OBO 委派撤销机制；自动策略优化。以上均不作为 MVP 已实现承诺。

### 冻结条件

完成 SEC-002 授权上限与 SEC-003 策略合成评审；明确 OPA/Cedar 单一选型及策略治理流程；确认审批职责、提醒渠道、升级关系和超时配置边界；确认 Auto-review 独立服务安全评估与分层 Golden Set；验证差异检测对高风险范围变化的保守行为；完成缓存撤销、OBO 重放、故障关闭、审计脱敏及跨模块契约测试设计。详细设计完成不表示实现或安全验证完成。

## 16. 设计决策记录

| 决策 | 推荐基线 | 理由与边界 |
|---|---|---|
| PDP/PEP | 决策与执行分离 | Policy Gateway 判定，Harness/Executor 强制执行 |
| 决策语义 | ALLOW / REQUIRE_APPROVAL / DENY | 显式表达审批等待，不把审批等同拒绝 |
| 策略引擎 | MVP 集成 OPA 或 Cedar 之一 | 复用成熟策略引擎；具体单选待实施评估 |
| 审批矩阵 | 工具类别 × 资源级别粗粒度 | 降低 MVP 治理复杂度，验证后逐步细化 |
| Auto-review | 独立部署 | 故障/权限隔离；不扩大决策边界 |
| Auto-review 阈值 | 平台安全基线 + 组织可收紧/覆盖 | 开箱即用和组织适配并存；强制人工类别不可覆盖 |
| 审批超时 | 到期提醒、升级、组织兜底三层 | 保持责任链；高风险/写操作默认拒绝 |
| 计划变化 | 文本差异 + 语义辅助 + 高风险人工 Review | 语义结果仅作信号，授权依据仍为结构化事实 |
| 多 Agent 身份 | 发起用户为授权主体，每层 Agent 单独决策 | OBO 单跳、短寿命，防止委派链权限膨胀 |
| 缓存 | 风险差异 TTL + 约 ±10% 抖动 | 平衡延迟与撤销时效；未经基准不承诺固定 SLO |
| 审计脱敏 | 一级移除、二级模糊化/受控、三级可保留 | 满足调查需要并限制敏感数据泄露 |
| 故障策略 | 受保护动作 fail-closed | 关键事实不确定时不使用陈旧许可 |

## 17. 待确认问题

以下不阻止形成 `v0.1-designed`，但需在跨模块冻结/实施前确认：

1. OPA 与 Cedar 的最终单一选型、策略作者权限、发布审批及运维责任。
2. 工具类别、资源敏感级别和组织可配置审批矩阵的初始目录。
3. 平台 Auto-review 安全基线由哪个治理角色批准；组织管理员覆盖的上/下限如何管理。
4. 审批提醒渠道、升级层级、各级时限及允许自动批准的低风险可逆只读动作清单。
5. 语义计划差异所需索引/解析能力及索引不可用时的人工兜底责任。
6. OBO 身份证明、签发、Audience、撤销和防重放的具体契约，归属 SEC-005。
7. 各风险级别 TTL 的最终值、缓存基础设施、版本失效传播时限和实测性能目标。
8. 一级/二级审计字段目录、脱敏算法、保留期、访问审批以及适用法规/合同约束。
9. 审计写入不可用时，不同风险动作的暂停边界和恢复责任。
