## 一、分层总览

全部 21 个全局组件分为 **4 层**，层内可大量并行，层间按箭头方向推进：

```
L0 运行时与安全底座（宪法层，最先冻结）
   G01 运行时核心契约（RT-001/002/003 + RT-004/006 横切）
   G02 威胁模型与安全治理（SEC-001 + SEC-010）
   G03 CTX/MEM Schema 套件（CTX-001/002 + MEM-001）
   G04 失败分类与检测器（REL-001 + REL-008A）
   G05 遥测采集基础设施（OBS-001）
   G06 评估数据集管理（EVA-001）

L1 核心服务层（依赖 L0，大多可并行）
   G07 授权与策略执行（SEC-002/003）
   G08 事件查询与留存（RT-008）
   G09 检查点与幂等（RT-005/007 + REL-004）
   G10 CTX 构建管线（CTX-003/007）
   G11 CTX 查询服务（CTX-004/005/006）
   G12 MEM 写入与读取路径（MEM-002/003/004）
   G13 重试决策与恢复协调（REL-002/003/005）
   G14 遥测数据模型层（OBS-002）
   G15 标注与评分框架（EVA-002/003）

L2 治理与执行层（依赖 L1）
   G16 沙箱与网络出口（SEC-004）
   G17 凭据代理与 MCP 治理（SEC-005/007）
   G18 写幂等账本与补偿工作流（REL-006/007）
   G19 工具治理与统一路由（REL-008/009 + HAR-003/005）
   G20 Harness 工程平台（HAR-001/002/004/006）
   G21 遥测质量与审计（OBS-003/004/005/006/007）

L3 收口层（依赖 L2，最后冻结）
   多租户数据治理与 Kill Switch（SEC-008/009）
   失败诊断与回归发布门禁（EVA-004/005/006）
   CTX 评测、压缩（CTX-008/009）
```

## 三、跨组交叉依赖点（四份报告合并后新发现）

这些是单独看某一份报告时不明显、合并后才能看清的跨组依赖：

| 依赖 | 说明 |
|---|---|
| **G13 → G23** | REL-005 的"故障注入验证"（REL-009，归入 G19）需要先于 EVA-004 完成，因为 EVA-004 失败归因强依赖 Harness 重放管线（G20）做反事实验证，而 REL-009 的 MVP 场景库又反哺 EVA-004 的归因训练数据 |
| **G20 → G23** | HAR-001 的 Harness 重放管线是 EVA-004 失败归因的强依赖（反事实验证），也是 EVA-006 发布门禁契约测试（HAR-006）的执行基础 |
| **G04 → G15** | REL-001 的 14 类症状词表同时被 REL 侧（G13 决策引擎）和 EVA 侧（EVA-002 第5层失败归因标注）消费，需保证两侧词表引用版本一致 |
| **G21(OBS-005) ← G22(SEC-009)** | 告警层的 Kill Switch 联动强依赖 SEC-009 状态机先冻结，这是 OBS 侧唯一指向 SEC 侧 L3 组件的依赖，建议 SEC-009 核心状态机提前到 L2 阶段完成 |
| **G09(RT-005) ↔ G18(REL-004)** | Checkpoint Protocol 的保留策略扩展字段（`expires_at`）需要和 REL-004 的四类检查点分类同步设计 |
| **G19(REL-009 故障注入) ↔ G20(HAR-006 契约测试)** | 两者都提到"攻击回放"场景，REL/HAR 报告已明确建议：故障注入框架归属 G19，G20 的契约测试通过调用 G19 的框架执行，避免重复实现 |
| **G11(CTX-006) ↔ G12(MEM-003)** | Context Selector 与 Memory Retrieval 的桥接（L1/L2/L3 渐进披露共享模型）是 CTX 与 MEM 两条线中唯一的强耦合点 |
| **G03(CTX-002) → G06(EVA-001)** | EVA-001 Golden Dataset 的基准集来源之一是 CTX-002 定义的语言/规模分层，需在 G03 冻结后 G06 才能完整引用 |

## 七、后续建议

1. **冻结优先级最高的 4 个契约**：G01（RT-001 Schema）、G03（CTX-001/MEM-001）、G04（REL-001 症状词表）、G05（OBS-001 Span 属性）——这 4 个契约一旦确定，几乎所有下游组件都可以开始 mock 开发。
2. **G13（重试决策与恢复协调）是全局最大的单一风险点**：代码量最大、技术难度最高、被 G09/G18/G19/G23 四个组件直接依赖，建议拆 2 个子团队并提前锁定接口。
3. **SEC-009 Kill Switch 状态机建议提前到 M2 阶段**（而非默认的 L3 收口层），因为它同时阻塞 G21（告警联动）和 G22 本身，提前完成核心状态机可以解除下游等待。
4. **G20（Harness 平台）与 G23（评估收口层）的衔接是关键路径**：EVA-004 失败归因、EVA-005 回归流水线、EVA-006 发布门禁三者串联依赖 G20 的重放管线，建议 G20 的 HAR-001 核心生命周期管理提前完成。
