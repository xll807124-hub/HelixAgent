## 2. 目标、范围与边界

### 2.1 目标

建立多租户环境下的数据隔离、数据驻留、留存、删除和备份治理框架，确保：

1. **租户隔离**：组织间数据不泄露，计算资源共享但存储和密钥 per-tenant 隔离
2. **数据驻留**：数据按区域策略存储和处理，支持合规域内恢复
3. **数据留存**：分层留存策略，支持合规审计
4. **数据删除**：可验证的端到端删除能力，满足数据主体权利
5. **数据备份**：可度量的 RPO/RTO，支持灾难恢复

### 2.2 范围

**纳入范围**：
- Organization 和 Team 两级组织模型
- 计算资源共享（Pool 模式），存储和密钥 per-tenant 隔离
- 单主区域 + 区域钉扎抽象层
- ISO 27001 基线合规、SOC 2 Type II 审计目标、GDPR 法律底线
- 平台代管的每租户密钥（envelope encryption + per-tenant DEK/KEK）
- 结构化数据硬删除 + 向量嵌入软删除（每租户独立索引/集合）
- RPO ≤ 15 分钟，RTO ≤ 4 小时（标准）/ ≤ 1 小时（高敏层）

**不纳入范围**：
- Silo 模式（物理隔离）作为能力预留，MVP 不默认部署
- True CMEK（客户自持 KEK）放入 V2/企业版
- EU 独立部署（仅在 GDPR 强制入 scope 时开启）
- 深于 Org → Team 两级的组织嵌套
- 多主区域多活架构

### 2.3 组织模型

```
Organization（组织）
├── Organization Admin（组织管理员）
├── Organization Settings（组织级配置）
│   ├── Identity Provider（身份提供者）
│   ├── Org-wide Policies（组织级策略）
│   └── Billing（计费）
└── Teams（团队）
    ├── Team A
    │   ├── Team Admin（团队管理员）
    │   ├── Members（成员）
    │   └── Team Settings（团队级配置）
    │       ├── Isolation Mode（隔离模式）
    │       ├── Region Policy（区域策略）
    │       └── Retention Policy（留存策略）
    └── Team B
        └── ...
```

**关键原则**：
- Organization 是计费、合规和顶级策略的边界
- Team 是资源隔离、成员管理和数据治理的边界
- 数据隔离发生在 Team 级别（`team_id`）
- 审计日志在 Organization 级别聚合

## 4. 核心设计决策

### 4.1 决策记录

| 决策点 | 候选方案 | 最终选择 | 理由 |
|--------|---------|---------|------|
| **隔离模式** | Pool-only / Silo-only / 混合 | 计算 Pool + 存储/密钥 per-tenant | 平衡安全与成本；Silo 作为能力预留 |
| **组织模型** | 单一租户 / 两级嵌套 / 多级 | Org → Team 两级 | 满足企业需求，避免过度复杂性 |
| **数据驻留** | 多活 / 单主区域 / 区域钉扎 | MVP 单主区域 + 区域钉扎抽象层 | EU 独立部署非多活；按需扩展 |
| **向量嵌入删除** | 硬删除 / 软删除 / 禁用 | 软删除 + 每租户独立索引/集合 | 换取可验证的整集删除能力 |
| **备份 SLA** | 多种目标 | RPO ≤ 15min / RTO ≤ 4h（标准）/ 1h（高敏） | 满足企业需求；同合规域内跨区域恢复 |
| **合规框架** | 单一框架 / 多框架分层 | ISO 27001 → SOC 2 → GDPR | 按优先级渐进满足 |
| **CMEK** | 不支持 / 平台代管 / 客户自持 | MVP 平台代管 per-tenant；模型预留 true CMEK | MVP 简化实现；V2 支持客户自持 |
| **删除权限** | 单一权限 / 分层权限 | 租户管理员 + 法务/合规 + 用户 DSAR | 平衡自助与管控 |

## 5. 租户隔离设计

### 5.1 隔离架构

```
┌─────────────────────────────────────────────────────────────────────┐
│                        计算层（Pool 模式）                            │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐                   │
│  │  Worker A  │  │  Worker B  │  │  Worker C  │  ← 共享计算资源    │
│  │ (Team A)   │  │ (Team B)   │  │ (Team A)   │                   │
│  └─────────────┘  └─────────────┘  └─────────────┘                   │
└─────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                        存储层（Per-Team 隔离）                       │
│  ┌─────────────────┐          ┌─────────────────┐                    │
│  │  Team A Storage │          │  Team B Storage │                    │
│  │  - Database     │          │  - Database     │                    │
│  │  - Object Store │          │  - Object Store │                    │
│  │  - Cache        │          │  - Cache        │                    │
│  │  - Vector Index  │          │  - Vector Index │                    │
│  └─────────────────┘          └─────────────────┘                    │
└─────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                        密钥层（Per-Team 隔离）                        │
│  ┌─────────────────┐          ┌─────────────────┐                    │
│  │  Team A KEK/DEK │          │  Team B KEK/DEK │                    │
│  │  (Envelope Enc) │          │  (Envelope Enc) │                    │
│  └─────────────────┘          └─────────────────┘                    │
└─────────────────────────────────────────────────────────────────────┘
```

### 5.2 租户标识传播

**端到端传播链路**：

```
[API 请求]
    │
    ▼
[API Gateway: 提取 team_id from JWT/Header]
    │
    ▼
[TraceContext: team_id, org_id 注入]
    │
    ▼
[AI Gateway: 区域路由 + 策略决策]
    │
    ▼
[Worker: 执行任务]
    │
    ▼
[存储层: team_id 分区 + ABAC 校验]
    │
    ▼
[审计日志: team_id 关联记录]
```

**标识来源优先级**：
1. JWT Token 中的 `team_id` claim（可信来源）
2. HTTP Header `X-Team-Id`（经 API Gateway 验证后使用）
3. 禁止从客户端请求体提取租户标识

### 5.3 存储隔离设计

| 存储类型 | 隔离机制 | 实现方式 |
|---------|---------|---------|
| **PostgreSQL** | Schema 隔离 | 每个 Team 独立 schema，`team_id` 列 + 行级安全策略 |
| **对象存储** | 前缀隔离 | `org/{org_id}/team/{team_id}/...` 路径前缀 |
| **Redis 缓存** | Key 前缀隔离 | `tenant:{org_id}:team:{team_id}:...` Key 模式 |
| **向量数据库** | 独立集合 | 每个 Team 独立 Collection/Index，支持整集删除 |
| **配置存储** | Namespace 隔离 | `org:{org_id}/team:{team_id}/...` Namespace |

### 5.4 密钥隔离设计（Envelope Encryption）

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Envelope Encryption 架构                         │
│                                                                     │
│  ┌──────────────┐      ┌──────────────┐      ┌──────────────┐    │
│  │  Team A DEK  │      │  Team B DEK  │      │  Team N DEK  │    │
│  │  (数据密钥)  │      │  (数据密钥)  │      │  (数据密钥)  │    │
│  └──────┬───────┘      └──────┬───────┘      └──────┬───────┘    │
│         │ encrypts            │ encrypts             │ encrypts   │
│         ▼                     ▼                      ▼            │
│  ┌──────────────┐      ┌──────────────┐      ┌──────────────┐    │
│  │  Team A KEK  │      │  Team B KEK  │      │  Team N KEK  │    │
│  │  (密钥密钥)  │      │  (密钥密钥)  │      │  (密钥密钥)  │    │
│  └──────┬───────┘      └──────┬───────┘      └──────┬───────┘    │
│         │ wraps                │ wraps                │ wraps      │
│         └──────────────────────┼──────────────────────┘           │
│                                ▼                                    │
│                    ┌──────────────────────┐                        │
│                    │  Master Key (KMS)   │                        │
│                    │  平台级密钥管理器    │                        │
│                    └──────────────────────┘                        │
└─────────────────────────────────────────────────────────────────────┘
```

**密钥层次**：
1. **Master Key**（KMS）：平台级根密钥，由平台管理
2. **Team KEK**（Key Encryption Key）：每个 Team 独立，由 Master Key 加密保护
3. **Team DEK**（Data Encryption Key）：每个 Team 独立，用于加密实际数据

**MVP 限制**：
- KEK/DEK 由平台代管，存储在平台 KMS
- True CMEK（客户自持 KEK）放入 V2/企业版
- 数据模型预留 `customer_managed_key_id` 字段

### 5.5 隔离验证

**自动化隔离测试**：
| 测试场景 | 预期结果 | 失败处理 |
|---------|---------|---------|
| Team A 用户尝试访问 Team B 代码 | 返回 403 Forbidden | 触发安全告警 |
| 跨 Team JOIN 查询 | 返回空结果 | 触发安全告警 |
| Team A 用户尝试访问 Team B 任务 | 返回 404 或 403 | 触发安全告警 |
| 缓存读取 Team A 数据时使用 Team B Key | 解密失败 | 触发安全告警 |

**持续监控**：
- 跨租户访问模式异常检测
- 隔离策略违规实时告警
- 隔离覆盖率指标上报

### 6.2 区域策略配置

**区域类型**：
| 类型 | 说明 | 适用场景 |
|------|------|---------|
| **Single Primary** | 单主区域，不允许跨区域 | MVP 默认、GDPR 非强制客户 |
| **Single Primary + Disaster Recovery** | 主区域 + 同合规域备份 | 标准 SLA 客户 |
| **Multi-Region Active** | 多区域多活 | V2 高可用场景（当前不实现） |

**区域扩展路径**：
1. MVP：US-East-1 单主区域
2. V1.x：EU-West-1 独立部署（GDPR 强制时）
3. V2：CN-North-1 独立部署

### 6.3 区域验证与强制

**写入时验证**：
```
1. 解析请求的 team_id
2. 查询 TenantRegionPolicy
3. 验证目标存储区域在 allowed_regions 中
4. 如违规：拒绝写入 + 触发告警 + 记录审计
5. 如合规：继续写入 + 记录区域标签
```

**跨区域传输控制**：
- 默认拒绝跨区域数据传输
- 例外需要安全团队审批
- 所有跨区域传输记录审计日志

### 6.4 EU 区域特殊处理

**GDPR 强制时**：
- Team 配置 `region_policy: "EU_ONLY"`
- 创建独立的 EU 部署环境（不是多活，是独立部署）
- 所有推理、存储、备份都在 EU 区域内
- 数据不得传输到 EU 外的任何服务

## 7. 数据留存设计

### 7.1 分层留存策略

```
┌─────────────────────────────────────────────────────────────────────┐
│                         分层留存架构                                 │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │                     热存储层 (Hot)                          │    │
│  │  - 最近 30 天                                              │    │
│  │  - 支持快速查询和分析                                       │    │
│  │  - 全量审计日志                                            │    │
│  └─────────────────────────────────────────────────────────────┘    │
│                                │                                    │
│                                ▼ (30 天后自动迁移)                   │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │                     冷存储层 (Cold)                         │    │
│  │  - 31-180 天                                               │    │
│  │  - 低成本存储                                              │    │
│  │  - 有限查询支持                                            │    │
│  │  - 审计日志                                              │    │
│  └─────────────────────────────────────────────────────────────┘    │
│                                │                                    │
│                                ▼ (180 天后)                         │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │                     合规保留层 (Compliance)                  │    │
│  │  - 按需保留（法律/合规要求）                                │    │
│  │  - 不可变存储                                              │    │
│  │  - 需要审批才能删除                                        │    │
│  └─────────────────────────────────────────────────────────────┘    │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 7.2 留存策略配置

**平台默认配置**：
| 数据类型 | 热存储 | 冷存储 | 合规保留 | 说明 |
|---------|-------|-------|---------|------|
| 任务日志 | 30 天 | 180 天 | 按需 | 默认覆盖 |
| 审计日志 | 30 天 | 180 天 | 按需 | 不可删除 |
| 代码变更 | - | - | 按需 | 绑定 Git 仓库策略 |
| 代码索引 | 30 天 | 90 天 | 不保留 | 可重建 |
| 记忆数据 | 90 天 | 不保留 | 不保留 | MEM 模块控制 |

**组织级覆盖**：
- 管理员可配置更严格的留存策略（缩短保留期）
- 延长保留期需要合规团队审批
- 所有变更记录审计日志

### 7.3 留存执行

**自动过期处理**：
1. 每日扫描热存储中的过期数据
2. 执行软删除（标记为 deleted）
3. 移动到冷存储层
4. 超过冷存储期后，执行物理删除（需审批）

**合规保留触发**：
- 法律调查保留：直到法律团队释放
- 审计保留：直到审计完成
- 合同保留：按合同期限

## 8. 数据删除设计

### 8.1 删除触发与权限

| 触发原因 | 发起人 | 审批要求 | 冷静期 | 处理方式 |
|---------|--------|---------|-------|---------|
| 租户管理员自助删除 | 租户管理员 | 双人复核 | 24 小时 | 软删除 + 备份 |
| 法务/合规强制删除 | 法务/合规 | 无需冷静期 | - | 硬删除 |
| 个人用户 DSAR | 用户本人 | 无需冷静期 | - | 硬删除（个人数据） |
| 平台清理过期数据 | 系统 | 自动执行 | - | 按留存策略 |
| 合同终止删除 | 管理员 | 合规审批 | 30 天 | 完整删除 |

### 8.3 向量嵌入删除策略

**每租户独立索引/集合**：
- 每个 Team 拥有独立的向量 Collection/Index
- 删除时直接删除整个 Collection/Index
- 支持可验证的整集删除能力

**删除保证**：
| 删除类型 | 保证级别 | 说明 |
|---------|---------|------|
| 结构化数据 | 可完全验证 | 数据库硬删除，无残留 |
| 向量嵌入 | 整集删除 | 删除整个 Collection，向量数据库不保留 |
| 缓存 | 完全删除 | Redis 立即删除 |
| 临时文件 | 完全删除 | 立即清理 |
| 备份数据 | 下一备份周期删除 | 备份中保留到下一备份覆盖 |

### 9.3 恢复目标

**RPO（Recovery Point Objective）**：
- **标准层**：≤ 15 分钟（通过 PITR 和实时复制实现）
- **高敏/付费层**：≤ 5 分钟（增强复制频率）

**RTO（Recovery Time Objective）**：
- **标准层**：≤ 4 小时（从备份恢复到服务可用）
- **高敏/付费层**：≤ 1 小时（预置恢复环境 + 自动化恢复）

### 9.4 恢复验证

**定期恢复演练**：
| 演练类型 | 频率 | 内容 |
|---------|------|------|
| 组件级恢复 | 每月 | 单个组件（数据库、存储）恢复测试 |
| 全系统恢复 | 每季度 | 完整环境恢复演练 |
| 隔离验证恢复 | 每季度 | 恢复后验证租户隔离仍然有效 |
| RTO 达标测试 | 每半年 | 验证实际 RTO 满足 SLA |

**恢复检查清单**：
- [ ] 数据库完整性验证
- [ ] 对象存储数据完整性验证
- [ ] 向量数据库索引完整性验证
- [ ] 租户隔离有效性验证
- [ ] 加密密钥可用性验证
- [ ] 审计日志连续性验证

- 支持客户自持 KEK（Bring Your Own Key）
- 客户 KEK 存储在客户自己的 KMS
- 平台不存储客户 KEK 明文

## 16. 版本与演进

### 16.1 MVP 范围（V1.0）

**已实现**：
- 计算 Pool + 存储/密钥 per-team 隔离
- Org → Team 两级组织模型
- US 单主区域 + 区域钉扎抽象层
- 平台代管的 per-team DEK/KEK（含 CMEK 字段预留）
- 30 天热存储 + 180 天冷存储
- 结构化数据硬删除 + 向量嵌入整集删除
- RPO ≤ 15 分钟，RTO ≤ 4 小时（标准）/ ≤ 1 小时（高敏）
- ISO 27001 基线覆盖

**暂不实现**：
- Silo 模式（物理隔离）
- True CMEK（客户自持 KEK）
- EU 独立部署
- SOC 2 Type II 认证
- 多主区域多活

### 16.2 演进路径

**V1.x**：
- EU 独立部署支持（GDPR 强制时）
- Silo 模式支持（高敏感客户）
- SOC 2 Type II 认证

**V2.0**：
- True CMEK（客户自持 KEK）
- 多主区域多活
- 高级合规功能（详细 DPIA）

## 17. 待确认问题

以下问题已在方案中明确处理：

1. ✅ **隔离模式**：计算 Pool + 存储/密钥 per-team 隔离，Silo 作为能力预留
2. ✅ **组织模型**：Org → Team 两级，不做更深嵌套
3. ✅ **数据驻留**：MVP 单主区域 + 区域钉扎抽象层；EU 独立部署
4. ✅ **向量嵌入删除**：软删除 + 每租户独立索引/集合
5. ✅ **备份 SLA**：RPO ≤ 15 分钟，RTO ≤ 4 小时（标准）/ ≤ 1 小时（高敏）
6. ✅ **合规框架**：ISO 27001 基线 → SOC 2 Type II → GDPR 法律底线
7. ✅ **CMEK**：平台代管 per-team DEK/KEK，模型预留 true CMEK
8. ✅ **删除权限**：租户管理员自助 + 冷静期 + 双人复核；法务/合规强制删除权；用户 DSAR
