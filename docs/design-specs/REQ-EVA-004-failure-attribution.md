## 1. 需求定义

### 1.1 核心目标

建立可验证的失败归因体系，实现从"任务是否成功"到"失败根因在哪里、为什么"的诊断能力升级。该体系必须满足以下约束：

1. **反事实可验证**：根因判定必须通过最小干预重放验证，不是"相关性排序"
2. **分类有效性可证明**：通过双人盲标Cohen's κ验证，κ < 0.7的类别必须合并
3. **定位指标分层报告**：top-1/3/MRR、首错步命中率、首错步偏移距离，禁止用均值掩盖尾部类
4. **约束必须可判定**：每条约束必须附带可判定的checker，不能只有自然语言描述
5. **校准闭环**：抽样方案版本化，被审样本准确率反向校准置信度

### 1.2 设计目标

| 目标维度 | 具体目标 |
|---------|---------|
| 归因覆盖率 | 失败任务归因率 ≥ 95% |
| 根因定位准确率 | top-1准确率 ≥ 70%（复合门槛，定义见§6.4） |
| 分类一致性 | Cohen's κ ≥ 0.7（双人盲标） |
| 置信度校准 | 置信度与实际准确率相关性 ≥ 0.7 |
| 人工审核比例 | ≤ 15%（由分层抽样预算推导） |
| 证据链完整性 | 每条归因包含 ≥ 3条证据 |

### 1.3 用户价值

| 使用方 | 价值 |
|-------|-----|
| ML工程师 | 获得per-component失败分布+可操作改进建议 |
| 评估工程师 | 获得evidence链+置信度，支持人工复核 |
| 发布经理 | 获得按根因分布的门禁报告 |
| 安全工程师 | 获得独立的安全失败归因分类 |
| SRE工程师 | 获得生产故障归因报告，支持复盘 |

## 4. 核心设计：反事实验证作为判定条件

### 4.1 根因的严格定义

**行业问题**：规则引擎+LLM-as-Judge产出的是"相关性排序"——哪一步看起来最像错的。但这不等于根因。

**本设计定义**：

> **根因（Root Cause）**：在失败轨迹中，通过最小干预重放验证后，能够导致结果发生改变的那一步。

**判定条件**：

```
候选根因必须同时满足：
1. 相关性条件：该步骤与失败结果存在语义关联
2. 因果条件：对该步骤进行最小干预（注入正确观察/约束/工具结果），重放后任务收敛成功
3. 最小性条件：移除该步骤后，失败仍然发生
```

### 4.2 最小干预重放验证流程

```
候选根因步骤（top-k）
    ↓
[最小干预构建]
- 仅修改该步骤的输入/输出/约束
- 保持其他所有步骤不变
    ↓
[确定性重放执行]
- 复用Harness的重放管线
- 执行至收敛或最大步数
    ↓
[结果判定]
- 收敛成功 → 升级为确认根因
- 未能收敛 → 降级为"相关步骤"
```

**成本控制**：
- 只在top-k候选（k=5）上执行
- 复用Harness的确定性重放管线
- 超时或资源超限自动终止

### 4.3 判定结果类型

| 判定结果 | 定义 | 置信度调整 |
|---------|------|-----------|
| CONFIRMED_ROOT_CAUSE | 通过反事实验证 | +0.1 |
| RELATED_STEP | 相关但非根因 | 维持原置信度 |
| UNCONFIRMED | 反事实验证失败 | 降级为0.5以下 |
| INCONCLUSIVE | 无法完成验证 | 标记need_review |

## 5. 三维正交分类体系

### 5.1 分类维度定义

**第一维：症状（Symptom）**
- 来源：`REQ-REL-001` MVP症状词表
- 定义：可直接观测的失败表现
- 示例：`TIMEOUT`、`TEST_FAILURE`、`TOOL_ERROR`
- 状态：**MVP已固化**

**第二维：阶段（Phase）**
- 来源：基于项目架构定义的执行阶段
- 定义：失败发生在哪个执行逻辑阶段
- 分类：

| 阶段代码 | 名称 | 说明 |
|---------|------|------|
| CONTEXT_LOADING | 上下文加载 | 加载代码、符号、依赖 |
| PLANNING | 规划 | 生成执行计划 |
| TOOL_SELECTION | 工具选择 | 选择要使用的工具 |
| TOOL_EXECUTION | 工具执行 | 执行工具调用 |
| REASONING | 推理 | 逻辑推理和决策 |
| OUTPUT_GENERATION | 输出生成 | 生成代码/文本 |
| VALIDATION | 验证 | 运行测试、lint |
| COORDINATION | 协调 | Worker间协作 |

**第三维：根因类别（Root Cause）**
- 来源：融合MAST + AgentRx + 项目REL-001
- 定义：导致失败的本质原因
- 详细分类见§5.2

### 5.2 根因类别详细定义

```
A. 认知与规划错误（Cognitive & Planning）
   A1. False Premise（虚假前提）：基于未验证的假设行动
       - 定义：Agent对任务或环境做出了未经验证的假设
       - 验证：对假设进行断言，失败则触发
       - 优先级：P0（占认知错误主体）
   
   A2. Specification Neglect（规范忽视）：忽略任务要求或约束
       - 定义：Agent遗漏或误解了任务描述中的关键要求
       - 验证：对比任务描述与实际执行
       - 优先级：P0
   
   A3. Reasoning Error（推理错误）：逻辑推理链断裂
       - 定义：推理步骤之间存在逻辑矛盾或跳跃
       - 验证：检查推理链一致性
       - 优先级：P1
   
   A4. Planning Failure（规划失败）：无法生成有效计划
       - 定义：无法将任务分解为可执行步骤
       - 验证：检查计划完整性
       - 优先级：P2

B. 知识与理解错误（Knowledge & Understanding）
   B1. Misunderstanding（误解）：错误理解任务意图
   B2. Knowledge Gap（知识缺口）：缺少必要知识
   B3. Context Insufficient（上下文不足）：未获取足够上下文

C. 执行错误（Execution）
   C1. Tool Misuse（工具误用）：错误使用工具
   C2. Tool Failure（工具失败）：工具本身故障
   C3. Syntax Error（语法错误）：生成语法错误的代码
   C4. Incorrect Target（错误目标）：修改了错误的文件/函数

D. 协作错误（Coordination）
   D1. Communication Error（通信错误）：Worker间消息误解
   D2. Dependency Missing（依赖缺失）：缺少必要的前置输出
   D3. Conflict（冲突）：多个Worker产出冲突

E. 环境错误（Environment）
   E1. Resource Exhausted（资源耗尽）：内存、磁盘、时间耗尽
   E2. External Dependency Failure（外部依赖失败）：外部服务不可用
   E3. Environment Setup（环境配置）：环境初始化失败

F. 安全相关（Security）
   F1. Guardrails Triggered（护栏触发）：被安全策略阻止
   F2. Permission Denied（权限拒绝）：权限不足
   F3. Malicious Input Detected（恶意输入）：检测到恶意输入

G. 其他（Other）
   G1. Unknown（未知）：无法确定根因
   G2. Inconclusive（不确定）：证据不足
```

### 5.3 分类有效性验证

**双人盲标协议**：

```
1. 标注准备
   - 从归因集中随机抽取样本（N ≥ 50）
   - 分布：优秀15 + 差15 + 模糊20

2. 盲标执行
   - 两名标注者独立标注
   - 不知道对方标注结果
   - 不知道ground truth

3. 一致性计算
   - 计算Cohen's κ（根因类别）
   - κ < 0.7 → 该类别必须合并或重新定义
   - κ ≥ 0.7 → 类别有效

4. 结论固化
   - 标注指南版本与归因结果一起固化
   - 新增/修改类别必须重新κ验证
```

**"其他"桶上限**：
- 上限：≤ 10%
- 超限触发：分类学修订流程

## 6. 根因定位算法

### 6.1 定位目标

在长程轨迹中定位decisive root-cause step，支持分层指标报告。

### 6.2 分层指标定义

| 指标 | 定义 | 目标 |
|------|------|------|
| top-1准确率 | 预测的首位根因步骤 = 真实根因的比例 | ≥ 70% |
| top-3准确率 | 真实根因在前3候选中的比例 | ≥ 85% |
| MRR | Mean Reciprocal Rank | ≥ 0.75 |
| 首错步命中率 | 预测的首错步 = 真实首错步的比例 | ≥ 60% |
| 首错步偏移距离 | 预测步距真实首错步的平均步数差 | ≤ 10步 |
| **per-根因类最低值** | 每个根因类别的最差指标值 | 必须单独报告 |

**禁止行为**：
- ❌ 用均值掩盖尾部类
- ❌ 用整体MRR掩盖某类准确率低于0.5
- ✅ 必须报告per-根因类最低值

### 6.3 定位算法流程

```
步骤1：后向搜索（Backward Search）
   - 从轨迹末端向前搜索
   - 识别首个decisive step（导致后续失败的关键步骤）

步骤2：候选集生成
   - 使用约束违反检测生成top-k候选
   - 使用LLM-as-Judge生成语义排序候选
   - 合并去重，生成最终候选集

步骤3：反事实验证（核心）
   - 对top-3候选执行最小干预重放
   - 通过 → 升级为CONFIRMED_ROOT_CAUSE
   - 未通过 → 降级为RELATED_STEP

步骤4：最终定位
   - 选取引用最高的CONFIRMED步骤
   - 若无CONFIRMED步骤，选择置信度最高的候选
   - 记录定位过程和证据
```

### 6.4 复合门槛定义（准确率分母）

**定义**：

```
准确率分母 = 有效归因任务数 - INCONCLUSIVE任务数

有效归因任务：
- 归因完成（不论对错）
- 非归因超时、非资源耗尽导致无法归因

INCONCLUSIVE任务（排除）：
- 反事实验证超时
- 轨迹数据损坏
- 约束合成失败
```

**理由**：避免分母过大导致准确率虚高，必须在封存holdout集上测，不得在调参集上报数。

## 7. 约束合成与管理

### 7.1 约束必须可判定

**原则**：每条合成约束必须附带可判定的checker，否则等于让LLM给自己打分。

**可接受的checker类型**：

| checker类型 | 描述 | 示例 |
|------------|------|------|
| CODE_CHECKER | 可执行代码验证 | `assert file.contains("class Foo")` |
| REGEX_CHECKER | 正则表达式匹配 | `pattern: ^def \w+\(` |
| SCHEMA_CHECKER | JSON Schema验证 | `{"type": "object"}` |
| PROPERTY_CHECKER | 属性测试 | `len(symbol.references) > 0` |
| LLM_JUDGE_CHECKER | LLM判定（需额外校准） | `判断输出是否包含关键概念` |

**不可接受**：
- ❌ 纯自然语言描述
- ❌ "看起来合理"
- ❌ 无客观判据的语义判断

### 7.2 种子来源分级

约束来源必须分级，同对抗样本血缘逻辑：

| 等级 | 来源 | 血缘报告 | 占比上限 |
|------|------|---------|---------|
| L1 | 人审种子 | 单独报告 | 无上限 |
| L2 | 从失败轨迹归纳 | 单独报告 | ≤ 50% |
| L3 | 纯生成 | 单独报告 | ≤ 30% |

**理由**（同EVA-001防生成器指纹塌缩）：
- 纯生成约束会塌缩到同一分布
- 给出虚假高的"规则覆盖率"

### 7.3 约束保质期管理

**问题**：被修复或被模型吸收的约束继续留着，会给出虚高的"规则覆盖率"。

**保质期规则**：

```
约束元数据：
- generated_at: timestamp
- retired_at: timestamp（初始为null）
- source_level: L1 | L2 | L3
- constraint_type: CODE_CHECKER | REGEX_CHECKER | ...

保质期触发条件（满足任一）：
1. 该约束检测到的失败次数 ≥ 5，且成功率 > 95%
2. 该约束检测到的失败次数 = 0 持续60天
3. 对应根因类别已被修复

retired_at写入：
- 永久贬值
- 不参与规则覆盖率计算
- 近60天新增约束上的表现单独报告
```

## 8. 证据链设计

### 8.1 证据链结构

```typescript
EvidenceChain {
  // 约束违反记录
  constraint_violations: {
    constraint_id: string;
    constraint_type: CheckerType;
    violated_at_step: number;
    violation_details: string; // 违反的具体原因
    checker_result: CheckerResult; // 可判定的检查结果
  }[];
  
  // 相关步骤摘要
  relevant_steps: {
    step_index: number;
    step_type: "Action" | "Observation" | "Reasoning";
    summary: string;
    relevance_score: number; // 0-1
    is_root_cause_candidate: boolean;
  }[];
  
  // 外部证据
  external_evidence: {
    source: "LINTER" | "TEST" | "BUILD" | "SECURITY_SCAN";
    result: ExternalResult;
    attached_to_step: number;
  }[];
  
  // 反事实验证结果
  counterfactual_verification?: {
    candidate_step: number;
    intervention: string;
    replay_result: "CONVERGED" | "FAILED" | "TIMEOUT";
    evidence: string;
  }[];
  
  // 证据摘要
  summary: string; // 自然语言总结
}
```

### 8.2 证据完整性要求

| 证据类型 | 必需 | 说明 |
|---------|------|------|
| 约束违反 | 至少1条 | 如有违规必须记录 |
| 相关步骤 | 至少2条 | 首错步 + 关键中间步 |
| 外部证据 | 按需 | 测试失败/lint错误等 |
| 反事实验证 | top-k候选必填 | 验证结果必须记录 |

## 9. 置信度校准体系

### 9.1 置信度组成

```typescript
ConfidenceScore {
  // 证据完整性 (0-0.3)
  evidence_completeness: number;
  
  // 因果链强度 (0-0.4)
  causal_chain_strength: number;
  
  // 反事实验证结果 (0-0.2)
  counterfactual_result: number;
  
  // 分类器历史准确率 (0-0.1)
  classifier_accuracy: number;
  
  // 总分
  total: number; // 0-1
}
```

### 9.2 分层抽样预算推导

**人工审核比例不由固定比例控制，而由抽样预算推导**：

```
分层抽样设计：
1. 定义分层维度
   - 根因类别（A1-G2）
   - 置信度区间（<0.5 / 0.5-0.7 / 0.7-0.85 / >0.85）
   - 任务难度（来自EVA-001）

2. 分配抽样权重
   - 高风险类（A1/A2/F类）→ 高权重
   - 低置信度区间 → 高权重
   - 高难度任务 → 高权重

3. 推导审核数量
   - 总审核预算（人时/月）
   - 单样本审核时间
   - → 月度审核数量上限

4. 按权重分配
   - 每层按权重分配审核名额
   - 确保尾部类至少有最小审核量
```

### 9.3 闭环校准

**核心不变量**：抽样方案版本化，被审样本的实际准确率反向用于校准置信度。

```
校准流程：
1. 月度审核执行
2. 收集审核结果
3. 计算per-置信度区间的实际准确率
   - 置信度0.7-0.85区间的样本，实际准确率是多少？
4. 对比理论置信度 vs 实际准确率
   - 偏差 > 0.1 → 触发置信度重校准
5. 更新置信度计算公式参数
6. 新版本发布需离线回放验证
```

## 13. 处理逻辑与流程

### 13.1 归因分析主流程

```
步骤1：接收归因请求
   - 验证任务状态为FAILED
   - 加载关联的评分结果和失败事件
   - 记录归因开始时间

步骤2：轨迹预处理
   - 标准化为Trajectory IR
   - 识别Action-Observation对
   - 提取关键里程碑
   - 标记边界case

步骤3：三维分类
   - 症状匹配（使用REL-001检测器）
   - 阶段分析（基于架构定义）
   - 候选根因生成

步骤4：约束合成（启用checker）
   - 按种子来源分级生成约束
   - 执行checker验证
   - 记录约束违反

步骤5：候选排序
   - 约束违反分数
   - LLM语义分数
   - 合并生成top-k候选

步骤6：反事实验证（核心）
   - 对top-3候选执行最小干预重放
   - 通过 → CONFIRMED_ROOT_CAUSE
   - 未通过 → RELATED_STEP

步骤7：证据链构建
   - 收集约束违反记录
   - 收集相关步骤
   - 收集外部证据
   - 生成证据摘要

步骤8：置信度计算
   - 证据完整性评分
   - 因果链强度评分
   - 反事实验证评分
   - 分类器准确率评分

步骤9：人工审核路由
   - 检查是否触发审核条件
   - 分配到对应审核队列
   - 更新审核比例统计

步骤10：结果输出
   - 生成AttributionResult
   - 生成EvidenceChain
   - 更新下游契约状态
   - 触发EVA-005/EVA-006流程
```

### 13.2 人工审核触发条件

| 条件 | 优先级 | 处理方式 |
|------|--------|----------|
| LLM置信度 < 0.7 | P2 | 进入审核队列 |
| 分类为G1.Unknown | P0 | 必须审核 |
| 分类为G2.Inconclusive | P1 | 必须审核 |
| 涉及安全类别F1/F2/F3 | P0 | 安全工程师审核 |
| 根因类别κ < 0.7（近期样本） | P0 | 分类学修订 |
| 与历史分布差异 > 30% | P2 | 进入审核队列 |
| 反事实验证INCONCLUSIVE | P1 | 必须审核 |

## 18. 验收标准

### 18.1 功能验收

| 验收项 | 验收条件 | 验证方式 |
|--------|---------|---------|
| 三维分类覆盖 | 症状/阶段/根因全覆盖 | 单元测试 |
| 反事实验证 | top-3候选必须执行验证 | 集成测试 |
| 根因步骤定位 | top-1准确率 ≥ 70%（复合门槛） | holdout集验证 |
| 证据链完整性 | 每条归因包含 ≥ 3条证据 | 样本审核 |
| 约束checker | 所有约束必须附带可判定checker | Schema验证 |

### 18.2 质量验收

| 验收项 | 目标 | 验证方式 |
|--------|------|---------|
| 分类一致性 | Cohen's κ ≥ 0.7 | 双人盲标 |
| 置信度校准 | 相关性 ≥ 0.7 | 统计验证 |
| Verifier precision | ≥ 0.85 | holdout集 |
| Verifier recall | ≥ 0.80 | holdout集 |
| 人工审核比例 | ≤ 15% | 统计报告 |

### 18.3 性能验收

| 验收项 | 目标 |
|--------|------|
| 单任务归因延迟P95 | < 120秒 |
| 批量归因吞吐量 | ≥ 100任务/分钟 |

### 18.4 holdout集隔离要求

```
要求：
- 所有指标必须在封存holdout集上测
- 不得在调参集上报数
- holdout集per-version隔离
- exposure_count控制

验证流程：
1. 调参阶段：使用开发集
2. 调参冻结：封存调参集
3. holdout测试：在封存集上测所有指标
4. 发布：使用全新holdout集
```

## 19. 版本与演进考虑

### 19.1 版本管理

```
归因版本 = major.minor.patch
- major：分类体系变更（新增根因类别、合并类别）
```
