## 2. 目标、范围与问题分析

### 2.1 目标

建立统一的连接器注册与策略执行边界，使每次 MCP 工具调用都能绑定经过验证的连接器版本、单工具 Schema、发起用户、Agent/Worker、Task、目标资源、授权版本和 Trace。连接器身份、用户授权和组织策略相互独立：连接器认证不能代替用户授权，连接器信任等级不能扩大 SEC-002 授权上限，Policy Gateway 的批准不能覆盖平台强制拒绝。

### 2.2 原需求缺口

原待办只列出连接器身份、权限、Schema 和审计，未明确：协议版本和认证基线、信任等级、签名要求、连接器/工具权限粒度、来源策略、恶意服务器和 SSRF 防护、调用审批、凭据托管、配置变更与 TOCTOU、配额、异常降级及可验证验收。这些缺口可能造成连接器身份冒用、工具清单被替换、权限范围过大、凭据泄漏、网络越界和审计无法归因。

### 2.3 范围

包含连接器注册与生命周期；远程 HTTP MCP 的授权基线；API Key 过渡适配器；连接器与工具级身份/授权；Schema 签名、内容摘要和版本；信任等级 L1-L4；平台级强制全局黑名单与组织级可选白名单；按信任等级计权的组织配额；SEC-002/003/005/006/008/009、HAR-005 与 Runtime 审计/Trace 的概念集成；异常处理、可观测性、评估和验收。

MVP 不规定具体数据库 Schema、序列化格式、服务端协议实现细节、特定 CA/PKI 厂商、特定配额数值、参数级语义授权或完整行为异常检测。参数级内容检查归 `REQ-SEC-006`；MCP 路由与适配归 `REQ-HAR-005`；基础工具调用契约归 `REQ-HAR-003`。

### 2.4 设计不变量

1. MCP 工具发现、授权和执行均不能绕开 Tool Harness/PEP；执行动作必须接受 Policy Gateway（SEC-003）确定性决策。
2. 有效权限是用户当前 SEC-002 授权、任务批准范围、组织策略、连接器信任等级上限、连接器策略、工具级策略及 SEC-003 决策的交集；任何一项拒绝或不确定均不得放宽。
3. 连接器身份只证明“哪个连接器端点/进程正在响应”，不证明其内容可信，也不授予其代表用户的权利。
4. MCP 工具定义及结果均是外部不可信数据；签名有效也只证明来源/完整性，不保证工具安全、无恶意或输出正确。
5. 工具 Schema 以单个工具为权限和版本治理单位；MVP 不作参数级授权。执行前必须确认当前工具定义与已批准摘要相符。
6. 平台全局黑名单不可由组织或用户覆盖；组织白名单可进一步限制，不可扩大平台允许范围。
7. API Key 仅作有迁移期限的兼容适配器，标记 `@deprecated`；不得成为新连接器默认路径或长期凭据存放方式。
8. 信任等级决定上限而非自动放行；较高等级仍须经过身份、权限、策略、网络和凭据校验。
9. 配置、端点、身份材料、传输、工具清单或签名身份发生安全相关变化时，旧批准不得被静默复用。
10. 注册、状态改变、策略决定和工具调用均关联组织、用户、Task、Worker、Action、connector/version、tool/schema version 与 Trace，并按 RT-008 规则脱敏与留存。

## 3. 公开依据与设计参考

研究访问日期：2026-09-23。下列为公开资料明确描述的能力；不据此推断厂商未公开的内部系统或实现。

### 3.1 MCP 官方授权与安全指南

**公开事实**：HTTP 传输的授权规范采用 OAuth 2.1 安全要求，包含资源元数据发现、PKCE、短期令牌、最小 scope 与受众校验；安全指南讨论 token passthrough、SSRF、同意和不可信工具/结果等风险。STDIO 的凭据处理与 HTTP 授权路径不同。  
**设计推断**：本平台以符合当前 MCP Authorization 规范的 OAuth 2.1 风格流程作为远程连接器首选；不同传输必须明确独立信任与凭据边界，不能把“支持 MCP”当作安全认证。

来源：[MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)、[MCP Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)。访问日期：2026-09-23。

### 3.2 GitHub Copilot

**公开事实**：企业管理策略可配置 MCP 服务器允许/拒绝规则；拒绝优先，多个策略来源可叠加收紧。GitHub 文档提醒已配置服务器可能自主使用其工具，并提供受限 GitHub MCP 访问方案。  
**设计推断**：平台强制黑名单应高于组织配置；服务器允许与工具授权分开，逐工具缩小可用面。

来源：[Enterprise managed settings](https://docs.github.com/en/copilot/reference/enterprise-managed-settings-reference)、[Configure MCP servers](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/configure-mcp-servers)。访问日期：2026-09-23。

### 3.3 Claude Code

**公开事实**：工具权限由宿主执行层强制，支持 deny/ask/allow 及执行前钩子；提示指令本身不能改变宿主权限。  
**设计推断**：连接器工具需在调用执行点强制授权，不能依赖模型自律或连接器自报权限。

来源：[Permissions](https://code.claude.com/docs/en/permissions)、[Hooks](https://code.claude.com/docs/en/hooks)。访问日期：2026-09-23。

### 3.4 OpenAI Codex

**公开事实**：MCP 服务器和单工具可配置审批模式；独立 Auto-review 只处理合资格的边界升级请求，不改变既有沙箱、文件或网络权限。  
**设计推断**：Auto-review 应作为 PDP 侧独立服务；PEP 只消费策略决定并执行，不兼任策略评估或权限扩张。

来源：[Codex Auto-review](https://developers.openai.com/codex/concepts/sandboxing/auto-review)、[Codex Configuration Reference](https://developers.openai.com/codex/config-reference)。访问日期：2026-09-23。

### 3.5 Cursor

**公开事实**：Cursor公开提供MCP服务器/工具控制、网络策略和沙箱配置；官方说明部分 allowlist 属便利控制而非绝对安全边界。2025年公开披露的 MCP 配置信任问题表明，首次批准后配置被修改而未重新确认可导致风险，厂商随后修复了变更后重新审批行为。  
**设计推断**：批准必须绑定规范化配置内容和工具 Schema 摘要，而非仅绑定文件名、服务器名或稳定 ID；强制控制必须在服务器端/PEP执行。

来源：[Cursor MCP](https://cursor.com/docs/mcp)、[Cursor permissions](https://cursor.com/docs/reference/permissions)、[Cursor sandbox](https://cursor.com/docs/reference/sandbox)、[Check Point MCPoison research](https://research.checkpoint.com/2025/cursor-vulnerability-mcpoison/)。访问日期：2026-09-23。

### 3.6 Microsoft Foundry

**公开事实**：连接器可采用用户 OAuth、托管身份或 Agent 身份；认证配置由连接管理，令牌面向下游资源受众；工具流量可经 AI Gateway 施加认证、速率、IP 与审计控制（部分能力注明预览限制）。  
**设计推断**：凭据获取应与模型和工具定义隔离，连接器需要明确身份模式及目标受众，网关策略和后端工具权限需同时存在。

来源：[Toolbox authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/tool-authentication)、[Agent identity](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)、[Tool governance](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/governance)。访问日期：2026-09-23。

### 3.7 KIMI Code

**公开事实**：支持MCP工具统一权限机制、按工具名规则控制和延迟发现；文档建议高风险工具保留人工审批，并警示宽泛通配规则及自动批准模式。  
**设计推断**：工具清单可以按需呈现以减少上下文负担，但候选工具应先经可信策略裁剪；延迟发现不应成为绕过登记的方式。

来源：[Kimi Code MCP](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/mcp.html)。访问日期：2026-09-23。

### 3.8 DeepSeek Harness

**公开事实**：公开的插件框架将工具注册与执行权限/沙箱区分，审批可为单次授权，缺少审批处理器时失败关闭。  
**设计推断**：对高风险或低信任连接器采用单次、动作绑定的审批，不能记忆为无限期授权。

来源：[DeepSeek Harness Permissions](https://deepseekdocs.com/en/docs/user-guide/permissions)、[MCP client reference](https://github.com/deepseek-ai/deepseek-harness/tree/master/packages/mcp/mcp-client)。访问日期：2026-09-23。

### 3.9 证据边界

上述资料支持授权、策略、网络、工具级审批及身份治理原则，但未公开足以直接复用的统一 L1-L4 连接器信任矩阵、签名强制等级或配额计权公式。本文的分级、配额和状态规则均是本项目设计决策，不归因于厂商事实。竞品能力随产品版本变化，实施前需再次核验官方文档。

## 4. 功能需求与治理模型

### 4.1 用户与场景

| 使用方 | 目标 |
|---|---|
| 组织管理员 | 登记连接器、选择身份方式、审查签名和工具、收紧组织白名单/配额并停用连接器 |
| 安全管理员 | 维护平台全局黑名单、信任等级判据、安全基线和事故封禁 |
| 任务发起用户 | 在自身授权范围内使用已批准连接器及工具，并对高风险操作完成审批 |
| Harness/PEP | 只向 Worker 暴露当前获准工具，并在每次执行前重新校验 |
| 独立 Auto-review（PDP侧） | 仅对 SEC-003 判定可自动审查的升级请求给出受限建议 |
| 凭据代理 | 按连接器身份、用户授权、批准范围和目标受众发放或代理短期凭据 |
| 安全运营/审计 | 追溯连接器版本、Schema变更、批准、调用、拒绝和撤销事件 |

### 4.2 输入与输出（概念层面）

登记输入包括：组织与登记主体、连接器稳定标识、传输类型、端点或本地运行来源、服务身份/认证方式、声明版本、发布者/来源证据、签名身份与签名材料、发现的工具名称和 Schema、拟申请的资源/动作范围、数据级别及网络需求。

治理输出包括：连接器状态、信任等级及证据、批准的传输/身份方式、已批准工具集合及各工具 Schema 摘要、资源/动作上限、网络目的地约束、凭据托管模式、配额占用、策略/授权版本、审批引用及审计关联。不得将凭据秘密、完整敏感参数或完整工具结果写入普通审计。

### 4.3 身份、签名与 Schema 绑定

1. 每个登记实例分配平台稳定的 connector identity；实例身份与发布者/组织、传输端点、认证主体分别记录，避免把显示名称作为身份凭据。
2. 远程 HTTP 连接器优先使用 MCP Authorization 规范中的 OAuth 2.1 风格授权。授权服务器发现、回调/状态校验、PKCE、资源受众绑定、短期令牌及最小 scope 遵循规范要求；禁止向 MCP 服务器透传本平台收到的上游访问令牌。
3. API Key adapter 只用于尚不能完成 OAuth 迁移的兼容场景，标记 `@deprecated`。密钥由 SEC-005 托管/注入，限制组织、连接器、工具和目标；禁止写入 Agent 上下文、普通配置、Trace 或日志。新连接器不得默认选择此方式。迁移期限和退出日由平台治理发布，不在本需求虚构日期。
4. STDIO 连接器按本地进程供应链与执行边界治理：命令来源、固定版本/摘要、环境变量最小化、沙箱配置及进程身份需登记；不把远程 HTTP OAuth 流程机械套用于 STDIO。
5. 注册时发现工具清单，对每个工具保存规范化工具名、描述/输入 Schema 的规范化摘要、服务器身份、连接器版本和时间。签名覆盖连接器清单及逐工具 Schema 摘要，验证签名链、签名者是否获准、有效期/撤销状态与摘要一致性。
6. MVP 要求发布方或受信任治理方提供可验证签名。签名缺失、未知密钥、签名失效或不匹配不得按可信等级自动激活；按 L3/L4 的受限方式处理，明确标记未验证并进入人工安全审查或仅隔离测试。对于无法取得合格签名的低影响连接器，可在 L3 限制范围内经双人批准使用，不得因此授予高风险工具、敏感资源、凭据自由访问或广域网络。
7. 每次发现/调用前确认被调用工具的 Schema 摘要仍与获批版本一致。新工具、Schema、描述、端点、命令、认证主体或签名者变化均生成新版本并使旧批准失效。相同名称不表示相同工具。
8. Schema 签名证明来源与完整性，不证明实现安全、工具结果真实或不存在提示注入；工具输出和说明仍是不可信内容，交由 SEC-006 及后续消费者处理。

### 4.4 L1-L4 信任等级及有效能力

等级由可验证证据评估，连接器不得自行声明最终等级。等级上调须由治理审批并保留证据；关键证据过期/失效自动降级或暂停。级别决定的是最大允许能力，不替代具体动作授权。

| 等级 | 判据摘要 | 工具权限与审批 | 网络边界 | 密钥托管 |
|---|---|---|---|---|
| **L1：平台托管/强验证** | 平台管理的连接器或经过安全审查的发布方；可验证签名、固定版本、完整工具清单与安全责任人；持续供应链管理 | 仅获批工具；低风险只读可依组织策略使用，写入/敏感/不可逆动作仍由 SEC-003 判定并按规则审批 | 仅登记端点或平台代理目的地；默认拒绝其他出站访问，域名/IP解析变化需防 SSRF | SEC-005 代理/短期身份；连接器运行面不暴露根凭据；用户委托凭据按最小 scope 和受众提供 |
| **L2：组织验证** | 组织选定且完成来源、签名、工具、权限和网络审查；版本固定、负责人明确 | 获批工具级授权；读操作可按策略执行，写入及高风险工具经 SEC-003 决策，必要时人工审批 | 仅组织白名单目的地，默认拒绝；需受控出口代理 | SEC-005 托管短期凭据；组织级密钥按连接器隔离，Agent 不持长期秘密 |
| **L3：受限/条件验证** | 外部或社区连接器，签名/供应链证据不足但经过明确评审；签名缺失只能在本级受限例外批准 | 默认禁用写/管理/不可逆工具；逐工具显式批准；敏感资源、高风险操作强制人工审批；参数级语义检查归 SEC-006 | 隔离运行，仅可访问精确目的地白名单；无任意互联网、私网或云元数据访问 | 优先无凭据/只读匿名；确需认证时仅 SEC-005 提供单任务、短时、窄 scope 代理凭据；禁止持有组织根密钥 |
| **L4：未验证/不可信** | 新登记、签名无法验证、来源/版本变化未复审、命中风险信号或被降级 | 不得用于生产任务；仅隔离测试/沙箱评估，工具调用需显式审批且无敏感数据；平台规则可完全拒绝 | 网络默认全拒；仅专用隔离评估环境按批准临时开放 | 不得注入生产凭据；仅使用合成数据和测试凭据，离开评估环境不可用 |

平台可对任一连接器强制更严限制。L1 不意味着无条件信任；所有等级仍受 SEC-002、SEC-003、SEC-006、SEC-008、SEC-009 和执行沙箱约束。证据矛盾、无法评级或状态服务不可用时，按更低等级处理；无法确认等级则按 L4。

### 4.5 双层来源准入与配额

**平台级全局黑名单（强制）**：覆盖已知恶意发布者、端点/域名/IP/证书/签名密钥/包摘要/工具特征等可治理标识。拒绝优先，组织不能例外放行。黑名单更新有版本、理由、证据、生效时间和审计记录；误报纠正走治理流程。

**组织级白名单（可选收紧）**：组织可限定允许的发布者、端点、传输类型、签名者和连接器类别；启用后不匹配者拒绝。组织白名单只能与平台准入范围取交集，不能覆盖全局黑名单。未配置组织白名单时，仍需满足平台基线及组织信任等级/审批策略。

不设置所有组织共享的硬性连接器数量上限；采用按组织配置的加权资源配额，限制连接器总风险/资源消耗。计权维度至少包含信任等级、启用状态、工具数量/暴露规模、网络/凭据能力和审计负载。高信任连接器权重较低但非零；L3/L4 权重更高，L4 主要占用隔离评估配额。具体权重、容量和超额阈值须根据平台资源与风险评估确定，不在需求设计阶段臆造数字。

配额达到告警阈值后提示管理员；超过配额时拒绝新增或上调能力，不自动停用已有安全关键连接器。配额例外须有期限、审批人、理由和审计。恶意/紧急事件的封禁通过全局黑名单或 SEC-009 Kill Switch，不依赖配额机制。

### 4.6 授权决策与工具调用流程

1. **发现前过滤**：HAR-005 请求可用能力时先检查平台全局黑名单、组织准入/白名单、连接器状态、信任等级及配额；未通过者不向模型暴露工具定义。
2. **工具清单同步**：连接器适配器以已登记身份连接端点，获取工具清单和 Schema；校验来源、认证主体、签名、版本和逐工具摘要。发现变化即进入待复审状态，撤下受影响工具，不在当前任务中静默更新。
3. **能力裁剪**：按 Worker 能力、用户 SEC-002 权限、任务批准范围、组织政策、L1-L4 上限和工具级 allow/deny 列表求交集；拒绝优先。只把获准工具名和必要 Schema 暴露给模型。
4. **形成 Action**：模型提出工具调用后，Harness 规范化连接器身份、工具版本、参数结构和资源引用；参数内容按敏感数据最小化原则提供给策略层，语义/注入检测依 SEC-006，不以模型自述作为授权事实。
5. **PDP 决策**：Policy Gateway 作为 PEP 消费确定性 PDP 决策。独立 Auto-review 服务部署在 PDP 侧，仅处理 SEC-003 标记为可升级的审批请求；其建议不得改变信任等级上限、绕过黑名单、扩大 RBAC/任务/网络/凭据范围或替代强制人工审批。
6. **凭据准备**：若目标工具需认证，向 SEC-005 提供已验证连接器和批准范围引用；SEC-005 独立验证授权，按连接器信任等级、工具、资源、用户、任务和受众发放短期凭据或代理请求。连接器不获得平台根凭据。
7. **执行前复核**：执行器在副作用前再次校验连接器状态、工具 Schema 摘要、身份、用户授权版本、策略/审批有效性、网络策略和 Kill Switch 状态。任一版本变化或状态不明均拒绝/暂停。
8. **执行与结果处理**：在 HAR-005/003 指定适配器与隔离执行边界中调用。输出标注连接器和工具来源、版本及信任等级，作为不可信结果交给 SEC-006/Context 控制；敏感输出按策略检测、脱敏或阻断。
9. **审计与撤销**：记录决策、执行结果、耗时、字节/调用量等最小必要证据；停用、撤销、全局封禁或 Kill Switch 时阻止新调用、使批准/缓存失效，并按 SEC-005 撤销相关凭据。

### 4.7 生命周期与状态

连接器生命周期概念状态：草稿、待验证、待审批、已批准/未激活、活动、待复审、受限、健康异常、暂停、撤销、过期。工具有独立发现/待审/批准/禁用状态；父连接器暂停/撤销时所有子工具立即不可用。

状态改变必须由有权限主体发起，校验合法迁移并产生 RT-003 事件。以下变化至少触发待复审并撤销旧工具许可：端点/命令/证书或身份主体变化、签名者变化、清单增删工具、工具名称或 Schema 摘要变化、传输/认证模式变化、信任证据到期、组织授权变化、全局黑名单命中。紧急封禁直接进入暂停/撤销，不等待常规审批。

连接器发现缓存只作性能优化，不能作授权事实源。缓存键包含组织、连接器身份/版本、工具/Schema 版本、信任等级、主体/任务、授权/策略版本和状态代次。撤销或变更无法确认传播时 fail-closed。

### 4.8 人类在环与产品交互

管理员在登记时能看到发布者与端点证据、传输/身份方式、逐工具说明和 Schema 摘要、要求权限、网络目的地、数据敏感级别、信任等级判定依据、配额权重及缺失证据；批准页面清楚区分连接器级授权与逐工具授权。

开发者在任务中只看到经权限裁剪的工具；首次使用、信任降级、Schema/身份/端点变化、高风险动作和组织策略要求均触发审批。审批针对明确用户/任务/连接器版本/工具/资源/动作及有效期，不能被后续参数或工具变更扩大。拒绝或超时不转为允许；审批人可要求补充信息、拒绝或批准限定范围。

运行中可按单工具、连接器、组织或平台范围暂停。界面和事件应显示原因类别、受影响任务、凭据撤销状态和恢复条件，不暴露秘密或其他租户连接器存在性。

### 4.9 异常与失败处理

| 场景 | 处理 |
|---|---|
| OAuth 发现、PKCE、资源受众或令牌校验失败 | 拒绝连接/调用；不回退到更宽松认证 |
| 仅有 API Key 的旧连接器 | 仅经兼容策略和明确期限例外运行；标记 `@deprecated`，短期托管并限制工具/资源；不允许新接入默认采用 |
| Schema 签名缺失/无效或摘要改变 | 禁止按原批准执行；撤下变更工具并转复审；允许符合 L3 条件的隔离/限权例外，不提升信任等级 |
| 平台全局黑名单命中 | 无条件拒绝并告警，组织无覆盖能力 |
| 组织白名单启用且无匹配 | 拒绝并返回不泄露内部目录的原因 |
| SSRF、DNS重绑定、私网/回环/链路本地/元数据地址 | 连接前及连接期间由受控出口执行目的地校验；解析变化、重定向或不确定时拒绝 |
| 连接器身份、证书或签名者变化 | 暂停/待复审，撤销旧批准与相关凭据 |
| RBAC、Policy Gateway、信任目录或黑名单服务不可用 | 受保护调用 fail-closed；不得使用过期允许缓存 |
| Auto-review 不可用、超时或输出无效 | 升级人工或拒绝，绝不自动放行 |
| SEC-005 不可用 | 需要凭据的调用拒绝/暂停；不从配置或模型上下文取备用密钥 |
| 连接器超时、协议错误或工具结果格式不符 | 按 HAR-005/REL 策略分类；安全/Schema错误不盲目重试，记录证据 |
| 审计持久化失败 | 高风险/有副作用调用暂停或拒绝；按 RT-008 和 SEC-003 处理，不静默放行 |
| 配额超额 | 拒绝新增或扩权请求，提示治理审批；不影响已有连接器的正常安全撤销 |
| Kill Switch 或组织紧急停用 | 阻断新 Action、失效许可、通知 SEC-005 撤销凭据并保留现场证据 |

### 4.10 权限、安全与合规边界

- SEC-002 是用户/组织/资源授权权威；本需求不另造可扩大权限的连接器 RBAC。
- SEC-003 PDP 产生 ALLOW/REQUIRE_APPROVAL/DENY；Policy Gateway 作为 PEP，在执行入口强制实施；独立 Auto-review 属于 PDP 侧且只对允许范围内的升级请求工作。
- SEC-005 是凭据签发与撤销权威；连接器治理只提供经批准的最小化授权上下文，不保存或暴露根凭据。
- SEC-006 对连接器描述、工具输入/输出和外部内容执行提示注入/恶意内容控制；Schema 参数级语义授权不纳入本 MVP。
- SEC-008 定义组织数据隔离、驻留、留存、删除和备份；本需求产生的数据均带组织归属并遵循其策略。
- SEC-009 定义全局/组织/连接器级 Kill Switch 后续事故流程；本需求提供可执行暂停、许可失效和凭据撤销联动点。
- HTTPS/TLS、端点/受众验证、SSRF防护、出口限制、凭据最小化和沙箱隔离纵深防御；证书指纹不能单独替代有效 TLS 身份验证。
- 审计遵循 RT-003/006/008；不得记录访问令牌、API Key、完整敏感参数、完整源码或不必要工具输出。审计访问需 RBAC 控制并脱敏。
- 本设计不构成 OAuth、MCP 或任何法规合规认证声明。

### 4.11 性能、成本与延迟

工具发现、签名验证和 Schema 规范化主要在登记/版本变更时进行；运行时复用经验证的摘要，但每次执行仍校验版本代次、状态、授权和策略有效性。可缓存静态元数据和已批准工具列表；不得缓存为越过撤销的许可。

OAuth 交互、审批等待、签名验证、工具执行和审计写入分别统计，不把人工等待计入同步授权延迟。审计可异步管线化，但安全关键调用必须获得可靠提交或受控暂挂语义。配额按工具数、调用量、网络和凭据风险计权，避免仅按连接器条数造成资源/风险失真。

具体吞吐、延迟 SLO、配额权重和容量阈值在实现基准及负载模型确认后制定；本设计不设未经测量的硬数值。

### 4.12 可观测性与评估

最低指标包括：按信任等级/传输/认证方式的登记与活动数；待审批和复审时长；工具暴露与调用分布；签名/Schema变化、黑名单命中、策略拒绝、越权尝试；OAuth成功/失败；连接延迟与错误类别；调用字节/次数；配额占用与例外；凭据签发/撤销关联；审计提交失败；停用到生效及撤销传播时延。

Trace 关联 connector_id、connector_version、tool_name、schema_digest、trust_level、decision_id、policy_version、credential reference（非凭据值）、Action、Task 和 Worker。Metric 标签禁止使用用户ID、原始路径、完整端点查询参数或高基数工具参数。

评估覆盖：恶意/未知签名、签名内容替换、工具新增/删除、Schema同名异参、DNS重绑定、SSRF、OAuth state/PKCE/受众错误、token passthrough、越权工具、跨组织访问、审批重放、缓存撤销、策略服务故障、审计故障、配额绕过、Auto-review越界及API Key迁移。按等级报告误放行/误拒绝；所有黑名单绕过、未授权副作用、凭据泄漏和 L4 生产调用均为阻断性缺陷。

### 4.14 依赖与接口边界

**上游与权威来源**：
- `REQ-RT-001/003/006/008`：共享主体/资源/运行实体、事件、Trace、审计查询/脱敏/留存。
- `REQ-SEC-001`：风险类别与数据分级。
- `REQ-SEC-002`：身份、租户、资源、操作授权及授权版本。
- `REQ-SEC-003`：PDP决策、审批与拒绝语义；独立 Auto-review 位于 PDP 侧，Gateway 为 PEP。
- `REQ-SEC-005`：凭据托管、短期签发和撤销。
- `REQ-SEC-006`：提示注入和恶意输入/输出检测。
- `REQ-SEC-008`：租户隔离、驻留、留存、删除与备份。
- `REQ-SEC-009`：Kill Switch 和事故响应。
- `REQ-HAR-003/005`：工具调用契约、MCP发现/路由、PEP强制执行。

**概念交互**：注册/变更提交；身份与签名验证；工具清单发现和逐工具Schema摘要；授权/审批判定；凭据申请；运行时调用；审计/Trace事件；暂停/撤销和缓存失效。具体API、数据库DDL、签名格式、OAuth客户端类型和策略引擎文法由对应协议/实现评审确定。

### 4.15 MVP 与版本演进

**MVP**：采用当前 MCP Authorization 规范版本评审后锁定的 OAuth 2.1 风格远程授权为首选；API Key 仅为标记 `@deprecated` 的过渡适配器；强制逐工具权限与 `tools/list` 裁剪；要求可验证签名并以 L1-L4 分级处置缺失/不合格签名；平台全局黑名单 + 可选组织白名单；信任等级决定工具、审批、网络和凭据能力上限；按等级与能力加权配额；SEC-002/003/005/006/008/009 和 HAR-005 集成；端到端审计与 fail-closed。

**后续候选**：Schema参数级细粒度授权（本期由 SEC-006 做内容/注入检测，不等同参数级授权）；更丰富的证明透明度/供应链证明；自动风险基线；可信连接器目录联邦；更精细的调用速率与成本配额；DPoP/发送方约束等强化方式。候选项需独立评审，不作为本 MVP 承诺。

**冻结条件**：确认MCP规范具体版本与传输支持矩阵；制定L1-L4证据清单、等级转换责任和签名例外审批；确定全局黑名单维护/申诉程序；确认组织配额计权、容量模型和例外审批；与SEC-002/003/005/006、HAR-005完成契约与权限交叉评审；完成OAuth/SSRF/Schema变更/撤销/审计故障测试设计。详细设计完成不表示实现或验证完成。

| 身份与认证 | 仅提出连接器身份 | 连接器、发布者、端点、工具版本分离；OAuth 2.1首选，API Key过渡弃用 | 明确可信主体和凭据责任 | MCP、Microsoft Foundry |
| 信任分级 | 未定义 | L1-L4决定工具、审批、网络和密钥托管上限 | 风险差异化，签名缺失可受限处理 | 本项目设计推断；行业分层治理实践 |
| Schema | 泛化提到Schema | 签名覆盖连接器清单和逐工具摘要，变更使批准失效 | 防篡改和TOCTOU，粒度到单工具 | MCP、Cursor公开案例 |
| 授权粒度 | 未明确 | MVP `tools/list`逐工具授权和暴露裁剪 | 最小权限、执行点强制 | GitHub、Codex、KIMI |
| PEP/PDP | 未定义 | 独立Auto-review在PDP侧，Policy Gateway为PEP | 防止审批器扩大执行边界 | Codex、SEC-003既有设计 |
| 来源准入 | 未定义 | 平台不可覆盖全局黑名单 + 组织可选白名单 | 平台底线与组织收紧并存 | GitHub企业策略 |
| 配额 | 未定义 | 不硬限数量，按信任等级/能力加权 | 对齐真实风险和资源消耗 | 本项目设计决策 |
| 网络/凭据 | 未定义 | SSRF出口控制、等级化网络边界与SEC-005短凭据 | 降低外传和密钥爆炸半径 | MCP、Foundry、Cursor |
| 审计/生命周期 | 仅提及审计 | 状态机、版本变更、调用、审批、撤销Trace全链路 | 可验证、可追责、可恢复 | Runtime合同与平台审计基线 |

## 6. 修改理由总结

本设计把抽象的“连接器身份、权限、Schema和审计”落为可强制执行的治理边界：连接器身份不等于用户授权，签名不等于安全结论，信任等级不等于自动放行。MCP OAuth 2.1 风格授权和弃用 API Key 降低长期秘密暴露；逐工具批准和 Schema 摘要绑定减少工具清单替换风险；全局黑名单与组织白名单形成明确策略优先级；等级化网络/凭据处理和加权配额控制低信任连接器的爆炸半径；PDP/PEP职责延续 SEC-003，审计与撤销则复用 Runtime、SEC-005 和 SEC-009，避免重复建立权威来源。

## 7. 对其它待办的影响

| 需求 | 影响与同步点 | 风险与缓解 |
|---|---|---|
| `REQ-HAR-005` | 路由需支持已登记连接器身份、逐工具发现/裁剪、版本固定、PEP前置校验和停用传播 | 路由绕过治理；AC测试覆盖发现、直接调用与缓存失效 |
| `REQ-HAR-003` | Tool Adapter需携带connector/tool/schema版本、来源和风险事实 | 契约差异；后续以统一工具调用契约对齐 |
| `REQ-SEC-002` | 复用用户/资源授权，不让连接器身份提权 | 服务身份与用户身份混淆；分别鉴权并取交集 |
| `REQ-SEC-003` | MCP工具类别/风险/审批进入PDP；独立Auto-review留在PDP侧，Gateway作为PEP | PEP重复判定；划定权威职责并做集成测试 |
| `REQ-SEC-005` | 支持OAuth/API Key兼容凭据托管及连接器、工具、受众/资源绑定撤销 | 凭据意外暴露；只由CDP托管/注入并测撤销 |
| `REQ-SEC-006` | 检查连接器描述、参数和工具输出中的恶意指令；不承担参数级授权 | 内容检测被误当权限判断；策略授权与内容检测保持分离 |
| `REQ-SEC-008` | 注册表、白名单、配额、审计按组织隔离并遵守驻留/删除规则 | 跨租户缓存/索引混淆；租户边界测试 |
| `REQ-SEC-009` | 增加连接器、工具、组织与平台范围停用及SEC-005撤销联动 | 在途调用竞态；执行前检查Kill Switch代次 |
| `REQ-OBS-001/002/003/004/006/007` | 纳入连接器审计事件、Trace关联、指标、脱敏和留存 | 高基数/敏感字段；低基数聚合、受控审计 |
| `REQ-EVA-001/003/005/006` | 纳入恶意MCP、Schema替换、授权绕过、SSRF与故障注入样本 | 数据集覆盖不足；按信任等级和工具类别分层 |

## 8. 待确认问题

下列事项可在形成 `v0.1-designed` 后通过跨模块冻结确认，不阻止本轮写入：

1. 实施时锁定的MCP Authorization规范版本及STDIO/HTTP传输的首批支持范围。
2. L1-L4证据目录、等级评审角色、复核周期与无签名L3例外的双人审批职责。
3. 平台全局黑名单数据源、紧急发布责任、误报申诉与恢复时限。
4. 组织可配置配额的计权权重、告警/阻断阈值、隔离评估容量及例外期限。
5. OAuth连接器是否支持用户委托与服务身份两种模式的MVP优先顺序，以及各工具的目标受众目录。
6. API Key adapter的迁移/退出日期及存量连接器兼容责任人。
7. 证书/Schema签名的信任根、签名格式、吊销信息来源与轮换流程。
8. `tools/list`工具描述变化是否一律重新审批，或允许经过治理的兼容性分类；默认安全行为是旧许可失效。

## 9. 设计决策记录

| 决策 | 基线 | 边界 |
|---|---|---|
| MCP授权 | OAuth 2.1风格 MCP Authorization 为远程首选；API Key `@deprecated` | 规范具体版本实施前确认；STDIO单独治理 |
| Schema签名 | MVP要求签名；缺失/不合格走分级受限放行而非默认全禁 | 不将签名视为安全或行为证明 |
| 信任等级 | L1-L4决定能力上限 | 仍须逐次用户授权与Policy决策 |
| 权限粒度 | MVP到单工具/`tools/list` | 参数级延后；SEC-006做内容安全，不等同授权 |
| Auto-review | 独立服务部署在PDP侧 | Gateway是PEP，只执行决定 |
| 连接器数量 | 配额而非全局硬性数量限制，按等级/能力加权 | 权重和容量待基准确认 |
| 准入名单 | 平台强制全局黑名单 + 组织可选白名单 | 组织配置只能收紧，不能覆盖黑名单 |
| 默认失败 | 关键身份、版本、策略、授权、审计不确定时fail-closed | 连接器可在隔离测试环境按明确例外评估 |
