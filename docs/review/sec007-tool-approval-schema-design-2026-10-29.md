## 2. 需求与实施前问题（基线记录）

依据：[需求分析报告](../需求分析报告.md)中的 SEC-007，以及 [REQ-SEC-007](../design-specs/REQ-SEC-007-mcp-connector-governance.md) §2.4、§4.3、§4.6～4.9。要求逐工具批准，定义或安全相关身份变化使旧批准失效；发现、调用和副作用前均复核。工具 Schema 签名、定义准入、用户/任务权限是不同层次。

要解决的问题：管理员批准过的是一个确定的工具定义，而不是一个可被替换的名称。发现缓存、同名工具、旧批准和等待凭据期间的检查结果，都不能让新定义绕过复审。

本轮核查发现：

| 位置 | 实施前行为 | 影响 |
|---|---|---|
| `ToolRegistry._approvals` | 按 `schema_digest` 全局存储；批准接口没有组织/连接器参数 | 无法证明批准属于当前组织和当前提供方 |
| `ToolSchema.compute_schema_digest` | 只计算工具名和已解析的输入 Schema | 描述、风险、能力及版本变化不使该摘要变化 |
| `ToolInputSchema` / MCP 解析 | 只保留部分顶层字段 | `minProperties` 等字段的变化可以在解析后消失，连 `compute_full_hash` 也无法识别 |
| `detect_schema_change` | 与全局同名工具历史比较，依据窄摘要 | 不是提供方自己的可信变更基线；描述变化会报告未变化 |
| 发现/执行入口 | 没有调用逐工具批准检查 | 有批准记录不等于批准门禁已经生效 |
| `ToolApproval.is_valid` | `now > valid_until` 才到期 | 到期时刻本身仍有效，边界需要明确修正 |
| 生命周期 | 已有 `PENDING_REVIEW` 及凭据失效联动 | 缺少清单变更触发和复审完成条件；`RESTRICTED → PENDING_REVIEW` 当前未允许 |

已用独立内存对象复现前述摘要、批准范围、解析丢失与到期边界；记录在[设计基线 JSON](./sec007-tool-approval-schema-baseline-2026-10-29.json)。没有调用外部服务或变更生产状态。这些探针不是新功能通过的测试报告。

## 3. 官方产品对标

访问日期：2026-10-29。只采用官方文档；公开行为与本项目设计选择分开表述。

| 产品/规范 | 官方公开行为 | 优点 | 本项目借鉴与规避 |
|---|---|---|---|
| [Cursor Run Modes](https://cursor.com/docs/agent/security/run-modes) | MCP 调用纳入运行模式；Allowlist 和 Auto-review 对待批准调用采用不同路径，后者可交给分类器判断 | 明确调用前的权限决策，减少重复操作负担 | 借鉴逐调用检查；本轮只做确定性的批准匹配，不开发分类器或默认全放行 |
| [Claude Code MCP](https://code.claude.com/docs/en/mcp#dynamic-tool-updates) | 收到 `list_changed` 后刷新工具；刷新失败时保留此前发现结果。项目服务器批准还受工作区信任约束 | 支持运行中变更，批准来源与仓库内容分离 | 借鉴变更触发刷新和可信批准来源；本项目已收到变更/失效信号后，旧清单仅作历史，不继续用于调用 |
| [MCP Tools 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) | 定义 `tools/list`、`tools/call`、清单变更通知及工具定义字段；不强制特定 UI；不可信服务器的 annotations 不能直接信任 | 协议提供发现和变更机制，客户端保留治理责任 | 通知不是批准；服务端自称只读、无风险不等于本平台授权。该版本仅作本次对标参考，不据此升级或冻结项目协议版本 |

设计结论：批准必须绑定实际提供方及完整定义，并在执行端强制检查。只靠名称白名单、客户端可见列表或描述中的“安全”声明不足以实现本需求。这个结论是本项目设计选择，不声称上述产品采用相同的摘要或存储结构。

## 4. 建议本轮范围

**目标：单进程内完成“定义登记 → 明确批准 → 发现/执行校验 → 变更失效 → 复审后受控恢复”的后端闭环。**

包含：

- 注册级逐工具定义准入，绑定组织、连接器身份/版本、完整定义摘要及当前代次。
- 未批准、已过期、已撤销或摘要不符时，从发现列表隐藏，并拒绝直接调用。
- 清单新增、删除、描述/Schema/风险/能力/版本改变时，使旧批准失效并触发当前连接器复审。
- 复用上项的生命周期停止、缓存代次及 SEC-005 撤销联动；凭据等待前后再次核对批准。
- 可信审批回调、最小审计、拒绝原因、并发保护、真实本地 HTTP 联调及全量验证。

本轮不包含：前端审批页面、新 HTTP 管理端点、完整 SEC-002/003 或 Auto-review、每次调用的用户/任务/资源审批工作流、发布方工具清单签名格式重构、远端通知订阅/分页/后台发现客户端、多实例传播、持久化迁移、真实外部凭据服务。

本轮接收现有可信适配层已取得的清单或变更/刷新失败信号；未观测到的远端变化不能宣称已经检测。批准只增加定义准入条件，不代替或扩大现有黑名单、组织策略、签名、环境、配额、凭据检查。完整调用授权仍按原需求作为剩余工作跟踪。

## 5. 设计方案

### 5.1 完整定义与批准范围

1. 保留完整原始 `inputSchema`；原始工具附加定义字段保真保留并参与定义摘要，不能悄悄丢弃后再声称定义相同。无法保真处理或不合法的输入拒绝登记。未知字段参与变更检测不等于实现了它的执行语义、权限或输出校验。
2. 增加有版本标识的 `definition_digest`：覆盖工具名、描述、完整输入 Schema、原始附加定义、平台风险/能力配置和工具版本；不包含登记时间、审计时间。固定规范化规则，键顺序变化不影响摘要；不自行推断数组重排或 Schema 改写是业务等价。非 JSON 值和 NaN/Infinity 等拒绝。
3. 原 `schema_digest` 保留历史兼容/诊断用途；新的批准门禁必须使用完整定义摘要，不能拿旧摘要冒充新版完整摘要。
4. 新批准作用域至少包括 `(org_id, connector_id, connector_revision, tool_name, definition_digest, manifest_generation)`，另有批准 ID/修订号、审批来源引用、审批人和有效期。连接器修订绑定实际配置与身份/签名者信息，不能只信任可不变的版本字符串。
5. 当前切片默认只允许组织匹配的登记连接器；没有显式跨组织授权契约时拒绝跨组织访问和批准查询。不能用 A 组织/A 连接器的批准替代 B 的批准。
6. 旧记录缺少范围或新版摘要时只作历史，不自动填组织、不自动批准现有工具。部署后需重新明确批准，测试中的合法调用也须通过受控批准夹具建立前提。

### 5.2 批准入口与审计

现有 ToolRegistry 继续保存工具与批准记录；新增或扩展薄编排层连接注册表、生命周期、批准授权回调和执行器，不另建 PDP。

- 批准入口使用可信调用方上下文和注入的授权校验回调。回调缺失、拒绝、异常、组织/审批范围不匹配均不签发有效批准。`approved_by` 或 `approval_type` 字符串不是授权证明。
- 提交批准时携带评审开始时的摘要、代次和审批来源引用；若等待审批期间工具改变，拒绝旧批准提交。原有双人/安全负责人等类型只在回调验证了对应依据后记录，不能靠标签宣称实现了真实审批流程。
- 有效期统一为 `now >= valid_until` 即失效，处理时区一致性；禁止空主体、空引用和已到期批准。未给到期时间沿用既有永久批准能力，但仍受版本、撤销和状态约束。
- 批准/复审完成的关键审计失败时不发布有效批准、不解除阻断。变更或撤销时即使审计失败，也维持已经生效的阻断，并记录可重试错误。
- 审计复用现有工具批准、Schema 变化和策略决策事件；只记录 ID、摘要、代次、动作和结果。不得记录凭据、完整敏感定义或跨组织内容。

### 5.3 发现与调用门禁

- `tools/list` 先检查每个提供方自己的批准，再进行现有能力裁剪和同名合并。未批准提供方不能贡献描述、Schema 或扩大参数集合；保留现有命名/合并契约。
- `tools/call` 在协议入口拒绝未批准目标，外部沿用不可用响应，避免区分其他组织的未知/未批准工具。
- v2 执行器也必须具备同一批准/定义权威引用；缺少装配则拒绝，不能通过直接调用执行器绕过协议入口。
- 调用方传入的工具快照与注册表当前定义不符时拒绝；不静默换成另一版本执行。凭据准备前捕获批准 ID/修订号、摘要和代次，等待后及扣配额/交给传输前复核。
- 批准撤销后再批准同一摘要，也不能使旧在途准备继续执行；用批准修订号和代次区分。被阻断调用不取新凭据、不扣配额、不发送新请求。
- 不承诺取消已经交给外部服务执行的请求；保留现有前置拒绝与执行期失败的错误码分层。

### 5.4 变更与复审

推荐本轮采用**连接器级复审**：一个工具的有效定义变化、清单增删、连接器配置/身份版本变化，就使该连接器当前一代批准失效。其他连接器及其他组织不受影响。

1. 首次登记只生成待批准工具，不自动批准；已登记的相同快照重复同步不改变代次。
2. 变更在同步入口先建立本地阻断、提升清单代次并撤销旧批准，再更新待审快照。所有登记/替换/批量同步/移除入口归入同一治理路径，不能用旧的写入口绕过。
3. 活动连接器进入 `PENDING_REVIEW`；为 `RESTRICTED` 增加同样的合法迁移。已暂停/撤销等不可调用状态不因变更被提升状态；保留待审标记和阻断。
4. 进入待复审复用已验收的凭据失效流程。撤销未完成、无适配器或直接 OAuth/Bearer 为 `unsupported` 时，复审批准也不能越过现有凭据恢复限制。
5. 所有摘要变化都需要复审。原 `breaking/safe` 分类仅作诊断，不能自动继承批准。无变化的重试幂等；部分清单、解析错误或已知变更后的刷新失败，不回退为“旧清单仍获批”。
6. 明确批准选定工具并确认当前清单复审完成后，才允许通过生命周期恢复闸门。未选定工具继续隐藏，不要求自动批准整个清单。
7. 直接 `activate/resume/transition_to` 也检查未完成复审，避免只改父状态绕过；签名、凭据、审计、生命周期原条件继续生效。
8. 审批/同步完成回调在提交前复核代次；并发停止、更新与恢复遵守统一锁顺序。网络撤销及外部授权回调不得在生命周期/缓存锁内等待。

### 5.5 接口草案与兼容性

以下为已确认设计；实施先定稿 [MCP API 文档](../api/sec-007-mcp-connector-governance-api.md)，再编码。

| 接口职责 | 必需输入/输出约束 |
|---|---|
| 登记/同步清单 | 可信组织与连接器、完整工具快照、预期清单代次、操作者；返回是否变化、当前代次、待审状态和凭据撤销摘要 |
| 签发/查询/撤销逐工具批准 | 组织、连接器及修订、工具、完整定义摘要、预期代次、审批来源和有效期；查询副本，无范围不返回有效批准 |
| 检查调用批准 | 当前连接器、提供方工具快照、组织；返回不可变的批准上下文或安全的拒绝类别；不发送凭据 |
| 执行前复核 | 比较批准修订号、清单代次、连接器修订及摘要；撤销、到期或不一致拒绝 |
| 标记待复审/完成复审 | 绑定当前清单摘要与代次，复用 LifecycleManager；明确选定可启用工具，缺失可信审批或撤销未完成不得恢复 |

内部旧调用点、测试夹具与 API 文档一并迁移。旧的无作用域批准函数不能继续成为执行授权入口；旧记录只作历史读取。原数据库 DDL 与 Runtime 实体/Event Schema 不在本轮修改范围，不声称实现了批准持久化恢复。

### 5.6 UI、依赖与实施顺序

本轮没有前端页面，UI Skill 及 UI 设计规范确认不适用；不把后端审批回调当作已经交付了用户审批界面。前端任务仍在手册原位置。

无计划新增生产依赖、环境密钥或服务；沿用现有环境和扫描工具。如后续实现确实需要新增受控依赖或共享契约变更，先说明并按规则确认。

实施顺序：接口契约 → 完整定义/范围化批准 → 变更与生命周期联动 → 协议及执行器门禁 → 联调/全量测试/安全扫描 → 交付待验收。
