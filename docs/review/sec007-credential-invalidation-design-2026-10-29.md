## 2. 问题与代码证据

[需求分析](../需求分析报告.md)要求短期、范围受限、任务绑定且可审计的凭据。[SEC-007](../design-specs/REQ-SEC-007-mcp-connector-governance.md) §4.7～4.8 / AC15 要求停用阻断新调用、缓存失效，并由 [SEC-005](../design-specs/REQ-SEC-005-credential-proxy.md) 负责受托管凭据撤销。

以下为实施前静态核查基线，保留以说明要解决的问题；当前实现与实测结果见第 9 节及测试报告：

1. `LifecycleManager.pause/revoke` 仅调用 `transition_to` 更新注册表状态，没有调用凭据失效接口。
2. `AuthorizationManager.revoke_credentials` 仅删除一个 `org:user:connector` 缓存键；不覆盖同连接器全部用户，不撤销 CDP 租约。
3. 缓存键用冒号拼接，新增连接器级清理不能依赖字符串前缀/后缀匹配；应使用明确的组织、用户和连接器边界。
4. `AuthorizationManager` 刷新完成后直接回填缓存；独立 `TokenManager` 也有相同回填行为。两者都没有停用代次检查。
5. v2 执行器通过 `asyncio.to_thread` 准备凭据，等待返回后只查当前可调用状态；暂停后快速恢复为 ACTIVE 时，旧操作可能继续，因此本切片需要代次检查。
6. `SEC005CredentialProxyClient` 丢弃签发结果的 `token_id`，只返回 token 和过期时间。CDP 已有 `revoke_token(token_id)`，但连接器适配层未保留对应关系。
7. CDP 当前 `_mint_token` 仍为示例实现，真实 Vault/外部 OAuth 服务未装配；调用 CDP 成功不等于已证明真实外部服务撤销。

主要涉及现有 `authorization/auth_manager.py`、`authorization/oauth_handler.py`、`authorization/credential_adapter.py`、`lifecycle/lifecycle_manager.py`、注册表、v2 执行器及其测试；不另建一套凭据权威。

## 4. 已批准范围与边界

**本次交付目标**：同一进程内，连接器暂停/撤销后所有关联凭据停止被平台使用，受托管凭据触发既有 SEC-005 撤销；旧刷新/签发结果不能使其重新可用，失败状态可追踪且不能被忽略。

覆盖 OAuth/Bearer 本地缓存、现有 SEC-005 派生凭据、已存在的 TokenManager 兼容路径，以及等待凭据期间的暂停/恢复竞态。既有生命周期转入不可调用状态时应用同一失效钩子，防止通过直接 `transition_to` 绕过。

本切片限定于已装配的组件和单进程调用链。直接 OAuth/Bearer 没有服务端撤销适配器时，清除本地使用副本并明确返回 `unsupported`，不声称完成远端撤销；真实 Vault/OAuth 提供商实现、跨实例 <5s 传播、重启后的持久化撤销队列、已发出的副作用撤回、组织停用/Kill Switch 和独立工具批准失效继续列为后续缺口。**本切片不会将 AC15 或 SEC-005 整体勾为完成。**

已确认的暂停语义：SEC-005 §6 的“任务暂停未撤销”允许现有凭据继续到 TTL；SEC-007 §4.7 对“连接器停用”要求许可/凭据失效。两者对象不同，按用户确认区分：

| 操作 | 推荐行为 |
|---|---|
| 普通任务暂停 | 保留现有 SEC-005 规则，本轮不改变 |
| 连接器暂停/撤销 | 清除所有关联用户缓存、提升失效代次、触发受托管凭据撤销 |
| 连接器恢复 | 先满足签名/生命周期条件及本地失效完整性；需要新授权或新签发，不能恢复旧副本 |
| 外部撤销失败、未装配或 unsupported | 连接器保持不可调用；提供明确状态供重试/人工处理，不自动绕过；本轮不增加风险豁免入口 |

本轮没有发现新的《执行手册》与《迭代规则》顺序冲突。上述暂停对象、外部撤销范围及失败恢复策略属于用户已确认的设计边界。已确认的文档优先级、正文顺序和测试门槛继续有效。

## 5. 设计方案与接口（2026-10-29 已批准实施）

### 5.1 失效流程

1. 校验连接器和组织范围、合法状态迁移。拒绝请求不暴露其他组织凭据；复用可信调用方上下文，不把本方法当作新增管理员认证入口。
2. 在同一进程的同步临界区内先标记不可调用，提升连接器凭据代次，再清除该连接器全部主体的缓存；不可因远端故障回滚为可调用。
3. SEC-005 适配器维护 `(org_id, connector_id) → token_id 集合`，只存撤销句柄和必要元数据；清理所有已登记派生租约，复用 CDP 的既有撤销接口。失败句柄保留用于重试，成功句柄删除。
4. 刷新、签发和缓存写入携带开始时的代次；返回后在锁内比较，过时代次不得回填或返回给执行器。迟到的新租约进入同一撤销流程，不能因已清空旧索引而遗漏。
5. 执行器在凭据等待前后核对同一代次，再在扣配额/交给传输前检查状态。即使期间发生暂停→恢复，也拒绝旧调用；新授权后由新请求重新开始。
6. 不在锁内执行网络调用。受托管撤销失败按 SEC-005 最多重试 3 次，采用有界超时和退避；最终结果保留 `partial`。不新建分布式调度框架，不丢失本进程内待处理句柄。
7. 写入不含秘密的失效摘要：组织、连接器、操作者、代次、清理数量、撤销结果、错误类别。审计失败不能取消已经完成的阻断；同时不得被报告成完整成功。可靠持久审计仍为独立缺口。

### 5.2 接口契约

已在编码前将以下契约落实到 [MCP API 文档](../api/sec-007-mcp-connector-governance-api.md)，随后编写生产代码。

| 接口 | 已批准约定 |
|---|---|
| `AuthorizationManager.invalidate_connector_credentials(connector_id, org_id, reason, actor)` | 连接器级、跨全部用户、重复调用安全；返回结构化失效结果，禁止调用方注入 token 内容 |
| `SEC005CredentialProxyClient.revoke_connector_credentials(connector_id, org_id, reason)` | 只撤销该组织/连接器所签发的句柄；不得扩大为整任务或其他连接器撤销；失败保留索引 |
| `LifecycleManager(..., authorization_manager=...)` | 复用既有管理器；所有停用入口触发同一失效过程。需要认证却未装配时仍先阻断，撤销结果记 `unconfigured`，恢复不得绕过 |
| `LifecycleManager.pause/revoke/transition_to` | 保留现有调用参数和布尔返回的“状态是否生效”含义；该 bool 不表示远端撤销完成，文档必须明确 |
| `LifecycleManager.get_credential_invalidation_status(connector_id, *, org_id)` | 返回失效摘要，由可信组织上下文使用；不返回令牌、根密钥、refresh token 或其他组织记录 |
| OAuth 存入/刷新及 TokenManager | 使用结构化作用域键和代次；旧操作的结果拒绝写入；内部兼容调整同步调用方及契约测试，不接受无代次的迟到异步回调 |

失效结果草案字段：`connector_id`、`org_id`、`generation`、`local_invalidated`、`cleared_count`、`credential_revocation_status`（`not_required/complete/partial/unsupported/unconfigured`）、`pending_count`、`retryable`、`audit_recorded`、`error_code`。其中 `complete` 仅表示**已装配的撤销提供方**确认完成；供应商真实能力未验证时必须标明验证范围。零缓存不等于零已签发租约。

此切片只新增内部 Python 契约，不新增 HTTP 管理端点。不会修改已冻结的 RT 实体或 Event Schema；SEC-005 的既有请求/响应字段保持兼容，连接器映射留在适配器内。若实施中必须修改共享契约，则停下提交冲突确认。
